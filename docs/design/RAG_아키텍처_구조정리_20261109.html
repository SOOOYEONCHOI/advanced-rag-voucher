README, 구현 현황·GPU·pgvector 분석, 모듈화 구조 분석(모두 2026-11-09)과 코드 기본값을 한 장으로 묶었습니다.

4가지 질문에 대한 결론부터.

① 검색 구성

Dense·Sparse·RRF·Reranker·Fallback·파싱 모두 구현

기본은 Qdrant 서버 측 Dense + Kiwi BM25 + 가중 RRF → bge-reranker. BM42·SPLADE는 선택 경로. 검색 DB 장애 시 다른 DB로 전환하는 기능은 없음.

② 평가

골든셋 생성→검수→평가→대시보드까지 구현

보관된 수치(6월: Recall@10 81~88%, 인용 정확도 약 37%)는 현재 버전 성능이 아님. 평가셋 편향·평가와 운영 조건 차이 보완이 필요.

③ GPU

모델별 vLLM 프로세스, H100 2장 운영 기록

L40S 48GB 1장은 핵심 3개 모델만, 입력 길이·동시성을 줄이면 시험해볼 수 있는 후보. ASR·TTS·VLM까지 상주는 불가에 가까움.

④ pgvector

현 단계는 Qdrant 유지가 합리적

근거는 통합 완성도·한국어 sparse·부하 분리·전환 비용. 품질·속도 우위는 같은 조건 비교 실험이 없어 미입증.

전체 아키텍처

CPU 백엔드가 업무 로직·그래프를 돌리고, GPU 작업(생성·임베딩·재정렬·파싱·음성)은 모두 별도 서버를 HTTP로 호출합니다. 외부 AI API는 쓰지 않습니다.

포트·GPU 번호는 운영 배포 스크립트(deploy/gpu/…/run-*.sh) 기준. 개발 통합 스크립트는 GPU 0 한 장에 8001/8002/8003.

모듈·계층 구조

한 백엔드 안에서 책임을 나누고, 핵심 구현체를 교체할 수 있게 만든 모듈형 모놀리스입니다. 마이크로서비스나 독립 SDK로 분리된 상태는 아닙니다.

adrag_backend/app/
├─ routes/        HTTP API (chat·query·ingest·evaluation·voice …)
├─ services/      업무 로직 (rag_service·ingest_service·version …)
├─ graphs/        LangGraph 질의 처리
│   ├─ rag_graph.py      노드 연결·분기 조립
│   ├─ nodes/            12개 단계
│   ├─ edges.py          조건 분기
│   ├─ retrieval_engine  검색 채널·RRF 설정
│   └─ preprocessing/    질의 정규화·키워드
├─ core/          config·runtime_settings·container·registry·http
├─ interfaces/    Protocol 계약 (embedding·reranker·llm·vectorstore…)
├─ clients/       모델 서버 호출 (vLLM·Kiwi BM25·sparse·ASR)
├─ repositories/  PostgreSQL·Qdrant 접근
├─ parsers/       loaders·detectors·chunkers·processor
├─ ingest/        Excel 라우팅·청크·사진·레코드
├─ evaluation/    ports·adapters·dataset·metrics·runner
├─ prompts/ models/ utils/
adrag_backend/excel_ingest/        Excel 사진·구조 추출(수정 금지)
adrag_backend/offline_evaluation/  CLI 평가·골든셋·기록 결과

임베딩·Reranker교체 쉬움 Protocol + 팩토리
LLM교체 가능 별도 레지스트리
파서·청커단독 사용 가능 자체 레지스트리

벡터 DB부분 Qdrant 자료형·필터가 곳곳에 남음

조립 방식 — 컨테이너·계약·레지스트리

여기서 “컨테이너”는 Docker가 아니라 필요한 객체를 만들어 연결하는 Python 객체(PipelineContainer)입니다.

Settings (env + DB 설정)→ PipelineContainer→ GraphDependencies(settings, container)→ partial(node, deps=…)→ LangGraph
장치역할현재 등록 구현주의
core/container.pyembedding·vector_store·sparse·kiwi_bm25·reranker·preprocessor를 cached_property로 지연 생성embedding=vllm, vector_store=qdrant, reranker=vllm설정 이름만 바꿔서는 새 구현이 생기지 않음 — 클래스 작성 + 팩토리 등록 필요
interfaces/typing.Protocol 계약(EmbeddingProvider, Reranker, LLMProvider, VectorStore, DocumentParser…)상속 없이 메서드만 맞으면 사용메서드 이름뿐 아니라 반환 형식·점수 척도까지 맞아야 교체 가능
core/registry.py최종 답변 LLM 선택local, openai(호환 코드만, 사용 승인 아님)container.local_llm만 바꿔도 최종 답변 LLM은 그대로
core/http.py프로세스 전역 httpx.AsyncClient 연결 풀(timeout 120s, 최대 연결 100)임베딩·Reranker·LLM·ASR·의미보강재시도·회로차단 없음. Docling·Qdrant·PG는 이 풀을 거치지 않음
runtime_settings.py기본 설정에 DB 저장 설정을 덮어씀. 버전이 바뀌면 그래프 재생성—일부 요청 초기화는 아직 get_settings() 사용
교체 절차 요약: ① 모델 서버 준비 → ② URL·모델명·입력 한도 맞춤 → ③ API가 같으면 설정만, 다르면 Protocol 구현 + 팩토리 등록 → ④ 임베딩은 차원·정규화 확인 후 재색인 → ⑤ Reranker 임계값·LLM 컨텍스트 예산 재평가.

질의 처리 그래프 (LangGraph 12노드)

일반 질의(ainvoke)와 스트리밍(astream_events)이 같은 그래프를 씁니다. 실패 경로가 노드 단위로 분리되어 있습니다.

점선 = 실패·재시도 경로. 입력 오류·가드레일 차단·권한 오류·검색 시스템 오류는 곧바로 build_response로 갑니다.

적재(Ingest) 파이프라인

업로드→ ParseStep
원본 저장·컬렉션 확인→ ChunkStep
파일 라우팅·파싱·청킹·사진 연결→ EmbedStep
Qwen3-Embedding→ IndexStep
Qdrant·PG·자원·버전 반영

단계별 체크포인트·재개·실패 보상이 있고, 새 버전이 활성화되면 검색 필터가 활성 버전만 보도록 연동됩니다. Excel은 백엔드 전용 경로(EXCEL_PARSE_MODE)와 파서 서버 경로(EXCEL_PARSER) 두 설정이 따로 있습니다.

질문 ①RAG 검색 구성과 지금 구현 범위

하이브리드 검색(Dense·Sparse·RRF), Reranker, Fallback, 문서 파싱 각각 어디까지 구현됐는지.

후보가 줄어드는 과정 (코드 기본값)

Dense 질문별 ≥80+Kiwi BM25 ≥80→ 가중 RRF(k=60) → 40→ Reranker → 10→ 컨텍스트 최대 6 (문서당 2)
구성상태구현 내용한계·확인할 점
Dense기본Qwen3-Embedding-4B, 코사인. 재작성 질문이 여러 개면 각각 검색하고 Dense 가중치를 나눠 배분(1.5 ÷ 3 = 0.5씩)—
Sparse: Kiwi BM25기본적재·질의 모두 Kiwi 형태소 토큰 → qdrant/bm25 형식, named sparse kiwi_bm25, IDF는 Qdrant. k1 1.2 / b 0.5 / 평균 길이 128. 확장 용어·법령 참조·키워드 반영k1·b 값이 현재 방식에서 최적이라는 근거 없음
BM42선택FastEmbed 로딩·인코딩·Qdrant sparse 검색기본 qdrant_hybrid 경로에는 들어가지 않음
SPLADE선택외부 /encode 서버 호출 클라이언트서버 배포·가동 증거 없음
Python BM25Legacy제한 후보에서 BM25 재계산 (retrieval_engine="legacy")주석 일부가 과거 방식을 설명 — 실제 분기 기준으로 판단
RRF기본Qdrant Query API 한 번 호출로 prefetch + 가중 RRF. 질의 유형별 가중치(아래 표)가중치는 코드상 “평가셋으로 튜닝할 초기값”
Reranker기본bge-reranker-v2-m3를 vLLM /v1/score로. 본문 해시 중복 제거, 문서명·섹션 경로를 앞에 붙여 채점, 응답 개수·인덱스·점수 검증top_k=10은 “10개 반환”이지 “10개만 채점”이 아님 → 후보 수·길이가 부하 결정. 임계값 0.25 ≠ 정답 확률 25%
Fallback기본관련성 미달 → 범위 확대 재검색(원 질문·임계값 0.1, 1회) / Reranker 장애 → RRF 상위 사용·CE 임계값 우회 / LLM 오류 → 컨텍스트 재사용해 생성 재시도 / 재시도 후 근거 부족 → “관련 정보 없음”없음 Qdrant 장애 시 다른 검색 DB로 전환. Reranker 장애 경로 품질은 따로 평가 필요
질의 유형DenseKiwi BM25
법령·조문 참조0.71.5
개념 설명1.50.7
메뉴·매뉴얼0.81.5
사고 사례·서술형1.50.8
RRF는 척도가 다른 코사인 유사도와 BM25 점수를 직접 더하지 않고 순위로 합칩니다. 그래서 정확한 용어(모델명·조문·메뉴명) 질문은 BM25 쪽 가중치를 높이는 구조입니다.

배분에서 얻은 교훈: ① LLM 55.8GB는 가중치 필수량이 아니라 vLLM이 미리 잡은 예산(0.70×80)이며 대부분 KV 캐시입니다. ② 생성(지연 민감)과 임베딩(적재 시 대량 배치)을 다른 GPU에 나눠, 문서 적재 중 임베딩 부하가 채팅 생성과 연산을 다투지 않도록 배치했습니다(효과를 수치로 측정한 기록은 없음). ③ max-model-len은 backend의 VLLM_MAX_MODEL_LEN·EMBEDDING_MAX_MODEL_LEN과 반드시 같아야 합니다(작으면 긴 청크에서 400 오류). ④ 추가 예정인 TTS(약 20GB)·VLM(약 25~35GB)은 GPU 1 여유로 넣는 안이 검토되었습니다.

L40S 48GB 1장으로 가능한가?

판단: 핵심 3개(LLM 9B + 임베딩 4B + Reranker)만, 입력 길이·동시성을 줄이면 “시험해볼 수 있는 후보”. 현재 운영 설정·처리량 그대로는 보장 불가, 음성·VLM까지 상주는 불가에 가깝습니다. 16비트 가중치 개략치는 LLM 약 18GB + 임베딩 약 8GB + Reranker 1GB대 = 약 27GB. 남는 약 20GB에 KV 캐시·활성값·CUDA 컨텍스트·파서를 넣어야 합니다.
L40S 48GB — 시험용 배분 예시 미검증합계 약 41.8GB + 여유 약 6GB
LLM 0.60 ≈ 28.8GB
임베딩 0.22 ≈ 10.6
조건판단조정 방향
핵심 3개, 짧은 입력·낮은 동시성가능성 있음LLM max-model-len 16K 이하·max-num-seqs 4~8, backend 컨텍스트 예산도 함께 축소
현재 24K 입력 + 동시 16부하 시험 필요KV 캐시가 약 10GB대로 줄어 동시 처리량 저하 예상
대량 임베딩 + 채팅 동시경합 검증 필요같은 GPU 연산을 나눠 쓰므로 적재 중 채팅 P95 측정
+ Docling OCR피크 확인 필요대기 약 2.6GB, 파싱 피크는 더 큼 — 여유분으로 감당되는지 측정
+ ASR·TTS·VLM 상주보장 불가TTS 약 20GB·VLM 25~35GB만으로 여유 초과
H100 비율을 그대로 복사하면 안 됩니다. 개발 스크립트의 임베딩 0.12는 48GB에서 약 5.8GB로 4B 가중치보다 작습니다. 부족하면 LLM FP8 양자화(L40S 지원)나 더 작은 모델을 비교 평가하되, 바꾼 뒤에는 검색·답변 품질을 다시 측정해야 합니다.

검증 순서: 핵심 3개만 기동 → 입력 길이·동시 시퀀스 보수적 제한 → 임베딩 배치·Reranker 입력 길이 제한 → 단일·동시 질의 측정 → 적재 병행 시 메모리 최대치·P95 확인 → 부족 시 양자화·소형 모델 비교.

질문 ④PGVector 하이브리드 검색 대비 현재 방식

결론: 현 단계에서는 Qdrant 유지가 낫다 — 다만 “검색 품질·속도가 더 좋다”는 근거가 아니라 “이미 통합·검증된 범위를 유지하고 전환 비용을 피한다”는 근거입니다. pgvector도 PostgreSQL 전문 검색과 결합해 RRF·Cross-encoder를 붙일 수 있으므로, 같은 임베딩·토큰화·후보 수·Reranker를 쓰면 품질 차이는 작을 수 있습니다. 품질은 DB 이름보다 파싱·청킹·토큰화·후보 누락이 좌우합니다.
관점현재 Qdrantpgvector 전환 시
검색 구성완료 Dense·Kiwi sparse·가중 RRF를 서버 측 한 번 호출로Kiwi 토큰화·BM25 정책·RRF를 SQL로 재구성 필요. PG 기본 전문 검색은 한국어 형태소 분석이 약함
한국어 정확 용어적재·질의에 같은 Kiwi 정책Kiwi를 빼면 비교 대상 자체가 달라짐
부하검색 부하가 업무 DB와 분리권한·버전·작업큐와 같은 PG 자원 공유
일관성약점 PG·Qdrant 두 저장소 동기화 관리강점 메타데이터·벡터 한 트랜잭션, 권한·버전 SQL 조인
운영벡터 DB 별도 서버(Ubuntu) 관리백업·복구 대상 단순화
임베딩 차원제약 없음Qwen3-Embedding-4B 최대 2,560차원 → 일반 vector HNSW 한도 2,000 초과. halfvec(4,000) 또는 차원 축소 검토. 실제 컬렉션 차원은 확인 필요
권한 필터Dense·Sparse prefetch에 같은 권한·활성 버전 필터필터가 강하면 근사 검색 후보가 모자랄 수 있어 iterative scan 튜닝 필요
