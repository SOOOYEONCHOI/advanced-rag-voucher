- 최종 상세 설계(2026-11-05): [백엔드 최종 설계 v1.1](문서_이전버전_복원_백엔드_최종설계_v1.1.md), [화면 영역별 API 명세 v1.1](문서_이전버전_복원_화면영역별_API_명세_v1.1.md). (v1.0은 이력 보존용) 화면 기준은 사용자 수정 목업 `mockups/admin_UI-12_이전버전복원_20261104_v0.2.html`이다. 상세 계약이 다른 부분은 이 최종 설계·API 명세를 따른다.
- 역할 분담: 백엔드 구현은 본 개발 범위이며, 프런트엔드 구현은 별도 개발자가 목업과 API 명세로 진행한다.

- 요구사항 식별자: 본 문서의 `VR-*`는 개발 추적용 임시 ID이며 기존 공식 기능 ID를 대체하지 않는다.

## 1. 목적과 확정 방향

문서 관리의 버전 이력에서 정상 처리된 이전 버전을 선택하면 문서 정보, 검색 대상 벡터, 청크, 사진 및 출처가 해당 버전으로 돌아가야 한다.

버전별 임베딩을 Qdrant에 보존하고 PostgreSQL의 현재 적용 버전을 전환한다. 정상 복원 과정에서는 파싱이나 재임베딩을 수행하지 않는다. 과거 벡터와 payload를 그대로 이용한다.

- 현재 v3에서 v1을 복원하면 현재 적용 버전은 v1이 된다. 복원 자체로 v4를 생성하지 않는다.
- 이후 새 파일을 올리면 전체 이력의 최대 버전 번호에 1을 더해 v4를 생성한다.
- 복원 행위는 버전 생성 이력과 별도의 적용 이력으로 누적 기록한다.
- 이전 버전의 내용은 유지하되 접근 권한은 현재 문서·대화 주제의 권한을 적용한다.

기존 D-18은 미구현 복원을 1차에서 제외하고 있으나, 이번 사용자 요청으로 별도 개발 대상으로 구체화한다. 구현 시 변경로그와 공식 요구사항의 범위 조정 사항을 함께 기록한다. 권한은 D-18에 맞춰 관리자 전용을 추천 기본안으로 한다.

## 2. 현행 구현과 변경 범위

| 항목 | 현행 소스 기준 | 요구 변경 |
|---|---|---|
| 버전 정보 | `tb_document_versions`, 기본키 `(document_id, version_no)` | 기존 이력 유지, 복원 검증에 필요한 메타데이터 보완 |
| 현재 문서 | `tb_documents.version_no` 및 현재 파일 정보 | 복원 시 같은 트랜잭션에서 일괄 변경 |
| 벡터 식별 | Qdrant payload의 `document_id`, `version_no` | 모든 신규 포인트에 필수 저장, 버전별 ID 충돌 방지 |
| 이전 벡터 | 최신본 전환 후 비활성 버전 포인트 삭제 | 정상 완료된 버전의 포인트 보존 |
| 검색 필터 | `version_visibility.py`의 공통 비활성 버전 제외 조건 | 보존된 모든 비활성 버전에 적용, 모든 검색 경로 점검 |
| 처리 작업 | `tb_ingest_jobs`와 기존 작업 처리 구조 | 복원 작업의 진행·실패·재시도 지원 |
| 버전 이력 UI | 실제 이력 조회, 복원 버튼 없음 | 복원 가능 여부·불가 사유·복원 실행 제공 |

현재 소스의 `vectors_purged_at`은 벡터 삭제 시각이다. 보존 여부와 복원 가능 여부를 이 컬럼 하나로 판단하지 않는다. 운영 데이터의 실제 보존 상태는 별도 조사 대상이다.

## 3. 기능 요구사항

### VR-01. 화면과 권한

- 버전 이력에서 복원 가능한 이전 버전을 단일 선택하고, 하단 ‘선택 버전 복원’ 버튼으로 확인창을 연다. 확인창의 ‘이 버전으로 복원’에서만 API를 호출한다(v0.2 목업 기준).
- 관리자만 실행할 수 있도록 프런트엔드와 서버 양쪽에서 검사한다. 비관리자의 이력 열람은 기존 정책을 유지한다.
- 확인창에 문서명, 현재 버전, 복원 대상 버전과 ‘검색·답변도 선택 버전으로 변경됩니다’를 표시한다.
- 현재 적용 버전, 처리 중 버전, 실패 버전에는 복원 버튼을 비활성화하고 사유를 표시한다.
- 데이터 누락 또는 모델 호환 문제로 복원이 불가능한 버전도 구체적인 사유를 표시한다.
- 접수 후 처리 상태를 표시하고 완료 시 문서 목록과 버전 이력을 갱신한다. 실패 시 기존 버전 유지 사실과 실패 사유를 알린다.
- 버튼 중복 클릭을 차단하고 화면 새로고침 후에도 진행 상태를 확인할 수 있어야 한다.

### VR-02. 복원 가능 조건

아래 조건을 모두 만족해야 적용할 수 있다.

1. 문서가 삭제되지 않았으며 실행자에게 관리·열람 권한이 있다.
2. 대상은 해당 문서에 속하고 정상적으로 적용된 이력이 있는 이전 버전이다.
3. 대상 벡터와 검색 payload가 완전하며 해당 임베딩 프로필로 질의할 수 있다.
4. 원본 파일, 청크 및 대상 버전에서 사용하던 사진·출처·연결 정보가 유효하다. 사진이 없는 문서에 사진 존재를 요구하지 않는다.
5. 같은 문서의 최신본 변경·복원·삭제 작업이 진행 중이지 않다.
6. 클라이언트가 확인한 현재 버전과 서버의 현재 버전이 일치한다.

복원 가능 여부는 서버가 판단한다. 화면에서 가능으로 보였더라도 실행 시 반드시 다시 검사한다.

### VR-03. 벡터와 관련 데이터 보존

- 동일 Qdrant 컬렉션 안에 호환되는 임베딩 프로필의 여러 버전을 보존한다.
- 포인트 ID는 최소 문서·버전·청크를 구분한다. 복원 시 기존 포인트 ID와 벡터를 재사용한다.
- 정상 최신본 전환 시 이전 정상 버전의 벡터·청크·원본·리소스·연결 정보를 삭제하지 않는다.
- 실패한 신규 적재의 불완전 데이터 정리는 유지하되 다른 정상 버전의 데이터를 지우면 안 된다.
- 즉시 정리뿐 아니라 재시도·예약 정리 경로도 보존 정책을 따라야 한다. 기존 purge 작업이 보존 벡터를 나중에 삭제하지 않도록 변경한다.
- 초기 정책은 문서가 유지되는 동안 정상 버전을 모두 보존한다. 용량을 모니터링하며 기간·개수 기반 자동 삭제는 이번 범위에서 도입하지 않는다.
- 문서 삭제 시 모든 버전의 검색 노출을 즉시 차단하고 기존 삭제 정책에 따라 전체 버전 파일·벡터·리소스를 정리한다. 감사 기록 보존 범위는 삭제 정책과 함께 명시한다.

### VR-04. 검색·답변 일관성

- 적용 버전의 기준은 PostgreSQL `tb_documents.version_no` 하나로 통일한다.
- Qdrant 포인트마다 `is_active`를 갱신하는 방식을 적용 버전의 기준으로 사용하지 않는다.
- 비활성 버전 제외 조건과 현재 사용자 권한 조건을 Qdrant 검색 전에 적용한다. 검색 결과를 받은 뒤 이전 버전만 제거하는 방식으로 대체하지 않는다.
- 밀집·희소·하이브리드 검색, 키워드·스크롤 조회, 재순위화 입력 및 직접 청크·사진 조회 등 관련 경로에서 동일한 버전 규칙을 지킨다.
- 버전 필터에 필요한 DB 조회가 실패하면 필터를 생략하지 않고 해당 검색을 실패 처리한다.
- 레거시 포인트의 `version_no` 누락을 v1으로 취급하는 기존 규칙은 데이터 확인·보정 계획과 함께 관리한다. 임의의 누락 포인트를 v1으로 간주하지 않는다.
- 청크·사진·출처 해석은 `(document_id, version_no)`를 포함해 수행한다. 현재 파일 경로만 사용해 과거 출처를 잘못 여는 문제를 방지한다.
- 검색·답변 캐시에 적용 버전 변경을 반영한다. 적용 버전 집합을 캐시 키에 포함하거나 전환 후 무효화한다.
- 요청 시작 시 선택한 버전을 해당 요청의 검색·사진·출처에 일관되게 사용한다. 전환 전에 시작된 답변은 기존 버전으로 완료할 수 있고 전환 후 시작된 요청부터 복원 버전을 사용한다.
- 문서·버전 수가 증가할 때 필터 크기와 검색 지연을 측정한다. 초기에는 공통 필터를 확장하고 별도 활성 검색 인덱스 도입은 측정 결과가 필요할 때 검토한다.

### VR-05. 전환 처리와 동시성

1. 복원 요청을 검증하고 문서별 진행 작업을 등록한다. 같은 문서의 변경 작업은 하나만 허용한다.
2. 데이터 보존 상태·벡터 무결성·모델 호환성을 검사한다. 준비 작업 중에는 현재 적용 버전으로 서비스한다.
3. 최종 전환 트랜잭션에서 문서 잠금을 획득하고 삭제 여부, 현재 버전, 진행 작업 소유권, 대상 버전을 다시 확인한다.
4. 기존 `active`를 `retired`로 변경하고 대상 버전을 `active`로 변경한다. 문서당 `active`는 정확히 하나여야 한다.
5. `tb_documents`의 버전·파일·파싱 결과 등 현재 내용 정보와 적용 시각을 갱신한다. 모델명, 문서 식별자, 소유자, 대화 주제 및 현재 권한은 유지한다.
6. 적용 이력과 작업 성공 상태를 같은 PostgreSQL 트랜잭션에 기록한다.
7. 커밋 후 캐시를 갱신하고 완료 상태를 반환한다.

- 외부 데이터 검증 중 장시간 DB 트랜잭션을 유지하지 않는다. 짧은 문서 잠금과 지속적인 진행 작업 표식을 함께 사용한다.
- 복원 대상 버전의 `retired_at`은 현재 상태와 모순되지 않도록 처리한다. 최초 업로드 정보는 유지하고 반복 적용 시각은 별도 적용 이력에 모두 기록한다.
- 업로드 버전 번호는 현재 버전이 아닌 전체 이력의 `MAX(version_no) + 1`로 계산한다.
- 복원은 벡터를 쓰지 않는 RDB 전환이 기본이다. 백업 복구가 필요하면 Qdrant 복구·검증을 먼저 마치고 적용 버전을 전환한다.

### VR-06. 오류·재시도·복구

- 검증 또는 전환 커밋 전에 실패하면 현재 적용 버전을 유지하고 작업만 실패 처리한다.
- 커밋 후 응답 유실·캐시 갱신 실패는 ‘전환 실패’로 오인해 자동 역전환하지 않는다. 작업 조회로 실제 결과를 확인하고 후속 처리를 재시도한다.
- 동일 멱등 키의 요청은 동일 작업·결과를 반환한다. 다른 대상에 같은 키를 사용하면 충돌로 처리한다.
- 워커 재시작 시 진행 작업을 복구하고, 성공 여부를 확인한 뒤 필요한 단계부터 재시도한다.
- 문서 잠금은 기존 최신본 변경·삭제 흐름과 공통으로 사용한다. 버전 `building/ready`만 검사해서 복원 작업을 놓치지 않도록 한다.

## 4. 데이터 설계 요구사항

아래 이름은 신규 항목의 제안명이며 구현 시 현행 스키마와 최종 대조한다. 변경은 Alembic upgrade·downgrade로 제공한다.

| 저장소 | 보완 내용 |
|---|---|
| `tb_documents` | 현재 버전 포인터 유지. 반복 적용 및 동시성 구분용 `activation_revision` 등 단조 증가값 추가 권장 |
| `tb_document_versions` | 임베딩 프로필 참조, 벡터 보관 상태, 기대 포인트 수·ID/내용 검증 정보, 검증 시각 보완 |
| 신규 `tb_document_version_activations` | 문서 ID, 변경 전·후 버전, `upload/restore` 구분, 실행자, 적용 시각, 작업 ID, 적용 순번 기록 |
| `tb_ingest_jobs` | 작업 유형·대상 버전·예상 적용 순번·멱등 키·처리 결과를 기존 구조에 맞춰 저장 |
| 신규 `tb_embedding_profiles` | 불변 모델 리비전, 벡터 차원·거리 함수·정규화·벡터 이름, 질의 인코딩 방식, 관련 처리 설정·지원 여부 기록 |
| 청크·리소스 테이블 | `tb_chunks`, `tb_chunk_resources`, `tb_spreadsheet_resources`, `tb_flow_graphs` 등의 버전별 조회·보존 검증 |
| Qdrant | 기존 벡터·payload와 함께 문서·버전·임베딩 프로필 식별자 유지, 검색 조건 필드 인덱스 점검 |

- 버전별 메타데이터는 현재 문서 화면·원본 열기·답변 출처를 재구성하기에 충분해야 한다. 기존 버전 테이블에 없는 문서 유형·제목 등의 필요한 값을 보완한다.
- 벡터 보관 상태는 예를 들어 `available`, `missing`, `archived`, `unknown`으로 구분한다. 상태 표기만 신뢰하지 않고 실제 검증 결과로 복원 가능 여부를 계산한다.
- 기대 포인트 수는 단순히 `chunk_count`와 같다고 가정하지 않는다. 텍스트·이미지 등 실제 적재 포인트의 종류와 ID 집합을 기준으로 검증한다.
- 프로필 기록이 없는 과거 데이터에 현재 모델을 무조건 대입하지 않는다. 신뢰할 수 있는 적재 기록으로 확인한 경우에만 보정한다.
- `vectors_purged_at`의 기존 삭제 이력 의미는 유지한다. 백업 복구 여부와 복원 가용성은 별도 상태·검증 기록으로 관리한다.

## 5. API 제안

| API | 목적 |
|---|---|
| 기존 `GET /api/ingest/documents/{document_id}/versions` | `can_restore`, `restore_block_reason`, 벡터 보관·모델 지원 상태 추가 |
| 신규 `POST /api/ingest/documents/{document_id}/versions/{version_no}/restore` | 복원 접수, `202`와 `job_id` 반환 |
| 기존 `GET /api/ingest/jobs/{job_id}` | 복원 진행·성공·실패 조회 |

- 요청에는 `expected_current_version_no`, `expected_activation_revision`, `idempotency_key`를 포함하는 안을 권장한다. 버전만 비교하면 v3 → v1 → v3의 중간 변경을 놓칠 수 있다.
- 성공 응답·작업 결과에는 문서 ID, 변경 전·후 버전, 적용 순번, 적용 시각을 포함한다.
- 주요 오류: `403` 권한 없음, `404` 접근 불가·삭제 문서, `409` 작업 중·현재 상태 변경·이미 적용 중, `422` 데이터 누락·모델 미지원, `503` 검증 저장소 일시 장애.
- 접근 불가 문서 응답은 기존 정보 비노출 정책을 우선 적용한다.

## 6. 고려사항 ① 이미 삭제된 과거 벡터 — 추천안

**추천: 기존 버전의 가용성을 먼저 조사하고, 동일 벡터를 확보할 수 있는 버전만 복원을 허용한다. 백업이 없으면 재임베딩을 ‘동일 벡터 복원’으로 처리하지 않는다.**

1. 문서·버전별 Qdrant 포인트, 원본, 청크, 리소스, 임베딩 프로필 존재 여부를 읽기 전용 점검 도구로 조사한다.
2. 벡터가 남아 있으면 ID 집합·포인트 수·payload·프로필을 검증한 뒤 복원 가능으로 표시한다.
3. 백업이 있으면 별도 임시 컬렉션 또는 격리 환경에 복구하고 대상 문서·버전의 포인트와 벡터·payload를 추출한다. 운영 컬렉션 전체를 과거 스냅샷으로 덮어쓰지 않는다.
4. 대상 버전만 원래 ID와 값으로 복구하고 관련 RDB·파일 데이터와 검증한 후 복원을 허용한다. 현재 버전과 다른 문서는 그대로 유지한다.
5. 백업도 없으면 ‘이전 벡터 없음: 동일 임베딩 복원 불가’로 표시한다. 원본 재처리가 필요하면 별도 명시적 작업으로 새 버전을 생성하며 이번 복원 기능과 구분한다.

신규 보존 버전은 사내 저장소에 Qdrant 백업, PostgreSQL 백업, 원본·리소스 백업과 버전별 검증 명세를 연계 보관한다. 권장 초기 백업은 일 1회 및 모델 전환·파괴적 작업 전이며, 보관 주기와 복구 목표는 운영 용량 기준으로 확정한다. 백업에는 dense/sparse 등 실제 사용하는 모든 벡터와 payload가 포함되어야 한다.

백업의 임베딩 값 동일성은 포인트별 벡터·payload 비교 또는 정규화된 해시 검증으로 확인한다. 포인트 개수 일치만으로 동일 복원을 판정하지 않는다.

## 7. 고려사항 ② 임베딩 모델 변경 — 추천안

**추천: 초기 릴리스는 현재 검색 프로필과 호환되는 버전의 복원만 허용한다. 모델 변경으로 호환성이 깨지는 경우 기존 모델·검색 경로를 유지할 준비가 되기 전까지 해당 버전의 복원을 차단한다.**

- 모델명 문자열만 비교하지 않는다. 모델 가중치 리비전, 차원, 거리 함수, 정규화, dense/sparse 구성, 질의 인코딩 설정을 불변 프로필로 식별한다.
- 차원이 같아도 서로 다른 모델의 벡터를 같은 의미 공간으로 간주하지 않는다.
- 현재 프로필과 호환되면 기존 컬렉션 안의 버전 전환으로 처리한다.
- 호환되지 않으면 화면에 ‘해당 버전의 임베딩 모델 미지원’과 사유를 표시한다. 다른 모델의 질의 벡터로 과거 벡터를 검색하지 않는다.
- 향후 서로 다른 프로필의 동시 활성화가 필요하면 프로필별 Qdrant 컬렉션·내부 모델 서비스로 검색을 분리한다. 해당 프로필로 질의를 임베딩하고 권한·버전 필터를 적용한 후 결과를 결합·재순위화한다. 서로 다른 모델의 원시 유사도 점수를 직접 비교하지 않는다.
- 과거 모델을 지원 종료하기 전 해당 프로필로 복원 가능한 버전을 조사하고, 유지 또는 복원 불가 전환을 명시적으로 결정한다.
- 원래 모델을 확보할 수 없어 재임베딩하는 경우 새 프로필의 새 버전으로 적재한다. 과거 버전의 벡터·프로필 기록을 덮어쓰지 않는다.
- 모델과 문서 데이터는 기존 사내 환경에서만 처리한다.

프로필별 다중 검색 구현은 향후 확장 범위다. 이번 범위에는 프로필 기록, 호환성 검사 및 미지원 복원 차단을 포함한다.

## 8. 도입 순서와 설정

1. 기존 데이터 가용성 점검 및 신규 스키마 마이그레이션을 준비한다.
2. 모든 검색 경로의 버전·권한 필터를 검증한 후 정상 버전 벡터 보존을 활성화한다.
3. 백그라운드 정리·재시도 작업까지 보존 정책을 적용하고 신규 버전의 검증 명세를 기록한다.
4. 백엔드 담당자는 복원 API·작업 처리·감사 이력을 구현하고, 프런트엔드 담당자는 별도로 화면을 연결한다.
5. 기존 버전 가용성 표시 및 격리 백업 복구 절차를 제공한다.
6. 테스트와 성능 점검 후 관리자가 기능을 활성화할 수 있도록 한다.

- 제안 설정: `DOCUMENT_VERSION_RESTORE_ENABLED` 기본 false, 정상 버전 벡터 보존을 위한 별도 설정도 기본 false로 시작한다.
- 검색 필터 검증 → 보존 활성화 → 복원 활성화 순서를 보장한다. 복원 활성화 시 보존 기능이 꺼져 있으면 설정 오류로 처리한다.
- 복원 기능을 끄더라도 이미 보존된 벡터를 삭제하거나 이전 purge 정책을 자동 재개하지 않는다. 기존 코드로 되돌릴 때도 보존 데이터를 삭제할 수 있는 워커·정리 작업을 먼저 중지한다.
- 스키마 downgrade는 복원 기능 중지 및 백업 후 수행한다. 보존 벡터 삭제를 downgrade에 포함하지 않는다.
- 운영 접속·반영은 별도 사용자 실행 절차로 제공한다.

## 9. 인수 테스트 및 완료 기준

| ID | 시나리오 | 통과 기준 |
|---|---|---|
| VR-T01 | v1 → v2 → v3 업로드 | 정상 버전의 벡터·청크·리소스 모두 보존, 검색은 v3만 사용 |
| VR-T02 | v3에서 v1 복원 | 현재 포인터 v1, v1 원본·청크·사진·출처 일치, 재임베딩 호출 0회 |
| VR-T03 | 동일 벡터 검증 | 복원 전 보관 값과 복원 후 사용 값의 벡터·payload 일치, 기존 포인트 ID 유지 |
| VR-T04 | v1 → v3 재복원 | 정상 전환, 적용 이력 두 건 유지, 문서당 active 정확히 하나 |
| VR-T05 | 복원 후 신규 업로드 | 현재 v1이어도 기존 최대가 v3이면 v4 생성 |
| VR-T06 | 데이터 누락·Qdrant 장애 | 전환 차단, 기존 문서·검색 유지, 구체적인 실패 사유 |
| VR-T07 | 동시 업로드·복원·삭제 | 동일 문서는 한 작업만 진행, 다른 요청 충돌 처리, 다른 문서는 독립 처리 |
| VR-T08 | 비관리자·권한 없는 문서 | 서버에서 차단, 문서·사진·출처·대상 버전 정보 누출 없음 |
| VR-T09 | 검색 채널·캐시 | 모든 채널에서 비활성 버전 제외, 캐시가 과거 답변 재사용하지 않음 |
| VR-T10 | 전환 중 요청 | 한 응답 안에서 버전 혼합 없음, 전환 후 신규 요청은 복원 버전 사용 |
| VR-T11 | 응답 유실·중복 클릭·워커 재시작 | 중복 전환·이력 생성 없음, 조회·재시도로 실제 결과 확인 |
| VR-T12 | 백업에서 특정 버전 복구 | 다른 문서·버전 불변, 벡터 동일성·관련 데이터 검증 후 적용 |
| VR-T13 | 모델 프로필 불명·불일치 | 복원 차단, 차원이 같아도 프로필이 다르면 호환으로 오판하지 않음 |
| VR-T14 | 문서 삭제·기능 비활성화 | 삭제 문서 전체 버전 검색 차단, 기능 비활성화가 보존 벡터 삭제를 유발하지 않음 |
| VR-T15 | 장기 보존 부하 | 대표 문서·버전 수에서 검색 전 필터 적용 확인, 검색 지연·필터 크기·저장 용량 측정 및 기존 기준선 비교 |

성능 통과 수치는 구현 전 현행 기준선과 예상 보존량을 측정해 합의한다. 측정 없이 임의의 응답 시간 보장을 확정하지 않는다.
