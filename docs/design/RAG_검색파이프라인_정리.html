검색 파이프라인 해설

사용자가 질문을 보내면 어떤 순서로 문서 조각(청크)을 찾고 줄이고 골라서 LLM에 넘기는지, 단계마다 누가 무엇을 하는지 정리했습니다.

기준: 2026-11-11 · refactor-1 브랜치 코드 대상 폴더: adrag_backend/app/graphs/

한눈에 보기

검색은 Qdrant의 Query API 한 번 호출로 끝납니다. 의미 검색(Dense)과 키워드 검색(BM25)을 Qdrant 서버가 각각 실행하고, 두 결과를 서버 안에서 RRF로 합쳐서 돌려줍니다.

  • 우리 코드는 검색 전 준비(질의 정리, 재작성, 임베딩, Kiwi 토큰화, 권한 필터, 가중치 결정)와 검색 후 정리(점수 가산, 리랭크, 관련성 판단, 컨텍스트 조립)를 맡습니다.
  • BM25는 토큰화만 우리가 하고(Kiwi), 점수 계산은 Qdrant가 합니다(qdrant/bm25 + IDF).
  • 검색 결과 40개를 리랭커가 다시 채점해 10개로 줄이고, 그중 기준 점수를 넘는 최대 6개가 LLM 컨텍스트에 들어갑니다.
앱(파이썬) Qdrant 서버 리랭커 서버 LLM·임베딩 서버

전체 흐름

LangGraph로 만든 12개 노드 그래프입니다(graphs/rag_graph.py). 회색 줄이 이 문서에서 다루는 검색 구간입니다.

단계별 설명

1

규칙 기반 질의 전처리

앱

LLM 없이 사전과 정규식, Kiwi 형태소 분석만으로 질문을 정리합니다. 순서는 다음과 같습니다.

  1. 정규화: 유니코드 NFC, 제어 문자 제거, 연속 공백 정리
  2. 복합어 띄어쓰기 통일: 사전의 복합어를 기준으로 띄어 쓴 변형을 하나로 맞춤
  3. 약어 확장: 한글 약어는 정식 명칭으로 바꾸고, 영문 별칭은 원문을 남긴 채 정식 명칭을 expanded_terms에 추가
  4. 법령 표기 통일: "3조"를 "제3조"로 바꿈. 뒤에 조사나 기호가 올 때만 바꾸므로 "3호기", "2조립"은 그대로 둠. QUERY_LAW_NOTATION_NORMALIZE=false면 건너뜀
  5. 패턴 추출: 법령 조문(제N조)과 날짜
  6. 키워드 추출: 띄어쓰기 토큰을 먼저 보존하고, Kiwi 명사로 보완. 기능성 불용어는 제외

graphs/preprocessing/query_preprocessor.py · 설정 ENABLE_QUERY_PREPROCESSING · 사전은 YAML 통합 사전

2

질의 재작성과 임베딩

LLM·임베딩

1단계 결과를 "전처리 힌트"로 붙여 로컬 LLM에 한 번 보내고, 검색용으로 다시 쓴 질의 몇 개를 JSON으로 받습니다. 기다리는 동안 원문 질의 임베딩을 동시에 계산합니다.

  • 원문 질의는 항상 목록 맨 앞에 둡니다. 재작성이 엇나가도 원문으로는 반드시 검색됩니다.
  • 재작성 질의는 한 번에 묶어 임베딩합니다. 실패하면 원문 임베딩으로 대신합니다.
  • LLM 호출이 실패하면 원문 질의 하나로만 진행합니다.

graphs/nodes/analyze_and_rewrite.py · 프롬프트 REWRITE_PROMPT · 임베딩 모델 EMBEDDING_MODEL_NAME

3

권한 필터 구성

앱

사용자 권한을 읽어 Qdrant 필터의 must 조건을 만듭니다. 이 필터는 다음 단계의 모든 검색에 똑같이 붙습니다.

  • security_level: 사용자 최고 등급 이하를 모두 허용(상위 등급이 하위 등급을 포함)
  • source_collection: 접근 가능한 컬렉션. 요청한 컬렉션과 겹치는 게 없으면 검색 없이 오류로 종료
  • 사용자별 추가 필터(metadata_filters)를 덧붙이되, 핵심 필드는 덮어쓰지 않음
  • 로그인하지 않은 사용자는 public 등급과 ANONYMOUS_DEFAULT_COLLECTIONS만 허용

4

검색어 묶음 만들기

앱

같은 질문을 검색 방식에 맞는 서로 다른 입력으로 나눕니다(QueryBundle).

입력구성쓰는 곳
dense_queries원문 질의 + 재작성 질의(중복 제거)와 각각의 임베딩Dense 검색
kiwi_bm25_query정규화 질의 + 확장 약어 + 법령 조문 + 키워드를 공백으로 이은 문자열BM25 검색

이어서 Kiwi 인코더가 kiwi_bm25_query를 토큰으로 자르고, Document(model="qdrant/bm25", options={k, b, avg_len}) 형태로 감쌉니다. 이 시점에는 아직 숫자 벡터가 아니라 "토큰을 공백으로 이은 글"입니다.

Dense는 문장 의미가, BM25는 정확한 단어 일치가 중요합니다. 그래서 Dense에는 자연스러운 문장을, BM25에는 핵심 단어를 모은 문자열을 넣습니다.

graphs/retrieval_engine.py build_query_bundle() · clients/kiwi_bm25_encoder.py

질의 유형 분류와 가중치 결정

앱

전처리 결과로 질문을 네 가지 유형 중 하나로 나누고, 유형마다 Dense와 BM25 중 어느 쪽 결과를 더 믿을지 정합니다.

유형판별 조건legacy 표
Dense / BM25		sop 표
Dense / BM25
법령 조문"제N조" 패턴이 있음0.7 / 1.50.7 / 1.5
메뉴·매뉴얼메뉴, 화면, 버튼, 탭 등의 단어0.8 / 1.51.0 / 1.5

어느 표를 쓸지는 QUERY_TYPE_PROFILE(legacy | sop)로 고릅니다. 작업표준 문서는 모델 코드나 부품명 같은 정확한 단어가 중요해서, sop 표는 BM25 쪽을 높게 둡니다.

Dense 가중치는 질의 수만큼 나눕니다. 예를 들어 Dense 1.0에 질의가 3개면 각 0.333입니다. 재작성 질의가 늘어나도 Dense 쪽 총합은 그대로입니다. DENSE_ORIGINAL_QUERY_SHARE를 주면 원문 질의에 그 비율을 먼저 떼어 줍니다.

6

Qdrant 하이브리드 검색

Qdrant 서버

준비한 것을 모두 담아 client.query_points()를 한 번 호출합니다. 실제 검색과 병합은 Qdrant 서버에서 일어납니다.

query_points() 한 번의 호출 안에서
Dense · 원문 질의using="dense" · limit 80
Dense · 재작성 1using="dense" · limit 80
Dense · 재작성 2 …using="dense" · limit 80
BM25 · Kiwi 토큰using="kiwi_bm25" · limit 80
↓ 각 prefetch에 같은 권한 필터 + 활성 버전 필터 적용 ↓
가중 RRF 병합점수 = Σ 가중치 ÷ (k + 순위)
↓
상위 40개 (chunk_id, RRF 점수, payload)
  • Prefetch는 "먼저 각자 후보를 뽑아 오는 하위 검색"입니다. Dense는 질의마다 하나씩, BM25는 하나입니다. 각 후보 수는 DENSE_PREFETCH_K·SPARSE_PREFETCH_K(기본 80)입니다.
  • BM25 점수: 앱이 보낸 토큰 글을 Qdrant가 qdrant/bm25로 희소 벡터로 바꾸고, 컬렉션의 kiwi_bm25 희소 인덱스(IDF 보정 켬)에서 점수를 매깁니다.
  • RRF는 점수 크기는 버리고 순위만 씁니다. Dense 코사인 점수와 BM25 점수는 척도가 달라서 직접 더할 수 없기 때문입니다. 여러 목록에서 꾸준히 위에 있는 청크가 높은 점수를 받습니다.
  • 활성 버전 필터: 문서를 개정하면 이전 버전 포인트가 Qdrant에 잠시 남을 수 있습니다. RDB(tb_documents.version_no)를 기준으로 활성 버전이 아닌 포인트를 모든 prefetch에서 뺍니다. 한 요청 안에서는 같은 버전 목록을 씁니다.
  • Qdrant 장애나 타임아웃(RETRIEVE_TIMEOUT, 기본 90초)이면 재시도하지 않고 바로 오류로 응답합니다. "문서 없음"과 구분하기 위해서입니다.

7

메타데이터 점수 가산

앱

Qdrant가 준 RRF 점수에 비율로 점수를 조금 더합니다. 질의 키워드가 청크 payload의 keywords와 겹치면 ×1.05, tags와 겹치면 ×1.03입니다. 다시 정렬한 뒤 후보 40개(CANDIDATE_TOP_K)를 남깁니다.

걸러내는 필터가 아니라 가산이라서 결과가 0건이 되지는 않습니다. RRF 점수가 0.0x 수준으로 작아서 고정값을 더하면 순위가 뒤집히므로, 곱하는 방식을 씁니다. 청크에 keywords·tags가 없으면 아무 영향이 없습니다.

graphs/retrieval_engine.py apply_soft_boost()

8

리랭크

리랭커 서버

후보 40개를 리랭커(크로스 인코더)가 원문 질문과 한 쌍씩 다시 읽고 0~1 사이 관련성 점수를 매깁니다. 위에서 10개(RERANKER_TOP_K)를 남깁니다.

  • 보내기 전에 본문이 같은 청크를 해시로 걸러 냅니다.
  • 본문 앞에 [문서명], 엑셀이면 [시트], [섹션]을 붙여 보냅니다. 리랭커가 맥락을 알면 점수가 정확해집니다.
  • 이 단계부터 청크의 score는 RRF 점수가 아니라 리랭커 점수입니다.
리랭커가 응답하지 않을 때: 타임아웃(RERANKER_TIMEOUT, 30초), 통신 오류, 응답 형식 오류가 나면 RRF 순서대로 상위 3개(RERANKER_DEGRADED_TOP_K)만 넘깁니다. RRF 점수는 기준 점수와 척도가 달라 전부 탈락하므로, 이때는 기준 점수를 0으로 임시 해제합니다(threshold_override). ENABLE_RERANKING=false일 때도 같은 방식입니다.

graphs/nodes/rerank.py · 모델 RERANKER_MODEL_NAME

9

관련성 판단과 재검색

앱

리랭커 점수가 기준(RELEVANCE_THRESHOLD, 0.25) 이상인 청크가 하나라도 있으면 다음 단계로 갑니다. 하나도 없으면 한 번(FALLBACK_MAX_RETRIES=1) 범위를 넓혀 다시 검색합니다.

  • 후보 수와 리랭크 수를 2배로(40→80, 10→20) 늘립니다. 컨텍스트 수 6은 그대로입니다.
  • 기준 점수를 FALLBACK_RELEVANCE_THRESHOLD(0.1)로 낮춥니다.
  • 재작성 질의를 버리고 원문 질의 하나로만 검색합니다. 재작성이 범위를 좁혔을 경우에 대비한 것입니다.
  • 재시도는 질의 재작성(3번 노드)을 건너뛰고 retrieve로 바로 갑니다.
  • 그래도 없으면 "관련 정보를 찾을 수 없습니다" 안내로 끝납니다.

graphs/edges.py check_relevance() · graphs/nodes/fallback_handler.py

10

컨텍스트 조립

앱

LLM에 넣을 글을 만듭니다.

  1. 기준 점수 미만 청크를 뺍니다.
  2. 본문이 같은 청크를 한 번 더 걸러 냅니다.
  3. 한 문서에서 최대 2개(CONTEXT_MAX_CHUNKS_PER_DOCUMENT)까지만 받습니다. 한 문서가 컨텍스트를 독차지하지 않게 하기 위해서입니다.
  4. 최대 6개(CONTEXT_TOP_K)까지 [번호] [문서명] 위치 + 본문 형식으로 붙입니다. 엑셀 청크는 위치에 시트와 셀 범위를 쓰고, 본문은 표시용 마크다운을 씁니다.
  5. 글자 수(MAX_CONTEXT_CHARS, 32,000)나 추정 토큰 수(모델 최대 길이 − 출력 토큰 − 여유 512)를 넘기는 청크는 건너뜁니다.

여기서 매긴 번호가 답변의 출처 번호 [1], [2]가 됩니다.

자주 받는 질문

Qdrant가 제공하는 검색기를 쓰는 건가요?

네. Dense 검색, BM25 검색, 두 결과의 RRF 병합까지 Qdrant Query API(query_points + Prefetch + RrfQuery)가 서버에서 처리합니다. 앱은 검색 전 준비와 검색 후 리랭크·정리만 합니다.

Kiwi는 어디에 쓰이나요?

BM25에 넣을 토큰을 만드는 데만 씁니다. 적재할 때 청크 본문에, 검색할 때 질의에 같은 정책을 적용해야 단어가 맞습니다. Qdrant의 BM25 모델은 한국어 형태소를 모르기 때문에, Kiwi로 미리 자른 토큰을 공백으로 이어 보내고 Qdrant 쪽 영어 어간 처리는 끕니다(disable_stemmer).

BM25 토큰 정책을 바꾸면 무엇을 해야 하나요?

KIWI_BM25_ENCODER_VERSION을 바꾸면 이미 적재된 포인트의 BM25 벡터는 예전 정책으로 만든 것이라 질의와 맞지 않습니다. scripts/rebuild_kiwi_bm25.py로 기존 포인트의 BM25 벡터를 다시 계산해야 합니다.

리랭커가 꺼지거나 죽으면 어떻게 되나요?

답변은 계속 나옵니다. RRF 순서대로 상위 3개만 컨텍스트로 넘기고, 기준 점수 비교는 건너뜁니다. 품질은 떨어지므로 로그의 mode=degraded로 확인할 수 있습니다.

RETRIEVAL_ENGINE=legacy는 무엇인가요?
  • 2026-07 이전 방식이며 기본값이 아닙니다.
  • Dense, BM25, BM42 채널을 각각 따로 검색하고 RRF 병합은 파이썬에서 합니다(_merge_rrf).
  • BM25는 Qdrant에서 후보를 스크롤로 가져와 rank_bm25로 점수를 다시 계산합니다. 후보 밖 문서는 찾지 못하는 한계가 있어 Qdrant 희소 인덱스 방식으로 바꿨습니다.
  • BM42 채널은 이 경로에서만 쓰입니다(RETRIEVAL_PROFILE).
권한 없는 문서가 검색 결과에 섞일 수 있나요?

권한 필터는 Qdrant의 각 prefetch에 직접 붙기 때문에, 권한 밖 포인트는 후보에 들어오지 않습니다. 병합 후에 걸러 내는 방식이 아닙니다. 비활성 버전 포인트도 같은 방식으로 빠집니다.

검색이 이상할 때 어떤 로그를 보면 되나요?
  • [RAG][query_preprocess]: 정규화 질의, 키워드, BM25 질의, Dense 질의 목록
  • [RAG][results][pre_rerank]: Qdrant가 돌려준 후보
  • [RAG][results][post_rerank]: 리랭크 결과와 모드(reranked / degraded / disabled)
  • [RAG][edge=check_relevance]: 기준 통과 수, 재검색 여부
  • [RAG][results][final_context]: LLM에 실제로 넣은 컨텍스트
  • RAG_DIAGNOSTIC_LOG=true면 단계별 개수와 점수 범위([RAG][diag])가 더 나옵니다.
