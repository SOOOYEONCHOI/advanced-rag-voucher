## 2. 수정 사항

### 2.1 ① 질의 법령 표기 변환 경계 수정

| | 내용 |
|---|---|
| 파일 | `adrag_backend/app/graphs/preprocessing/query_preprocessor.py`, `app/core/config.py`, `app/core/container.py` |
| 원인 | 숫자+조/항/호 뒤에 무엇이 오든 "제N조"로 바꿈. 숫자 중간에서도 매칭 |
| 수정 | 뒤가 문장 끝·기호·조사일 때만 변환, 앞이 `제`·숫자이면 제외 |
| 설정 | `QUERY_LAW_NOTATION_NORMALIZE`(신규, 코드 기본 `true` = 기존 동작). `false`면 법령 표기 변환과 법령 조문 추출(→ 법령 질의 분류)을 하지 않음 |

패턴 비교

```text
전: (?<!제)(\d+)\s*(조|항|호)(\s*의\s*\d+)?(?!원)
후: (?<![제0-9])(\d+)\s*(조|항|호)(\s*의\s*\d+)?(?=$|[^0-9A-Za-z가-힣]|(?:은|는|이|가|을|를|의|에|도|만|와|과|로|으로|에서|부터|까지))
```

### 2.2 ② BM25 토큰 정책 v2 (모델 코드·규격·호기 보존)

| | 내용 |
|---|---|
| 파일 | `adrag_backend/app/utils/kiwi_tokenizer.py`, `app/clients/kiwi_bm25_encoder.py`, `app/core/config.py` |
| 원인 1 | Kiwi가 "XG-500A"를 `XG`/`-`/`500`/`A`로 나누고, 검색 품사에 숫자(SN)가 없고 2글자 미만은 버림 |
| 원인 2 | Qdrant BM25(FastEmbed)가 받은 텍스트를 다시 소문자화하고 비단어 문자(`-`, `·`, `.`)에서 자름 |
| 원인 3 | "2조립" → `2조`+`립`(숫자+단위 정규식이 일반 단어를 자름) |
| 수정 | v2에서 Kiwi에 코드·N호기·규격 패턴 등록, 조/호 단위는 뒤가 조사·끝·기호일 때만. 코드·규격 토큰은 표준형으로 변환해 적재·질의 양쪽에 같게 적용 |
| 설정 | `KIWI_BM25_ENCODER_VERSION` 값이 정책을 고름: `kiwi-bm25-v1`(코드 기본, 기존) / `kiwi-bm25-v2` |

표준형 규칙: 소문자, 하이픈·가운뎃점·공백 제거, 소수점은 `_`, 하이픈 코드는 조각도 함께.

| 원문 | v1 토큰(문서) | v2 토큰(문서·질의 동일) |
|---|---|---|
| XG-500A | `XG`, `500` (질의는 `XG`만) | `xg500a`, `xg`, `500a` |
| ABC-12-3B | `ABC`, `12-3` (질의는 `ABC`만) | `abc123b`, `abc`, `12`, `3b` |
| M6 | (없음) | `m6` |
| 12N·m | `12` (질의는 없음) | `12nm` |
| 1.5mm | `1.5`, `mm` | `1_5mm` |
| 220V 전원 | `220`, `전원` | `220v`, `전원` |
| 3호기 | `3호` | `3호기` |
| 2조립 | `2조` | `조립` |
| 일반 명사·법령 조문 | (변화 없음) | (변화 없음) |

구현 중 확인한 사실
- Kiwi `add_re_word`는 같은 위치에서 겹치면 **나중에 등록한 패턴**이 이긴다 → v2 패턴은 맨 뒤에 코드 < N호기 < 규격 순서로 등록.
- 규격을 NNP로 등록하면 뒤 낱말 분석이 바뀐다("220V 전원" → `전`/`원`) → SL로 등록.
- 정책별 Kiwi 인스턴스: 운영은 설정 정책 하나만 만들고, 평가·테스트에서 다른 정책을 지정해도 기본 인스턴스를 바꾸지 않음.

### 3.5 해석과 한계

- 코드·규격 질의는 BM25 단계에서 크게 좋아졌고 최종 hybrid 상위 10건 안에 드는 비율도 올랐다. 일반 질의는 변화가 없다.
- **hybrid 1위 정확도는 거의 그대로**(0.625 → 0.637). BM25가 정답을 1위로 찾아도 Dense 순위와 RRF로 합치면 1위가 바뀌는 경우가 많다 → 4장 가중치 개선 대상.
- 운영 경로는 위 측정보다 BM25에 더 불리하다: SOP 질의 대부분이 "개념 설명" 유형(Dense 1.5 / BM25 0.7)으로 분류되고, 재작성 질의 2~3개가 Dense 쪽에 더해진다.
- 질의는 같은 정규식으로 만든 합성 질의라 v2에 유리하다. 실제 작업자 표현으로 만든 SOP 골든셋 확인이 필요하다.

## 4. 가중치 개선 계획 (계획만, 미구현)

### 4.1 현재 구조와 문제

| 위치 | 현재 | 문제 |
|---|---|---|
| `retrieval_engine.classify_query_type` | 법령 조문 → 법령 / 메뉴 단어 → 매뉴얼 / 사고 단어 → 사고 사례 / 나머지 → 개념 설명 | 법령·안전 도메인 기준. SOP 질의 대부분이 "개념 설명"으로 떨어짐. 사고 단어에 "작업자·현장·발생·원인"이 있어 SOP 질의가 "사고 사례"로 잘못 분류될 수 있음 |
| `retrieval_engine.RRF_WEIGHTS` (코드 상수) | 개념 설명 Dense 1.5 / BM25 0.7, 사고 사례 1.5 / 0.8, 법령 0.7 / 1.5, 매뉴얼 0.8 / 1.5 | 코드·규격 질의도 Dense 우위 가중치를 받음. 설정으로 바꿀 수 없음 |
| `vector_repository.search_hybrid` | Dense 가중치를 질의 수(원문 + 재작성)로 똑같이 나눔 | 재작성 질의가 모델명·품번을 바꾸거나 빼도 원문과 같은 비중 |
| `apply_soft_boost` | `inferred_type` 조건 | 값을 채우는 곳이 없어 동작하지 않는 코드(정리 대상) |
| 설정 `MENU_HINT_TERMS`, `NARRATIVE_HINT_TERMS` | 법령·안전 매뉴얼 단어 | SOP 단어 아님 |

### 4.2 개선 방향

1. **SOP 질의 유형 추가** — 규칙 기반, LLM 호출 없음
   - `CODE_SPEC`: 질의에 v2 코드·규격·N호기 토큰이 있음 → BM25 우위
   - `PROCEDURE`: 순서·방법·절차·단계·어떻게 등 → 균형 또는 Dense 약간 우위
   - `GENERAL`: 나머지
   - 법령 유형은 `QUERY_LAW_NOTATION_NORMALIZE=true`일 때만 유지
2. **가중치를 설정값으로** — 예: `QUERY_TYPE_PROFILE=legacy|sop`(기본 `legacy` = 지금 값 그대로, 규칙 6), `sop` 가중치 표는 설정(JSON)으로 덮어쓸 수 있게.
3. **원문 질의 비중 보장** — Dense 가중치 중 원문 비중을 설정값(예: `DENSE_ORIGINAL_QUERY_SHARE`, 기본 = 지금처럼 균등)으로 두어 재작성 질의가 원문을 희석하지 않게.
4. **soft boost 정리** — 쓰이지 않는 `inferred_type` 분기 제거 또는 실제 유형 연결(결정 필요).

### 4.3 실험 계획 (dev, 읽기 전용)

| 단계 | 내용 |
|---|---|
| 1. 기준 측정 | 지금 운영 경로 그대로(유형 분류 + 재작성 + 리랭커)로 Hit@1·Hit@10·MRR@10 측정. 이번 3.1절 질의 세트 + 골든셋 |
| 2. 격자 탐색 | Dense {0.7, 1.0, 1.5} × BM25 {0.7, 1.0, 1.5, 2.0} × RRF k {20, 60} × 원문 비중 {균등, 0.5}, 유형별로. Qdrant 질의만이라 수 분 |
| 3. 선택 기준 | 일반 질의 Hit@10이 기준보다 떨어지지 않는 조합 중 코드·규격 Hit@1 최대. 최종은 리랭커 포함 결과로 판단 |
| 4. 확인 | 고른 값으로 리랭커 포함 end-to-end, 임계값 통과율·fallback 비율 변화 확인 |

해석
1. 리랭커가 순위를 크게 끌어올리지만, 후보 단계에서 빠진 코드 질의는 살리지 못한다(현재 운영 코드만 Hit@10 0.883).
2. **가장 큰 요인은 재작성 질의가 원문을 희석하는 것.** 가중치는 그대로 두고 재작성만 빼도 코드+명사 0.883→0.967, 코드만 0.833→0.950.
3. 재작성을 유지하면서 **원문 비중 0.5 + BM25 1.5 + k=20**이면 재작성 제외 조합과 같은 결과 → 재작성의 표현 확장(동의어) 이점을 지키면서 희석만 막을 수 있다. 추천안.
4. 일반 질의는 모든 조합에서 같고, 절차 질의는 소폭 개선 → 회귀 없음(단 두 집합은 정답이 많아 민감도가 낮다).
5. 별도 발견: **절차형 질의는 리랭커 최고점이 임계값 0.25를 넘는 비율이 40~47%뿐**이다. 나머지는 fallback으로 간다. 고정 문구("작업 순서 알려줘")가 붙은 합성 질의의 특성일 수 있으나, 실제 "어떻게 해?" 질문에서도 같다면 답변 거부가 많아진다 → 실제 질의로 확인 필요.

한계: 합성 질의(코드 질의는 v2와 같은 정규식으로 생성), 컬렉션 1개(243청크), 법령 컬렉션은 미측정.
