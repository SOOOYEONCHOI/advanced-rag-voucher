# 일반 문서 검색 성능 저하 원인 분석 · 3유형(엑셀·법령·일반) 공통 개선 설계 (2026-11-11)

관련 ID: R4-1, R4-2, MOD-08(검색 엔진), F-4-01, F-4-02, API-05, (적재) F-2-xx 일반 문서 등록
상태: **설계안(구현 전, 승인 대기)** · 브랜치 `refactor-1`
분석 대상: dev에 등록된 일반 PDF 1건(FAQ형 해설 자료, 54쪽, 문서 유형 자동 판정 = `general`, 청크 24개)
※ 규칙 3에 따라 원문 문장은 옮기지 않고 쪽 번호·건수·현상만 적는다.

## 1. 결론 요약

엑셀·법령이 잘 되는 이유는 **"구조 단위로 자르고, 자른 조각마다 맥락(문서·위치)을 본문에 붙이기 때문"**이다. 일반 문서는 이 두 가지가 모두 없고, 그 앞 단계인 **파싱에서 텍스트 자체가 빠지고 있다.** 검색 엔진(가중치·리랭커)보다 **적재 단계 문제**가 핵심이다.

| 유형 | 파싱 | 청크 단위 | 청크 본문의 맥락 | 결과 |
|---|---|---|---|---|
| 엑셀 SOP | `excel_ingest` IR(셀 단위, 손실 없음) | 표 블록·레코드 | `시트:` `표:` `헤더:` + `항목: 값` | 양호 |
| 법령 | Docling(깨끗한 텍스트) | 조문(제N조) | `제N장 > 제N절 > 제N조` 경로를 본문 앞에 붙임 | 양호 |
| **일반** | Docling(**텍스트 일부 누락**) | **800자 고정 분할** | **없음**(header_path를 지우고, 붙이는 옵션은 코드에서 안 씀) | **불량** |

## 2. 원인 (근거 포함)

### C1. 파싱 단계 텍스트 누락 — 가장 큰 원인

- 이 PDF는 **페이지 전체가 스캔 이미지(0,0 ~ 페이지 크기)이고 그 위에 보이지 않는 OCR 텍스트층**이 있는 구조다(PyMuPDF로 확인: 페이지마다 전체 크기 이미지 1개 + Q 아이콘 이미지 1개).
- `docling-parser`는 텍스트층이 있으면 `do_ocr=False` 경로로 간다(`docling-parser/app/services/parser.py:44-46`, `_has_text_layer`). 이때 Docling 레이아웃 모델이 일부 텍스트 영역을 **그림(picture) 영역**으로 판정하면 `export_to_markdown()`에서 그 안의 글자를 내보내지 않는다.
- 실측
  | 항목 | PDF 텍스트층 | 적재된 청크 |
  |---|---|---|
  | 글자 수 | 약 18,650자 | 약 14,600자(마지막 청크 끝 오프셋) |
  | 질문(Q) 문장 | 37개 | **약 16~17개만 남음** |
  | 답변 표지 "A" | 36개 | 37개(남음) |
- **FAQ에서 검색에 가장 중요한 질문 문장이 절반 이상 사라졌다.** 사용자의 질문은 FAQ의 질문과 표현이 가장 비슷한데, 그 문장이 색인에 없다. 답변만 남은 청크는 "A"로 시작하는 맥락 없는 문단이 된다.

### C2. OCR 오타가 원문 텍스트층에 이미 있음

- 텍스트층 자체가 OCR 결과라 핵심 용어가 틀린 글자로 들어 있다(예: "중대" → "증대", "처벌" → "치별", "위험" → "위협", "제22조" → "계 22 조").
- BM25(Kiwi)는 글자가 다르면 일치하지 않는다. 사용자가 "중대산업재해"로 물으면 "증대산업재해"가 들어 있는 질문 문장과 맞지 않는다. Dense는 어느 정도 버티지만 C1·C3와 겹치면 순위가 크게 밀린다.

### C3. 문서 구조(Q/A·섹션)를 무시한 800자 고정 분할

- `split_general_markdown`은 문서 전체를 이어 붙인 뒤 `RecursiveCharacterTextSplitter(800, 160)`로 자른다(`app/parsers/chunkers/general.py:197`).
- 실측: 청크 0 하나에 **표지 + 목차 표 + 서로 다른 문답 3개의 답변**이 섞여 있고, 다른 청크에서는 한 답변이 두 청크로 갈라지거나 **질문은 앞 청크, 답변은 뒤 청크**로 나뉜다.
- 한 청크에 주제가 여러 개 섞이면 임베딩이 어느 주제에도 가깝지 않게 되고, 리랭커도 점수를 낮게 준다.

### C4. 청크 본문에 맥락이 없음(법령·엑셀과의 결정적 차이)

- 법령: `_make_content()`가 `제N장 > 제N조` 경로를 본문 앞에 붙임(`app/parsers/chunkers/law.py:384-388`).
- 엑셀: `_embedding_text()`가 시트·표 제목·헤더를 붙임(`app/parsers/chunkers/spreadsheet.py:405-`).
- 일반: `_chunk_general()`이 `header_path`를 **None으로 지우고**(`app/parsers/processor.py:137-140`), `include_header_path` 인자는 받기만 하고 **함수 안에서 쓰지 않는다**(`general.py:161`). 임베딩·BM25는 `chunk.page_content` 원문만 쓴다(`app/services/ingest_service.py:317-374`).
- 문서 제목도 첫 줄을 그대로 써서 **발행 연월("2022.1")이 제목**으로 저장됐다(`app/parsers/metadata_extractor.py:82-102`). 리랭커 입력의 `[문서명]`은 파일명이라 괜찮지만, 제목 메타를 쓰는 화면·필터에는 잘못된 값이 나간다.

### C5. section_title 오인식이 리랭커 입력을 오염

- 번호 제목 정규식(`general.py:27-35`, `1.`·`가.`·`(1)` + 75자 이하)이 **본문에 인용된 법조문 줄**을 제목으로 잡는다.
- 실측: 24개 청크 중 **10개 이상이 "가. 사업을 대표하고…" 또는 "1. 「산업안전보건법」 계 22 조…" 같은 인용문 줄을 section_title로** 가진다(뒤 청크로 계속 이어짐).
- 이 값이 리랭커 입력 `[섹션]`으로 들어가(`app/graphs/nodes/rerank.py:47-73`) 질문과 무관한 위치 정보가 붙는다.

### C6. 반복 머리말·꼬리말 잡음

- 페이지마다 문서 약칭·장 이름·쪽 번호·장식 기호가 반복된다. 청크마다 같은 잡음이 들어가 BM25 IDF와 임베딩을 흐린다.

### C7. 평가셋에 일반 문서가 없음

- 11-11 검색 개선의 측정은 SOP 합성 질의 240건 + 법령 골든셋(`korean_search_golden.json`)뿐이다. 일반 문서 성능이 나빠도 지표에 드러나지 않았고, 이번 개선도 검증할 수단이 없다.

## 3. 설계 원칙

1. **세 유형 모두 같은 원칙**: "구조 단위 청크 + 맥락 머리글 + 파싱 손실 0에 가깝게".
2. 엑셀(`excel_ingest` 규칙)·법령 청커·docling-parser 서버 코드는 **건드리지 않는다**(규칙 5). 공통부(색인용 텍스트 구성, 평가)만 손대고, 엑셀·법령은 **회귀 없음을 지표로 확인**한다.
3. 새 동작은 모두 설정값으로 켜고 끈다. **코드 기본값 = 현재 동작**(규칙 6). dev에서 켜서 측정 후 결정.
4. 화면에 보이는 청크 본문(출처 표시)과 **색인용 텍스트(임베딩·BM25 입력)를 분리**할 수 있게 한다.

## 4. 개선 설계

### S1. PDF 텍스트 복구 (C1 대응) — 우선순위 1

Docling 결과와 PDF 텍스트층을 **페이지별로 비교**해서 많이 빠진 페이지는 텍스트층으로 보충한다. backend 쪽에서만 처리한다(docling-parser 수정 없음).

```
Docling 페이지별 markdown ─┐
                          ├─ 페이지별 글자 수 비교(공백 제외)
PyMuPDF 텍스트층(page) ────┘    coverage = docling / textlayer
   coverage ≥ 0.85  → Docling 결과 사용(표 구조 보존)
   coverage <  0.85 → 해당 페이지를 텍스트층(블록 순서 정렬)으로 대체, metadata.text_source = "text_layer"
```

| 항목 | 내용 |
|---|---|
| 파일 | `app/parsers/loaders/docling_loader.py`(결과 후처리 훅), 신규 `app/parsers/loaders/pdf_text_layer.py`(PyMuPDF 블록 추출, 기존 `pdf_loader.py` 재사용 검토), `app/parsers/processor.py` |
| 설정(신규) | `PDF_TEXT_RECOVERY_MODE` = `off`(기본, 현재 동작) / `page_fallback` / `always_text_layer` · `PDF_TEXT_RECOVERY_MIN_COVERAGE`=0.85 |
| 로그·리포트 | 페이지별 coverage, 대체된 페이지 수를 등록 결과(job 로그)에 남긴다. 운영자가 "파싱 손실 문서"를 알아볼 수 있게 함 |
| 대안(승인 필요) | docling-parser에서 그림 영역 안 텍스트도 내보내거나, 전체 페이지 이미지 PDF는 OCR 경로로 강제. **서버 코드 수정이라 규칙 5 대상** → 결정 항목 Q-1 |

### S2. 텍스트 정제 (C2·C6 대응)

| 기능 | 내용 | 설정(신규, 기본 off) |
|---|---|---|
| 반복 머리말·꼬리말 제거 | 페이지 첫·끝 3줄 중 **전체 페이지의 40% 이상에서 반복**되는 줄(숫자 제외 비교)을 제거 | `GENERAL_STRIP_RUNNING_HEADERS` |
| OCR 오타 보정 사전 | **색인용 텍스트에만** 적용하는 치환 사전(예: 증대재해→중대재해, 치별→처벌). 화면 출처 본문은 원문 유지. 사전 파일은 설정 경로로 관리 | `INDEX_TEXT_CORRECTION_DICT`(경로) |
| 법조문 표기 정리 | `계 22 조`처럼 OCR로 깨진 조문 표기를 색인용으로 `제22조` 정규화 | 위 사전과 같이 |

※ 오타 사전은 문서마다 달라 일반화가 어렵다 → 범위·관리 주체는 결정 항목 Q-3.

### S3. 일반 문서 구조 인식 청킹 (C3·C5 대응) — 우선순위 2

`general` 유형 안에서 **구조 프로파일**을 판정하고 프로파일별로 자른다. 문서 유형 목록(auto/law/manual/general/spreadsheet)과 화면은 그대로 둔다.

| 프로파일 | 판정 신호 | 청크 단위 |
|---|---|---|
| `faq` | 질문형 문장(…나요?/…까요?/Q) 다음에 답변 표지(A)·답변 문단이 반복, 샘플 페이지에서 N쌍 이상 | **문답 1쌍 = 1청크**. 답변이 길면 나누되 **나뉜 조각마다 질문을 머리글로 반복** |
| `section` | Docling `#` 제목 또는 검증된 번호 제목이 일정 간격으로 등장 | 제목 단위, 길면 나눔(머리글에 제목 경로) |
| `plain` | 위에 해당 없음 | 현재 방식(800/160) 유지 |

- section_title 정규식 강화: ① 문장 종결(…다. …함.)로 끝나는 줄 제외, ② 「」·조문 인용(제N조, 계N조)으로 시작하거나 포함하는 줄 제외, ③ 앞뒤가 빈 줄인 짧은 줄만 인정, ④ Docling `#` 제목 우선. 목차 페이지(쪽 번호 열 표)는 청크에서 분리해 `content_type=toc`로 표시하고 검색 대상에서 낮춘다.
- 파일: `app/parsers/chunkers/general.py`(프로파일 분기), 신규 `app/parsers/detectors/general_structure.py`, `app/parsers/processor.py`
- 설정(신규): `GENERAL_STRUCTURE_CHUNKING` = `off`(기본) / `auto` · `GENERAL_FAQ_MIN_PAIRS`=5 · `GENERAL_MAX_CHUNK_CHARS`=1200
- 메타데이터: `structure_profile`, `faq_question`(FAQ일 때 질문 원문), `section_path`

### S4. 3유형 공통 "맥락 머리글" (C4 대응) — 우선순위 2

엑셀·법령이 각자 하던 것을 공통 규칙으로 정리하고, 일반에도 적용한다. **색인용 텍스트**(임베딩·BM25·리랭커 입력)에 붙인다.

| 유형 | 머리글 (색인용) | 현재 |
|---|---|---|
| 엑셀 | `시트:` `표:` `헤더:` (현행 그대로) | 있음 — 변경 없음 |
| 법령 | `제N장 > 제N조` 경로 (현행 그대로) | 있음 — 변경 없음 |
| 일반-faq | `[문서] 제목` + `[질문] …` | 없음 → 추가 |
| 일반-section | `[문서] 제목` + `[위치] 섹션 경로` | 없음 → 추가 |
| 일반-plain | `[문서] 제목` | 없음 → 추가 |

- 문서 제목 추출 보완: 첫 줄이 숫자·날짜뿐이거나 너무 짧으면 **원본 파일명(번호 접두어 제거)** 을 제목으로 쓴다(`metadata_extractor.extract_doc_title`).
- 리랭커: `_build_rerank_text`에 `[질문]`(faq_question)을 추가하고, 오인식이 줄어든 section_path를 쓴다.
- 구현 위치: `ingest_service._embed`/BM25 인코딩이 `page_content` 대신 `index_text`(= 머리글 + 본문, 없으면 page_content)를 쓰게 한다. 화면 출처 본문은 `page_content` 유지.
- 설정(신규): `GENERAL_CONTEXT_HEADER` = `off`(기본) / `on`

### S5. (선택) 예상 질문 생성 — 2단계 후보

- 일반 청크마다 자체 서빙 LLM으로 "이 내용으로 답할 수 있는 질문 2~3개"를 만들어 색인용 텍스트 뒤에 붙인다(기존 `semantic_enricher`의 요약·키워드 생성 흐름에 추가). FAQ가 아닌 해설서·안내서형 문서에 효과가 크다.
- 등록 시간·GPU 비용이 늘어 결정 항목 Q-4로 둔다. 외부 API는 쓰지 않는다(규칙 7).

### S6. 3유형 평가셋·회귀 기준 (C7 대응) — 우선순위 1(구현 전에 먼저)

| 셋 | 구성 | 저장 위치 |
|---|---|---|
| 엑셀 SOP | 기존 합성 240건 | 저장소 밖(`_eval_data`) |
| 법령 | 기존 `korean_search_golden.json` | 기존 |
| **일반(신규)** | FAQ 질문 37건(원문 질문 → 정답 쪽) + 같은 뜻 바꿔 말하기 37건 + 해설서·안내서형 문서 질문 30건 내외 | 문서 내용 포함 → **저장소 밖**(`_eval_data`) |

- 지표: 유형별 Hit@5/@10, MRR, 리랭크 후 Hit@5. 측정 도구는 11-11 검색 개선에서 쓴 dev 실측 스크립트(`offline_evaluation` hybrid_retrieval / hybrid_rerank 모드) 재사용.
- **통과 기준(안)**: 일반 Hit@10 개선 + 엑셀·법령 Hit@10 하락 0.01 이내.

| 3 | S4 맥락 머리글 + 제목 보완 + 리랭커 `[질문]` | 색인 텍스트 분리 | 일반만(엑셀·법령 색인 텍스트는 동일하게 유지) |
| 4 | S2 정제(머리말 제거·오타 사전) | — | 일반만 |
| 5 | 3유형 재측정, 단계별 기여도 표 작성 → 설정 기본값 결정 | 보고서 | — |
| (6) | S5 예상 질문 생성(승인 시) | — | 일반만 |

- 단계마다 설정을 하나씩 켜서 측정 → 어떤 수정이 효과가 있었는지 분리해서 보인다.
- 재적재 후 Kiwi v2 BM25를 쓰는 dev는 `rebuild_kiwi_bm25.py` 재실행 필요(기존 메모: v2 전환 시 필수).
- 스키마 변경: 없음 예상(신규 메타는 Qdrant payload·`tb_chunks` 기존 JSON 메타 필드에 저장). `index_text`를 DB에 따로 보관해야 하면 Alembic revision 추가 → 결정 항목 Q-5.

## 7. 되돌리는 방법

- 모든 기능이 설정값으로 꺼짐(기본 off). 끄고 일반 문서만 재적재하면 현재 상태로 돌아간다.
- 엑셀·법령은 색인 텍스트가 바뀌지 않으므로 재적재 불필요.

## 9. 요구사항 정의서·기능 목록에 반영할 것
