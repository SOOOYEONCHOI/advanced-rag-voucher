## 1. 역할과 이번 산출물의 범위

| 담당 | 수행 범위 |
|---|---|
| 백엔드 개발 | 버전 데이터 보존, 복원 검증·전환, 작업 처리, API, DB 마이그레이션, 권한·검색 일관성, 테스트·운영 절차 |
| 프런트엔드 개발자 | v0.2 목업의 Vue 구현, API 연결, 선택 상태·확인창·폴링·알림·접근성, 화면 진입 경로 |
| 전달 자료 | 사용자 수정 목업 v0.2 + 화면 영역별 API 명세 v1.1 |

이번 작업은 설계 문서 작성이다. 프런트엔드 소스, 사용자 수정 목업, 백엔드 실행 코드는 변경하지 않는다.

## 2. v0.2 화면에 따른 확정 계약

1. 이력 조회 → 이전 버전 한 개 선택 → 하단 ‘선택 버전 복원’ → 확인창 → 최종 ‘이 버전으로 복원’ 순서다.
2. 행 선택과 확인창 표시에는 서버 요청이 없다. 마지막 확인 버튼에서만 POST한다.
3. 현재 버전·불가 버전은 선택 불가다. 가능 여부와 불가 사유는 서버 응답을 기준으로 한다.
4. ‘적용 이력 보기’를 처음 펼칠 때 적용 이력 API를 호출한다.
5. 복원 진행창을 닫아도 작업은 계속된다. 문서 목록과 버전 이력 응답에서 진행 중 작업을 다시 찾을 수 있다.
6. 목업의 v3 → v1, 총 3개, 다음 v4, 2.4초 처리 시간은 예시다. 실제 값은 서버가 결정한다.
7. 목업의 `missing/model` 상태에서 전체 복원을 막는 예시 스크립트는 구현 규칙이 아니다. v1만 불가하고 v2가 가능하면 v2를 선택해 복원할 수 있어야 한다.
8. 현재 적용 배지는 `is_active`, 등록 정보는 해당 버전의 값으로 표시한다. 선택 강조는 프런트엔드 임시 상태이며 서버에 저장하지 않는다.

## 3. 핵심 복원 정책

- Qdrant에 정상 완료된 모든 버전의 벡터와 payload를 보존한다. 현재 적용 버전은 `tb_documents.version_no`가 결정한다.
- v3 → v1 복원은 기존 v1을 다시 활성화하는 작업이다. 새 버전·새 벡터·새 임베딩을 생성하지 않는다.
- 다음 업로드 번호는 `MAX(version_no) + 1`이다(현행 `IngestRecordRepository.next_version_no`가 이미 이 규칙 — 변경 불필요). 실패한 버전의 번호도 재사용하지 않는다.
- 포인트 ID는 `uuid5("{document_id}:{version_no}:{source_key}#{part_no}")`로 버전마다 다르다(현행 `app/ingest/records.py` `assign_chunk_identity` 확인). 버전 간 포인트 충돌이 없으므로 보존을 위한 ID 체계 변경은 필요 없다.
- 현재 문서의 식별자·소유자·모델명(`product_model`)·`doc_key`·대화 주제(`collection_id`)·보안 등급·권한은 유지하고 버전별 내용·원본·청크·사진·출처를 전환한다.
- 과거 payload의 ACL을 과거 권한으로 복원하지 않는다. 검색·리소스 접근은 현재 RDB 권한을 적용한다. Qdrant payload의 `security_level`이 검색 필터로 쓰이므로(`vector_repository.ensure_payload_indexes`), 문서 보안 등급이 바뀌면 **보존된 모든 버전 포인트의 `security_level`도 함께 갱신**한다(벡터·내용 payload는 불변, 보안 메타데이터만 갱신).
- 정상 완료된 이전 버전만 대상이다. 현행 코드는 문서 삭제 시에도 모든 버전을 `retired`로 바꾸므로(`retire_document_versions`) `retired` 상태만으로 판단하지 않고 적용 이력(5.3)과 `activated_at IS NOT NULL`로 판단한다.
- 버전별 임베딩 프로필이 현재 질의 경로와 호환되어야 한다. 다중 모델 검색은 이번 범위에서 구현하지 않는다.
- 관리자 전용 복원을 유지한다. 인증은 기존 `get_current_principal`, 판단은 서버의 `principal["is_admin"]`을 사용한다. 최신본 변경의 권한(관리자 또는 본인 업로드, `can_edit`)을 복원에 쓰지 않는다.

### 3.1. 권한과 화면 진입의 구분

현재 프런트엔드 라우터는 관리자 계정의 `/admin` 진입을 `/admin/users`로 이동시킨다. 백엔드 계약은 관리자만 복원 가능하게 고정하고, 관리자용 문서 관리 진입 경로 연결은 프런트엔드 담당 범위다(연동 인수의 선행 조건).

### 3.2. 범위 결정 기록 (구현 착수 전 필요)

D-18은 “버전 [이 버전 적용]이 없으면 1차에 새로 만들지 않는다(R1-5는 2차)”이다. 이번 요청은 이를 1차에 앞당기는 범위 변경이므로, 구현 착수 전에 `01_결정사항_변경로그.md`에 신규 결정(예: D-22 “R1-5 이전 버전 복원 1차 포함, 관리자 전용, 기본 OFF”)을 추가해야 한다. 이 문서는 그 결정의 초안 근거로 쓴다. → 11절 Q-1.

## 5. 데이터 모델

### 5.1. `tb_documents` 변경

| 컬럼 | 설계 |
|---|---|
| `version_no` | 기존 현재 적용 버전 포인터 유지 |
| `activation_revision` | bigint NOT NULL DEFAULT 1. 적용 순번. 이관 시 1, 이후 신규 업로드 최초 적용은 1, 최신본 변경 전환·복원마다 +1 |
| `pending_job_id` | text NULL, FK → `tb_ingest_jobs(job_id)` ON DELETE SET NULL. 문서별 변경 작업 점유 표식 |

`version_no`와 적용 순번을 함께 비교해 v3 → v1 → v3처럼 번호가 되돌아온 중간 변경도 검출한다.

**점유 표식 생명주기 (B-01)** — 최신본 변경과 복원이 같은 표식을 쓴다. 모든 획득·해제는 `lock_document()`(advisory xact lock) 아래에서 한다.

| 시점 | 최신본 변경(ingest + target_document_id) | 복원(restore) |
|---|---|---|
| 접수 | `_register_version_job`: `pending_job_id IS NULL` 확인(아니면 409 `JOB_IN_PROGRESS`) → 작업 INSERT·building 버전 INSERT·`pending_job_id` 설정을 한 트랜잭션 | 6.1 |
| 성공 | `activate_version` 트랜잭션에서 `pending_job_id = NULL` (자기 job일 때만) | 6.2 마지막 단계 |
| 실패 | `_execute` 실패 경로의 버전 failed 표시와 함께 해제 | 6.3 |
| 재시도 | `_reopen_version`에서 `pending_job_id IS NULL OR = 이 job` 확인 후 재획득 | 재시도 없음(새 요청) |
| 재기동 | 6.4 정합성 복구 | 6.4 |

- 해제는 항상 `UPDATE … SET pending_job_id = NULL WHERE document_id = ? AND pending_job_id = ?`로 자기 소유만 해제한다.
- 기존 `uq_doc_versions_in_progress`(building/ready 1개) 제약은 그대로 두어 이중 안전장치로 쓴다.
- **삭제(B-02)**: 현행 삭제는 잠금 없이 `_pending_versions`만 확인한다. 변경 후 삭제는 `lock_document()` 아래에서 `pending_job_id IS NOT NULL`이면 409(`JOB_IN_PROGRESS`)로 거절하고, 통과하면 같은 트랜잭션에서 삭제 표식을 먼저 확정한 뒤 정리를 진행한다. 복원 접수는 삭제 표식이 있는 문서에 접수되지 않는다(404).

- `vectors_purged_at`은 삭제 이력 의미를 유지한다. 백업 복구 뒤에도 가용성을 이 값만으로 판단하지 않는다.

- **이관(baseline)**: 삭제되지 않은 문서마다 1행 — `operation_type='baseline'`, `to_version_no = tb_documents.version_no`, `activation_revision = 1`, `actor_id/job_id = NULL`, `activated_at = coalesce(active_activated_at, created_at)`. 과거 replace 이력을 추정해 만들지 않는다. 삭제된 문서는 baseline을 만들지 않는다.

## 6. 접수·실행·복구 절차

### 6.1. 복원 접수 트랜잭션

1. 인증, 요청 형식 검사(실패 422 `INVALID_REQUEST`).
2. 문서 가시성 검사(`_load_visible_document` 재사용, 실패 404). 기능 설정(403 `FEATURE_DISABLED`). 관리자 권한(403 `ADMIN_REQUIRED`).
3. `lock_document()` 획득.
4. 멱등 키·fingerprint 확인. 같은 요청 재전송이면 예상 버전이 달라졌더라도 기존 작업을 반환한다(queued/running 202, completed/failed 200).
5. 삭제 여부(404), 대상 버전 존재(404 `VERSION_NOT_FOUND`), 현재 버전·적용 순번(409 `STATE_CHANGED`), 대상이 현재(409 `ALREADY_ACTIVE`), 점유(409 `JOB_IN_PROGRESS`), 사전 검증 상태(422 각 코드)를 검사한다. Qdrant 상세 검증은 이 트랜잭션에서 하지 않는다.
6. queued 작업 INSERT와 `pending_job_id` 설정을 함께 커밋한다.
7. `IngestJobManager.enqueue` 후 202. 저장 후 enqueue 실패는 접수 실패로 위장하지 않고 재기동 복구에서 재개한다.

이미 접수된 키의 결과 조회는 기능 비활성화 뒤에도 허용한다(4단계를 2단계 기능 검사보다 먼저 두지 않는 대신, 기능 OFF일 때도 멱등 키 일치 시 기존 작업을 반환하는 분기를 둔다).

### 6.2. 복원 작업

상태는 `queued → running → completed / failed`. 단계(`current_step`)는 `queued → validate → snapshot → activate → completed`.

- validate: 실행 시점 권한(실행자가 여전히 관리자인지 포함)·삭제·점유 소유·예상 상태, 대상 버전·프로필 재검사.
- snapshot: 원본 파일 존재, `tb_chunks`(대상 버전) 수, `tb_chunk_resources`·`tb_spreadsheet_resources`(대상 버전) 연결과 파일, `tb_flow_graphs`, Qdrant 포인트 ID 집합·수·payload 해시를 명세와 대조. 새 임베딩 생성 단계가 아니다.
- activate: 짧은 RDB 트랜잭션에서 최종 재검사 후 전환.

**최종 트랜잭션 (`IngestRecordRepository.restore_version`)**

1. `lock_document()`, `tb_documents … FOR UPDATE`로 `version_no`·`activation_revision`·`pending_job_id = 이 job`·`deleted_at IS NULL` 재확인. 대상 버전 `FOR UPDATE`로 `status='retired' AND activated_at IS NOT NULL` 확인.
2. 현재 active → `retired`, `retired_at = now()`.
3. 대상 → `active`, `activated_at = now()`, `retired_at = NULL`.
4. `tb_documents` 갱신 (B-06):
   - 바꾸는 값: `version_no`, `original_filename`, `stored_filename`, `source_path`, `file_size`, `file_format`, `parser_type`, `total_pages`, `chunk_count`(이상 버전 행), `doc_type`, `requested_doc_type`, `doc_type_source`, `title`(snapshot), `status='ready'`, `error_message=NULL`, `active_activated_at = now()`, `content_updated_at = now()`, `updated_at = now()`, `activation_revision = activation_revision + 1`, `pending_job_id = NULL`.
   - 유지하는 값: `document_id`, `uploaded_by`, `collection_id`, `security_level`, `product_model`, `doc_key`, `created_at`, `deleted_at`.
   - `updated_at`을 갱신해야 목록의 ‘최근 변경일’이 바뀐다(목업 `#updatedAt`).
5. 적용 이력 INSERT(`restore`, actor=실행자, job_id).
6. `tb_document_events` INSERT(`event_type='restore'`, snapshot에 from/to 버전) (B-17).
7. 작업 `completed`, `current_step='completed'`, result 저장.

문서당 active 1개는 기존 부분 UNIQUE `uq_doc_versions_active`(0003)가 보장한다(B-05). 2→3 순서를 지켜야 제약 위반이 나지 않는다.

### 6.3. 장애·재시도

- 커밋 전 실패: 적용 버전 유지, 작업 failed, 점유 해제(자기 소유만). 대상 retired 버전을 failed로 바꾸지 않는다.
- 커밋 후 알림·응답 처리 실패: 성공을 failed로 바꾸거나 자동 역전환하지 않는다.
- UI의 ‘다시 시도’: 최신 이력 조회 → 사용자 재확인 → 새 멱등 키로 새 POST.
- 응답 유실·타임아웃: 같은 키·같은 본문으로 재전송.
- `POST /jobs/{id}/retry`는 restore 작업에 409 `RESTORE_RETRY_REQUIRES_NEW_REQUEST`. 기존 ingest 재시도는 유지.
- 초기 배포는 현행 단일 프로세스 작업 관리자 구성을 유지한다. 다중 프로세스 실행 시 DB 원자적 claim을 먼저 추가해야 한다.

### 6.4. 작업 관리자 분기와 재기동 복구 (B-14)

- `IngestJobManager._execute`는 현재 `try` 블록 이전에 `request["file_path"] + ".checkpoint"`를 계산한다. restore 작업은 이 줄에서 `KeyError`가 나므로, 작업을 읽은 직후 `operation_type == 'restore'`이면 `document_version_restore.run(job)`으로 넘기고 반환한다.
- `requeue_interrupted`는 running을 queued·`current_step='queued'`로 되돌린다. restore는 매번 validate부터 다시 하므로 그대로 써도 된다. 단 재실행 전에 적용 이력에 같은 `job_id`가 있으면(커밋 완료) 작업만 completed로 맞추고 끝낸다.
- **점유 정합성 복구(기동 시 1회)**: `tb_documents.pending_job_id`가 가리키는 작업이 `completed/failed`이거나 없으면 해제한다. 최신본 변경 작업은 해당 버전이 `building/ready`로 남아 있으면 기존 실패 처리 규칙을 따른다.

### 6.5. 최신본 변경·최초 업로드 경로 보완 (B-04)

- `create_active_version`(최초 업로드): `tb_documents.activation_revision = 1`, 적용 이력 `upload` INSERT, 버전 snapshot·프로필·명세 기록.
- `activate_version`(최신본 변경 전환): `activation_revision + 1`, `pending_job_id` 해제, 적용 이력 `replace` INSERT, snapshot·프로필·명세 기록.
- 이 변경은 기존 동작(응답·검색)을 바꾸지 않는다. 설정과 무관하게 항상 기록한다(기록만 하는 것이므로 기본값으로 기존 동작이 깨지지 않음).

### 7.1. 보존 및 정리 (B-08·B-09)

보존 설정(`DOCUMENT_VERSION_VECTOR_RETENTION_ENABLED=true`)일 때 아래 정리 경로가 **정상 버전**을 지우지 않도록 막는다.

- 문서 전체 삭제는 모든 버전이 대상이다. 현행 `delete_by_document_id`는 문서 ID 기준이라 모든 버전 포인트를 지운다(확인). 추가로 버전별 `md_dir`(확인용 md 폴더)도 지운다 — 현행 `_chunk_writer.delete(filename, …)`는 현재 파일명 폴더만 지운다(B-09).

### 7.2. 검색 필터와 요청 snapshot (B-07)

**제외 대상 SQL 변경** — 현행 `_INACTIVE_SQL`은 “비활성 버전 중 `vectors_purged_at IS NULL`인 것이 있는 문서”만 필터 대상으로 삼는다. 보존·백업 복구 후에는 이 값이 실제 포인트 존재를 보장하지 않으므로 다음으로 바꾼다.

```sql
SELECT d.document_id, d.version_no
FROM tb_documents d
WHERE d.deleted_at IS NULL
  AND EXISTS (SELECT 1 FROM tb_document_versions v
              WHERE v.document_id = d.document_id AND v.version_no <> d.version_no)
```

즉 “버전이 2개 이상인 문서는 항상 현재 버전만 남기는 조건을 건다”. 실패 버전·백업 복구 중 포인트·보존 버전 모두 포함된다.

**요청 단위 snapshot** — 현행 `VectorRepository._visible()`이 아래 5곳에서 호출될 때마다 DB를 따로 조회한다. 하이브리드 검색 한 번에 채널별로 다른 시점의 버전을 볼 수 있다.

| `vector_repository.py` 위치(현행 행) | 메서드 |
|---|---|
| 326 | `search_bm25` |
| 421 | `search_sparse` |
| 587 | `search_hybrid` |
| 647 | `search_kiwi_bm25` |
| 705 | `search_similar` |

변경: 질의 처리 시작 시 `VersionSnapshot`(문서별 활성 버전 맵)을 한 번 만들어 contextvar로 전달하고, `_visible()`은 snapshot이 있으면 그것을 쓴다. 청크·사진·출처 조회도 같은 snapshot의 `(document_id, version_no)`를 쓴다. snapshot이 없을 때(관리 도구 등)만 즉시 조회한다.

- 전환 직전에 시작된 요청은 그 요청의 snapshot 버전으로 끝까지 답한다.
- 기존 대화 이력의 출처는 실제 인용했던 버전으로 해석하고, 접근 시 현재 권한을 다시 검사한다.
- 버전 기준 DB 조회 실패 시 검색을 실패 처리한다(현행 규칙 유지).
- 검색·답변 캐시: 현재 코드에 결과 캐시가 없다(B-13). 도입 시 `activation_revision` 합(또는 문서별 순번)을 키에 넣는다.
- 레거시 `version_no` 누락 포인트를 v1로 보는 현행 규칙(`IsEmptyCondition`)은 점검 도구로 v1 문서임을 확인한 경우에만 유지한다.

### 7.3. 장기 보존 시 필터 크기

현행 방식은 대상 문서마다 중첩 `Filter` 1개를 `must_not`에 넣는다. 보존을 켜면 개정 이력이 있는 모든 문서가 대상이 되어 조건 수가 문서 수만큼 늘어난다.

- 1차: 현행 방식을 유지하고, 대표 보존량(문서 수 × 평균 버전 수)에서 필터 크기·검색 지연을 측정한다(VR-T15).
- 측정 결과 기준선 대비 악화가 합의 한도를 넘으면 대안을 적용한다: 포인트 payload에 `doc_version_key = "{document_id}:{version_no}"` keyword 필드와 인덱스를 추가하고, 제외 조건을 `must_not: doc_version_key MatchAny([비활성 키…])` **단일 조건**으로 바꾼다. 기존 포인트는 `set_payload`로 키만 보정한다(벡터·내용 payload 불변). → 11절 Q-2.

### 7.4. 사진·출처 조회 (B-10)

- `GET /api/documents/{document_id}/spreadsheet-resources`(`list_document_resources`)는 현재 문서의 모든 버전 리소스를 돌려준다. 보존 후에는 이전 버전 사진이 섞이므로 기본을 현재 적용 버전으로 제한하고, 선택 인자 `version_no`로 특정 버전을 조회하게 한다(관리 화면용).
- `GET /api/spreadsheet-resources/{resource_id}`는 문서 가시성만 검사한다. 과거 대화의 인용 사진을 열 수 있어야 하므로 버전 제한을 두지 않되, 문서 삭제·권한 상실 시 404를 유지한다.

## 8. 복원 가능 여부와 오류 정책

서버는 응답 최상위와 각 행에 `can_restore`, `restore_block_code`, `restore_block_reason`을 준다. 가능이면 두 불가 필드는 NULL이다.

**산정 규칙 (B-11)**

1. 문서 단위 사유(최상위): `FEATURE_DISABLED` → `ADMIN_REQUIRED` → `JOB_IN_PROGRESS` 순서로 첫 번째.
2. 행 단위:
   - 현재 적용 행은 항상 `ALREADY_ACTIVE`(화면은 사유 문구를 표시하지 않고 ‘현재 적용 중’ 배지만 표시).
   - 그 외 행은 문서 단위 사유가 있으면 그 코드를 그대로 복사한다(목업: 비관리자 “관리자만 복원할 수 있습니다.”, 작업 중 “다른 작업이 진행 중입니다.”).
   - 문서 단위 사유가 없으면 행 고유 사유: `VERSION_NOT_RESTORABLE`(building·ready·failed·적용 이력 없음) → `PROFILE_UNKNOWN`/`MODEL_UNSUPPORTED` → `METADATA_MISSING` → `VERIFICATION_REQUIRED` → `VECTOR_MISSING`/`SOURCE_MISSING`/`RESOURCE_MISSING`.
3. 비관리자에게는 행 고유 사유(벡터 누락 등 내부 상태)를 노출하지 않는다 — 규칙 2의 복사로 자연히 가려진다.

| 코드 | HTTP(POST 시) | 의미 |
|---|---|---|
| `INVALID_REQUEST` | 422 | 본문 형식 오류(필드 누락·타입) |
| `FEATURE_DISABLED` | 403 | 복원 기능 비활성 |
| `ADMIN_REQUIRED` | 403 | 관리자 아님 |
| `VERSION_NOT_FOUND` | 404 | 문서에 없는 버전 번호 |
| `ALREADY_ACTIVE` | 409 | 현재 적용 버전 |
| `JOB_IN_PROGRESS` | 409 | 같은 문서 변경 작업 진행 중 |
| `STATE_CHANGED` | 409 | 예상 버전·적용 순번 불일치 |
| `IDEMPOTENCY_KEY_REUSED` | 409 | 같은 키를 다른 요청에 사용 |
| `RESTORE_RETRY_REQUIRES_NEW_REQUEST` | 409 | restore 작업에 `/jobs/{id}/retry` 호출 |
| `VERSION_NOT_RESTORABLE` | 422 | 정상 적용 이력이 없는 버전 |
| `PROFILE_UNKNOWN` / `MODEL_UNSUPPORTED` | 422 | 프로필 불명 / 현재 질의 경로와 비호환 |
| `METADATA_MISSING` | 422 | 문서 행 재구성 값(snapshot) 없음 |
| `VERIFICATION_REQUIRED` | 422 | 가용성 검증 미완료 |
| `VECTOR_MISSING` / `SOURCE_MISSING` / `RESOURCE_MISSING` | 422 | 벡터 / 원본 / 필요한 리소스 누락 |
| `VECTOR_INTEGRITY_MISMATCH` | 422(접수) / 작업 failed | 포인트 ID·내용 명세 불일치 |
| `DEPENDENCY_UNAVAILABLE` | 503(접수) / 작업 failed | 검증 저장소 일시 장애 |

- 접근 불가·삭제 문서는 코드 없이 기존 문구의 404(정보 비노출 정책 유지).
- 작업 실행 중 실패는 HTTP 오류가 아니라 `GET /jobs/{id}`의 `status=failed`, `error_code`로 전달한다.
- 이력 GET은 Qdrant 전체 읽기를 하지 않는다. 저장된 검증 기록·현재 지원 프로필로 판정하고 실행 시 다시 확인한다. DB 조회 장애는 5xx로 처리하며 빈 이력으로 위장하지 않는다.
- 사용자에게 보이는 `message`/`error`에 파일 경로·DB 오류·내부 주소를 넣지 않는다. 상세는 서버 로그(`event=version_restore …`)에만 남긴다.

## 9. 과거 데이터 및 모델 변경 추천안

### 9.1. 이미 삭제된 벡터

현행 0005 이관이 retired·failed 버전에 `vectors_purged_at`을 채웠고 전환 직후 purge가 동작해 왔으므로, **현재 운영·개발 데이터의 이전 버전 벡터는 대부분 없다**고 가정한다. 기능을 켜도 기존 retired 버전은 `VECTOR_MISSING`일 가능성이 높고, 실제로 복원 가능한 것은 보존 활성화 이후 새로 쌓인 버전부터다. 이를 사용자 안내·인수 기준에 반영한다.

가용성 점검 도구(`scripts/check_version_restore_availability.py`, dry-run 기본):

- 문서·버전별 포인트, 명세, 원본, 리소스, 프로필, snapshot을 분류해 표로 출력한다(원본 경로·내부 주소는 출력하지 않음).
- `--apply`일 때만 `vector_storage_state`·`restore_verified_at`·보정 가능한 snapshot을 기록한다.
- 백업이 있으면 격리 컬렉션 복구 → 대상 버전만 원래 ID·벡터·payload로 추출 → 현재 컬렉션에 복구 → 검증. 운영 컬렉션 전체를 과거 스냅샷으로 덮어쓰지 않는다. 필터 배포(7.2)가 복구에 선행한다.
- 백업이 없으면 동일 벡터 복원 불가로 표시한다. 재임베딩은 별도의 명시적 새 버전 작업이다.

### 9.2. 임베딩 모델 변경

현재 검색 프로필과 동일한 버전만 복원한다. 향후 다중 프로필은 프로필별 컬렉션·질의 임베딩으로 분리 검색 후 공통 재순위화한다. 이번에는 프로필 기록·호환성 검사·차단까지만 구현한다.

## 10. 설정·배포·검증

| 설정 | 기본 | 의미 |
|---|---|---|
| `DOCUMENT_VERSION_VECTOR_RETENTION_ENABLED` | false | 정상 버전 벡터·리소스 보존(정리 경로 중단) |
| `DOCUMENT_VERSION_RESTORE_ENABLED` | false | 복원 신규 접수 허용. 응답 `restore_supported`에 반영 |

- 조합 검증(B-15): 복원 true + 보존 false면 설정 로드 시 오류로 기동을 멈춘다(pydantic validator).
- 순서: 스키마(0006) → 검색 필터(7.2) → 정리 경로 변경(7.1) → 보존 활성화 → 가용성 점검 → 복원 활성화.
- 보존 설정을 꺼도 이미 보존한 정상 버전 데이터를 자동 삭제하지 않는다(7.1 `main.py` 축소 규칙). 기존 코드로 되돌릴 때는 purge가 실행되는 코드가 돌기 전에 확인 절차를 둔다.
- 복원 기능 비활성화는 신규 접수만 막는다.
- downgrade는 기능 중지·작업 정리·백업 후 수행하며 보존 벡터를 삭제하지 않는다. 0006 downgrade는 추가 컬럼·테이블·인덱스만 제거한다(적용 이력 테이블 삭제 전 백업 안내).
- 운영 서버·DB에 직접 접속하지 않고 사용자 실행용 점검·반영 절차를 제공한다.

| 검증 | 완료 기준 |
|---|---|
| 정상 전환 | v3 → v1, 포인터·파일·페이지·청크·사진·출처·`updated_at` 일치, 재임베딩 0회 |
| 보존 무결성 | 복원 전후 포인트 ID·벡터·내용 payload 불변, 다른 문서 영향 없음 |

| 점유 | 최신본 변경·복원·삭제가 같은 문서에서 하나만 진행. 최신본 변경 성공·실패·재시도 후 `pending_job_id` 정리. 재기동 후 고아 점유 해제 |

| 재시작 | queued/running 복원 복구, `file_path` 로직 진입 없음, 중복 적용 0 |

| 검색 | 5개 검색 메서드 모두 같은 snapshot, 보존된 비활성 버전 제외 |
