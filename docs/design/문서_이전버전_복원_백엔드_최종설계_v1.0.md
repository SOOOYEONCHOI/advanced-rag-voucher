## 1. 역할과 이번 산출물의 범위

| 담당 | 수행 범위 |
|---|---|
| 백엔드 개발 | 버전 데이터 보존, 복원 검증·전환, 작업 처리, API, DB 마이그레이션, 권한·검색 일관성, 테스트·운영 절차 |
| 프런트엔드 개발자 | v0.2 목업의 Vue 구현, API 연결, 선택 상태·확인창·폴링·알림·접근성, 화면 진입 경로 |
| 전달 자료 | 사용자 수정 목업 v0.2 + 화면 영역별 API 명세 v1.0 |

이번 작업은 설계 문서 작성이다. 프런트엔드 소스, 사용자 수정 목업, 백엔드 실행 코드는 변경하지 않는다. 기존 요구사항의 프런트엔드 구현은 별도 담당자의 범위로 분리한다.

## 2. v0.2 화면에 따른 확정 계약

1. 이력 조회 → 이전 버전 한 개 선택 → 하단 ‘선택 버전 복원’ → 확인창 → 최종 ‘이 버전으로 복원’ 순서다.
2. 행 선택과 확인창 표시에는 별도 서버 요청이 없다. 마지막 확인 버튼에서만 POST한다.
3. 현재 버전·불가 버전은 선택 불가다. 가능 여부와 불가 사유는 서버 응답을 기준으로 한다.
4. ‘적용 이력 보기’를 처음 펼칠 때 적용 이력 API를 호출한다.
5. 복원 진행창을 닫아도 작업은 계속된다. 문서 목록과 버전 이력 응답에서 진행 중 작업을 다시 찾을 수 있다.
6. 목업의 v3 → v1, 총 3개, 다음 v4, 2.4초 처리 시간은 예시다. 실제 번호·개수·처리 결과는 서버에서 결정한다.
7. 목업의 `missing/model` 상태에서 전체 복원을 막는 예시 스크립트는 구현 규칙이 아니다. v1만 불가하고 v2가 가능하면 v2를 선택해 복원할 수 있어야 한다.
8. 현재 적용 배지는 `is_active`, 등록 정보는 해당 버전의 값으로 표시한다. 선택 강조는 프런트엔드 임시 상태이며 서버에 저장하지 않는다.

## 3. 핵심 복원 정책

- Qdrant에 정상 완료된 모든 버전의 벡터와 payload를 보존한다. 현재 적용 버전은 `tb_documents.version_no`가 결정한다.
- v3 → v1 복원은 기존 v1을 다시 활성화하는 작업이다. 새 버전·새 벡터·새 임베딩을 생성하지 않는다.
- 다음 업로드 번호는 `MAX(version_no) + 1`이다. 실패한 버전의 번호도 재사용하지 않는다.
- 현재 문서의 식별자·소유자·모델명·대화 주제·권한은 유지하고 버전별 내용·원본·청크·사진·출처를 전환한다.
- 과거 payload의 ACL을 과거 권한으로 복원하지 않는다. 검색·리소스 접근은 현재 RDB의 문서 접근 권한을 적용하며, Qdrant의 ACL이 보조 필터로 사용된다면 모든 보존 버전에서 현재 권한과 일치하도록 동기화한다. 임베딩·내용 payload의 보존과 보안 메타데이터 갱신을 구분한다.
- 정상 완료된 이전 버전만 대상이다. `retired`여도 성공 적용 이력이 없으면 복원 불가다.
- 버전별 임베딩 프로필이 현재 질의 경로와 호환되어야 한다. 다중 모델 검색은 이번 범위에서 구현하지 않는다.
- 관리자 전용 복원을 유지한다. 인증은 기존 `get_current_principal`, 판단은 서버의 `principal.is_admin`을 사용한다.

### 3.1. 권한과 화면 진입의 구분

현재 프런트엔드 라우터는 관리자 계정의 `/admin` 진입을 `/admin/users`로 이동시킨다. 목업의 관리자 화면은 제안 상태이며 현재 제품의 진입 경로와 다르다.

백엔드 계약은 관리자만 복원 가능하게 고정한다. 프런트엔드 담당자는 관리자에게 문서 관리 화면 진입 경로를 제공해야 한다. 일반 사용자의 `can_edit`를 복원 권한으로 대체하지 않는다. 이 진입 경로 연결은 연동 인수의 선행 조건이며 백엔드 개발자가 라우터를 수정하지 않는다.

기존 D-18의 ‘미구현 복원은 1차에서 제외’는 이번 사용자 요청에 따른 범위 추가로 기록하고, 실제 구현 보고 시 변경로그·공식 요구사항 반영 항목에 남긴다.

## 5. 데이터 모델

아래는 신규·변경 스키마의 구현 기준이다. 자료형·FK는 현행 사용자/작업 키와 맞추며 운영 데이터 조사는 별도 단계에서 수행한다.

### 5.1. `tb_documents` 변경

| 컬럼 | 설계 |
|---|---|
| `version_no` | 기존 현재 적용 버전 포인터 유지 |
| `activation_revision` | bigint NOT NULL. 적용 순번. 이관 시 1, 이후 업로드 전환·복원마다 +1 |
| `pending_job_id` | nullable 작업 FK. 문서별 변경 작업의 지속적인 점유 표식 |

`version_no`와 적용 순번을 함께 비교하여 v3 → v1 → v3처럼 번호가 되돌아온 중간 변경도 검출한다. `pending_job_id`는 최신본 변경·복원·삭제의 공통 잠금 정책에 반영한다. 예전의 `building/ready` 조회만으로 복원 진행 여부를 판단하지 않는다.

삭제는 동일 문서 잠금 아래 진행 작업을 검사하고 삭제 표식을 먼저 확정한 후 정리한다. 복원 요청은 삭제 표식이 있는 문서에 접수되지 않는다. 장시간 삭제 자체를 새 큐 작업으로 바꾸는 것은 필수 범위가 아니다.

### 5.2. `tb_document_versions` 변경

| 컬럼 | 설계 |
|---|---|
| `embedding_profile_id` | nullable 프로필 FK. 과거 프로필 불명은 NULL 유지 |
| `vector_storage_state` | `unknown / available / missing / archived`, 기본 unknown |
| `vector_manifest_json` | 실제 적재한 dense/sparse·이름별 포인트 ID 집합 또는 그 명세 참조, 기대 수, 검증 해시 |
| `document_snapshot_json` | 버전별 제목·문서 유형·요청 유형·유형 판정 근거 등 현재 문서 재구성에 필요한 값 |
| `restore_verified_at` | 가용성 검증 시각 |

기존 파일명·경로·크기·파서·페이지·청크 수는 유지한다. `created_at`, `uploaded_by`, 원래 적재 `job_id`는 복원으로 덮어쓰지 않는다.

- 대상 활성화 시 `activated_at`을 마지막 적용 시각으로 갱신하고 `retired_at`은 NULL로 만든다. 반복 적용의 모든 시각은 별도 적용 이력에 남긴다.
- 이전 active는 retired로 전환하고 `retired_at`을 기록한다.
- 기존 `vectors_purged_at`은 삭제 이력 의미를 유지한다. 백업 복구 뒤에도 가용성을 이 값만으로 판단하지 않는다.
- 상태·검증 시각은 화면용 사전 판정 자료다. 실제 복원에서는 데이터 존재·명세·프로필을 다시 검증한다.
- 일부 과거 파일·리소스가 없어 완전한 복원이 불가능하면 `can_restore=false`다. 현재 버전 값을 과거 버전 값처럼 복사해 빈 필드를 임의로 채우지 않는다.

### 5.3. 신규 `tb_document_version_activations`

| 컬럼 | 설계 |
|---|---|
| `activation_id` | bigint identity PK |
| `document_id` | 문서 식별자 |
| `from_version_no` | 최초 등록은 NULL |
| `to_version_no` | 적용 버전 |
| `activation_revision` | 적용 순번 |
| `operation_type` | `upload / restore / baseline` |
| `actor_id` | 실행자 식별자. 삭제 정책에 따라 nullable FK |
| `job_id` | 작업 FK, UNIQUE. 복원 중복 적용 방지 |
| `activated_at` | timestamptz |

문서별 적용 순번 UNIQUE를 둔다. 복원 성공 전환과 이력 INSERT는 같은 트랜잭션이다. 실패는 적용 이력에 넣지 않고 작업 테이블에 기록한다.

과거의 정확한 전환 이력이 없다면 추정한 upload 이력을 생성하지 않는다. 이관 당시 현재 상태만 `baseline`으로 기록하고 API에는 ‘기준 상태 등록’으로 구분한다. soft delete 후에는 감사 이력을 유지한다. 추후 hard delete 시 FK·보존 정책을 별도 절차로 적용한다.

### 5.4. `tb_ingest_jobs` 변경

- 기존 `status`, `current_step`, `request_json`, `result_json`, `created_by`, 오류 컬럼을 재사용한다.
- 검색·멱등성용 `operation_type`(기존 행은 ingest), `document_id`, `idempotency_key`, `request_fingerprint`를 추가한다.
- 외부 응답은 기존 ingest 요청에 `target_document_id`가 있으면 `replace`, 복원 작업이면 `restore`로 매핑한다. 원래 업로드 작업의 응답·동작은 유지한다.
- `(created_by, operation_type, idempotency_key)` UNIQUE를 둔다. 기존 ingest 행의 NULL 멱등 키는 허용한다.
- restore 요청 JSON에는 대상 버전, 예상 현재 버전·적용 순번, 실행자 정보만 보관한다. 임시 업로드 파일 경로는 필요 없다.
- 요청 fingerprint는 문서·대상 버전·예상 상태를 정규화해 계산한다. 같은 키·같은 요청은 기존 작업 반환, 같은 키·다른 요청은 409다.
- 문서당 점유 표식의 등록과 작업 INSERT는 같은 트랜잭션이다. 완료·실패 시 자신이 소유한 점유만 해제한다.

### 5.5. 신규 `tb_embedding_profiles`

불변 모델 리비전, 차원, 거리 함수, 정규화, dense/sparse 및 이름별 벡터 구성, 질의 인코딩 설정·프롬프트·토크나이저 리비전, 프로필 해시, 지원 여부를 기록한다. 현재 질의 경로는 컬렉션별 지원 프로필을 식별할 수 있어야 한다.

같은 차원·같은 모델명만으로 호환을 판단하지 않는다. 과거 설정을 증명할 수 없는 경우 `PROFILE_UNKNOWN`으로 복원을 차단한다. 지원 여부는 프로필의 벡터 정의를 변경하지 않는 별도 운영 상태다.

## 6. 접수·실행·복구 절차

### 6.1. 복원 접수 트랜잭션

1. 인증, 문서 가시성, 관리자 권한, 요청 형식을 검사한다.
2. 문서별 기존 advisory lock을 획득한다.
3. 멱등 키와 fingerprint를 먼저 확인한다. 같은 요청의 재전송이면 예상 버전이 이미 달라졌더라도 기존 결과를 반환한다.
4. 문서 삭제 여부, 기능 설정, 현재 버전·적용 순번, 진행 작업, 대상 버전을 검사한다.
5. 사전 검증 상태상 복원 불가면 구체적인 오류 코드를 반환한다. Qdrant의 상세 검증을 이 트랜잭션 안에서 수행하지 않는다.
6. queued 작업과 `pending_job_id`를 함께 저장하고 커밋한다.
7. 기존 작업 관리자에 enqueue하고 202를 반환한다. DB 저장 후 enqueue 실패는 접수 실패로 위장하지 않고 재기동·복구 절차에서 재개한다.

이미 접수된 키의 결과 조회는 기능 비활성화 뒤에도 허용한다. 신규 접수만 차단한다.

### 6.2. 복원 작업

상태는 기존 `queued → running → completed / failed`를 유지한다. 복원 단계는 `queued → validate → snapshot → activate → completed`다.

- validate: 실행 시점의 현재 권한·삭제·점유·예상 상태, 대상 버전 및 프로필 재검사.
- snapshot: 원본, 청크, 원본-청크-사진 연결, 실제 벡터 ID·수·payload·검증 해시 확인. snapshot은 데이터 확인 단계명이며 새 임베딩 생성 단계가 아니다.
- activate: 짧은 RDB 트랜잭션에서 최종 상태 재검사 후 전환.

최종 트랜잭션의 변경:

1. 현재 active를 retired로 변경.
2. 복원 대상을 active로 변경.
3. `tb_documents`의 현재 버전·파일 정보·버전별 내용 정보·적용 시각을 갱신하고 적용 순번 +1.
4. 적용 이력 INSERT.
5. 작업을 completed로 변경하고 result 저장.
6. 해당 작업의 `pending_job_id` 해제.

문서당 active는 정확히 하나여야 한다. 기존 제약을 확인하고 없으면 active에 대한 부분 UNIQUE를 추가한다. 실패 버전용 `building/ready` 제약은 별도로 유지한다.

### 6.3. 장애·재시도

- 커밋 전 실패: 적용 버전 유지, 작업 failed 저장, 점유 해제. 대상 retired 버전을 failed로 바꾸지 않는다.
- 커밋 후 알림·응답·캐시 처리 실패: 이미 적용된 성공을 failed로 바꾸거나 자동 역전환하지 않는다.
- 재시작: restore 작업을 원래 서비스로 분기해 복구한다. job 완료 기록 또는 UNIQUE 적용 이력을 먼저 확인하고 중복 전환을 방지한다.
- UI의 ‘다시 시도’: 최신 이력을 조회하고 사용자가 다시 확인한 뒤 새 멱등 키로 새 restore 요청을 만든다.
- 응답 유실·타임아웃: 원래 요청 본문과 같은 멱등 키로 POST를 재전송해 기존 작업을 찾는다. 이 경우 새 키를 만들지 않는다.
- 기존 `POST /jobs/{id}/retry`는 restore 작업에 대해 409 `RESTORE_RETRY_REQUIRES_NEW_REQUEST`를 반환한다. 기존 ingest 재시도 동작은 유지한다.
- 초기 배포는 현행 단일 작업 관리자 구성을 유지한다. 여러 프로세스·서버에서 실행할 경우 DB 원자적 claim과 점유 복구 정책을 먼저 추가해야 한다.

## 7. 벡터 보존·검색 일관성

### 7.1. 보존 및 정리

- 신규 적재 성공 시 벡터 명세·프로필·문서 snapshot을 기록하고 봉인한다. 봉인된 버전의 벡터와 내용 payload는 복원 시 수정하지 않는다.
- 즉시 purge, 재시도 purge, 시작 시 복구 등 모든 정상 버전 정리 경로에서 삭제를 중단한다.
- 실패 신규 버전은 자신이 만든 데이터만 정리한다. 정상 과거 버전을 함께 지우는 `keep_version_no` 정리를 정상 전환 뒤 실행하지 않는다.
- 문서 전체 삭제는 모든 버전을 대상으로 하며, 삭제 표식 이후 어떤 버전도 검색되면 안 된다.
- 초기에는 정상 버전을 모두 보관한다. 자동 보존 기간·개수 제한은 제외한다.

### 7.2. 검색 필터와 요청 snapshot

- 사용자 권한과 현재 적용 버전 조건을 Qdrant 조회 전 적용한다. 비활성 포인트의 후처리 제거만으로 대체하지 않는다.
- `vectors_purged_at IS NULL`만으로 제외 대상을 고르는 기존 최적화는 변경한다. 백업에서 복구된 벡터와 보존된 retired 버전도 반드시 제외한다.
- 문서별 활성 버전 집합은 요청 단위로 한 번 정하고 모든 검색 채널과 청크·사진·출처 조회에 전달한다.
- 전환 직전에 시작된 요청은 그 요청이 선택한 기존 버전으로 완료할 수 있다. 커밋 뒤 새 요청은 새 적용 버전을 사용한다.
- 기존 대화 이력의 출처는 실제 인용했던 버전으로 해석하고, 현재 파일을 과거 인용처럼 열지 않는다. 접근 시 현재 권한은 다시 검사한다.
- 버전 기준 DB 조회 실패 시 검색을 실패 처리한다. 필터 없는 검색으로 우회하지 않는다.
- 적용 버전·적용 순번을 캐시 키에 반영하여 커밋 직후 오래된 답변이 노출되지 않게 한다. 알림 기반 삭제는 보조 처리다.
- 레거시 버전 번호 누락 포인트는 점검 후 v1임이 확인된 것만 보정한다.
- 문서·버전 수별 필터 크기, 저장량, 검색 지연을 측정한다. 별도 활성 벡터 컬렉션은 이번 범위에서 도입하지 않는다.

## 8. 복원 가능 여부와 오류 정책

서버는 각 행에 `can_restore`, `restore_block_code`, `restore_block_reason`을 제공한다. 가능이면 두 불가 필드는 NULL이다.

우선순위: 문서 접근 확인 → 기능 설정 → 관리자 권한 → 현재 버전 → 진행 작업 → 대상 정상 이력 → 프로필 → 데이터 가용성.

| 코드 | 의미 |
|---|---|
| `FEATURE_DISABLED` | 복원 기능 비활성 |
| `ADMIN_REQUIRED` | 일반 사용자에게 보이는 복원 제한 |
| `ALREADY_ACTIVE` | 현재 적용 버전 |
| `JOB_IN_PROGRESS` | 같은 문서의 변경 작업 진행 중 |
| `VERSION_NOT_RESTORABLE` | 정상 완료 이력이 없는 버전 |
| `PROFILE_UNKNOWN` / `MODEL_UNSUPPORTED` | 모델 프로필 불명 / 현재 질의 경로와 비호환 |
| `VERIFICATION_REQUIRED` | 가용성 검증 미완료 |
| `VECTOR_MISSING` / `SOURCE_MISSING` / `RESOURCE_MISSING` | 벡터 / 원본 / 필요한 리소스 누락 |
| `VECTOR_INTEGRITY_MISMATCH` | 포인트 ID·내용 명세 불일치 |
| `STATE_CHANGED` | 예상 버전·적용 순번 불일치 |
| `IDEMPOTENCY_KEY_REUSED` | 같은 키를 다른 요청에 사용 |
| `DEPENDENCY_UNAVAILABLE` | 검증 저장소 일시 장애 |

이력 GET은 대량 Qdrant 전체 읽기를 하지 않는다. 기존 검증 기록·현재 지원 프로필을 기반으로 판정하고 실행 시 실물을 다시 확인한다. 미검증 버전은 점검 도구로 검증한 후 허용한다. DB 조회 장애는 5xx로 처리하며 빈 이력으로 위장하지 않는다.

## 9. 과거 데이터 및 모델 변경 추천안

### 9.1. 이미 삭제된 벡터

가용성 점검 도구를 dry-run 기본으로 제공한다. 문서·버전별 포인트, 명세, 원본, 리소스, 프로필을 분류한다.

- 보존 데이터가 완전하면 available로 검증한다.
- 백업이 있으면 격리 컬렉션에 복구 → 대상 버전만 원래 ID·벡터·payload로 추출 → 현재 컬렉션에 복구 → 관련 데이터 검증 순서로 처리한다.
- 복구 중인 비활성 포인트도 검색에서 제외되어야 하므로 필터 배포가 복구에 선행한다.
- 현재 운영 컬렉션 전체를 과거 스냅샷으로 덮어쓰지 않는다.
- 백업이 없으면 동일 벡터 복원 불가로 표시한다. 원본 재임베딩은 별도 명시적 새 버전 작업이며 이번 복원 버튼에서 자동 실행하지 않는다.

사내 저장소에 Qdrant·PostgreSQL·원본·리소스 백업과 버전별 검증 명세를 연계 보관한다. 권장 백업 주기는 일 1회와 모델 변경·파괴적 정리 전이며 보관 기간·복구 목표는 용량 점검 후 정한다.

### 9.2. 임베딩 모델 변경

현재 검색 프로필과 동일하게 지원되는 버전만 복원한다. 차원이 같아도 다른 의미 공간이면 차단한다. 구 모델 서비스가 사라지거나 설정을 확인할 수 없으면 모델 미지원 또는 프로필 불명으로 표시한다.

향후 서로 다른 프로필을 동시에 사용해야 하면 프로필별 컬렉션·질의 임베딩으로 분리 검색한 뒤 공통 재순위화를 적용한다. 서로 다른 모델의 원시 유사도 점수를 직접 비교하지 않는다. 이번에는 프로필 기록·호환성 검사·차단까지만 구현한다.

## 10. 배포 및 검증

설정 제안: `DOCUMENT_VERSION_RESTORE_ENABLED=false`, `DOCUMENT_VERSION_VECTOR_RETENTION_ENABLED=false`. 순서는 스키마 → 검색 필터 → 정리 경로 변경 → 보존 활성화 → 가용성 점검 → 복원 활성화다.

- 복원 활성화는 보존 활성화를 전제로 한다.
- 보존 설정은 정상 버전 삭제를 허용하는 스위치가 아니다. 한번 보존한 정상 버전의 데이터는 설정을 꺼도 자동 삭제하지 않는다. 이력이 있는 배포는 되돌릴 때 purge 실행을 먼저 차단한다.
- 복원 기능 비활성화는 신규 접수만 막는다. 이미 접수된 작업의 조회·정상 종료는 유지한다.
- 스키마 되돌리기는 기능 중지·작업 정리·백업 후 수행하며 downgrade에서 보존 벡터를 삭제하지 않는다.
- 운영 서버·DB에 직접 접속하지 않고 사용자 실행용 점검·반영 절차를 제공한다.

| 검증 | 완료 기준 |
|---|---|
| 정상 전환 | v3 → v1 복원, 포인터·파일·페이지·청크·사진·출처 일치, 재임베딩 0회 |
| 보존 무결성 | 복원 전후 벡터·포인트 ID·내용 payload 불변, 다른 문서 영향 없음 |
| 반복 적용 | v3 → v1 → v3, 적용 순번 증가 및 이력 누락 없음 |
| 신규 업로드 | 현재 v1, 최대 v3이면 새 v4 생성 |
| 상태 경쟁 | 업로드·복원·삭제 충돌, 중간 상태 변경, 중복 클릭·멱등 키 충돌 검증 |
| 장애 | Qdrant·파일 누락·모델 미지원 시 기존 버전 유지, 커밋 뒤 응답 유실은 성공 재조회 |
| 재시작 | queued/running 복원 복구, 업로드 file_path 로직 진입 없음, 중복 적용 0 |
| 보안 | 관리자 전용 POST, 목록·이력·작업·사진·출처의 현재 권한 검사, 접근 불가 문서는 404 |
| 검색 | dense/sparse/hybrid/스크롤 등 전 채널 필터, 캐시·진행 요청의 버전 혼합 없음 |
| 삭제·설정 | 전체 버전 노출 차단, 복원 기능 종료 시 보존 데이터 자동 삭제 없음 |
| API | 전달 명세의 JSON·nullable·오류 코드·페이지네이션·시간대 일치, 기존 클라이언트 호환 |
| 부하 | 이력 GET에 전체 벡터 읽기 없음, 대표 보존량에서 필터 크기·지연·용량 측정 |

백엔드 완료 산출물은 코드·마이그레이션·자동화 테스트·API OpenAPI 명세·가용성 점검 도구·백업 복구 및 배포/되돌리기 절차·구현 결과 보고서다. 프런트엔드 인수는 별도 담당자가 화면별 API를 연결해 공동 확인한다.
