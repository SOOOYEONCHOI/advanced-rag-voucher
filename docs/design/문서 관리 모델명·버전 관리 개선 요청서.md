# 문서 관리 모델명·버전 관리 개선 요청서 (소스코드 검토 반영)

- 검토 대상: `adrag-voucher.zip` (2026-10-19 제공본)
- 참고 목업: `admin_UI-12_문서관리_20261012.html`
- 목적: 기존 관리자 UI 분위기를 유지하면서 **모델명 관리 + 파일명이 달라도 이어지는 문서 버전 관리**를 실제 서비스에 구현한다.
- **화면 표기명은 모두 `모델명`으로 통일한다.** 단, 이미 존재하는 DB 컬럼은 `tb_documents.product_model`로 유지하는 방향을 우선 채택한다. 프론트 API 키도 가급적 `product_model`을 재사용한다. `tb_llm_models.model_name`과 혼동하거나 불필요한 `model_name` DB 컬럼을 새로 만들지 않는다.

## 1. 소스 분석: 확인된 현재 상태

| 항목 | 상태 | 근거/설명 |
|---|---|---|
| 모델명 저장 필드 | **DB 정의 존재** | `migrations/versions/0003_versions_chunks_images.py`에 `tb_documents.product_model` 추가 |
| 모델명 업로드 인자 | **일부 구현** | `routes/ingest.py`의 `POST /ingest/upload`가 `product_model: Form(None)` 수신 |
| 모델명 DB 기록 | **일부 구현** | `ingest_pipeline.py` → `ingest_record_repository.py.update_document_info()`가 `product_model` 저장 |
| 모델명 엑셀 처리 | **일부 구현** | `ingest_pipeline.py` → `excel_runner.py`에 `product_model` 전달; 실제 파싱 경로에 활용 |
| 파일명 기반 자동 모델명 생성 | **미확인/개발 필요** | 선택 입력값이 없을 때 파일명 stem을 기본값으로 채우는 처리 확인되지 않음 |

| 문서 목록 모델명 출력 | **미구현** | `GET /ingest/documents`의 `DocumentItem` 응답에 `product_model` 없음; Vue 테이블에도 컬럼 없음 |
| 모델명 직접 수정 API | **미구현** | `PATCH /ingest/documents/{document_id}` 관련 라우트 없음 |
| 버전 테이블 | **DB 정의 및 초기 적재 존재** | `tb_document_versions` 테이블 생성, 최초 업로드에 v1 `active` 레코드 삽입 |
| 실제 최신본 교체 API | **미구현** | 기존 문서 ID에 새 버전을 등록하는 엔드포인트 미확인 |
| 실제 버전 이력 API/UI | **미구현** | 업로드한 실제 Vue 화면에는 버튼/모달이 없음; HTML 목업에는 시뮬레이션만 있음 |
| 현재 문서 목록 | **기능 있음** | `GET /ingest/documents`, 문서 클릭 및 삭제 기능 |
| DB 마이그레이션 | **구현되어 있음** | Alembic `0001` ~ `0003` 존재; 실제 운영 DB의 적용 여부는 별도 확인 필요 |

**중요한 차이:** 참고 HTML 목업에는 `현재 버전`, `최신본 변경`, `버전 이력`이 표시되어 있으나, 업로드한 실제 `adrag_frontend/src/views/AdminView.vue`는 `파일명 / 문서 유형 / 총 페이지 / 대화주제 / 업로더 / 파서 / 업로드 시각 / 작업(삭제)` 컬럼을 사용한다. 구현은 HTML 목업을 그대로 복사하는 것이 아니라 실제 Vue 코드에 적용해야 한다.

## 2. UI 변경사항 (기존 스타일 유지)

**문서 목록 컬럼(권장)**

`모델명 | 파일명 | 문서 유형 | 총 페이지 | 대화주제 | 업로더 | 파서 | 현재 버전 | 최근 변경일 | 작업`

- 실제 화면의 기존 컬럼은 가능한 한 유지한다. `모델명`을 `파일명` 앞에 추가한다.
- 모델명 표시값은 `product_model`이며, 파일명은 현재 활성 버전의 `original_filename`이다.
- 모델명 셀에 연필 아이콘을 두고 클릭 시 텍스트 입력, `저장`/`취소` 버튼을 표시한다.
- 저장 성공 후 화면 및 DB에 즉시 반영, 새로고침 후에도 유지한다. 공백·빈 문자열 입력은 차단한다.
- `작업` 컬럼에는 기존 삭제 버튼을 유지하고, `최신본 변경`, `버전 이력` 버튼을 추가한다.
- 현재 버전은 예: `v1`, `v2`, `v3`로 표시한다. 가로 스크롤, 컬럼 너비 조절, 반응형 레이아웃을 보존한다. 기존 `첫 번째 컬럼=파일명`을 가정한 리사이즈 이벤트/스타일은 수정한다.
- 업로드 화면의 **파일별 모델명 입력·수정·전송은 필수 개발 범위**다. 현재 공통 `제품 모델(선택)` 입력을 파일별 `모델명` 입력으로 변경한다. 자동 생성 후 목록에서만 수정하는 방식으로 완료 처리하지 않는다. 상세 구현과 검증은 9절을 따른다.

## 3. 모델명 저장·수정 규칙

### 3.1 신규 업로드

1. `product_model`이 명시적으로 입력되고 유효하면 이를 사용한다.
2. 입력되지 않았으면 업로드한 **원본 파일명에서 마지막 확장자만 제거**하여 기본값을 만든다. 예: `C2.assembly.rev2.pdf` → `C2.assembly.rev2`.
3. 앞뒤 공백을 제거한다. 최대 길이 100자 정책은 현재 업로드 API의 100자 제한과 통일하되, **조용히 잘라내지 말고** 422와 검증 오류를 반환한다. 현재 업로드 라우트의 `strip()[:100]` 처리를 명시적 검증으로 변경한다.
4. `tb_documents.product_model`에 영속 저장한다. 다른 문서와 같은 모델명을 허용한다.
5. `doc_key`는 기존 별도 컬럼으로 유지하고 모델명으로 대체하거나 문서 ID로 사용하지 않는다.

### 3.2 화면 수정 API

권장 예시(기존 라우터 스타일 준수):

```http
PATCH /ingest/documents/{document_id}/model-name
Content-Type: application/json

{"product_model": "NEOCON C2 제조 관리 문서 대장"}
```

- 백엔드에서 인증/수정 권한 확인(관리자 또는 정책상 허용된 문서 소유자).
- 존재하지 않거나 삭제된 문서는 404, 무권한 403, 잘못된 값 422 등 적절히 응답한다.
- `tb_documents.product_model`과 `updated_at` 갱신; 필요 시 `tb_document_events`에 수정 이력 추가.
- 목록 조회 `GET /ingest/documents`에 `product_model`, `version_no`, 최신본 파일명, 최근 변경일을 포함한다.
- **모델명만 수정할 경우 재파싱/재청킹/재임베딩을 실행하지 않는다.** 다만 Qdrant payload의 모델명으로 검색 필터 또는 답변 메타데이터를 사용한다면 RDB와 Qdrant 동기화 정책을 구현하고 검증한다. 이미 생성된 청크 텍스트 머리말에 모델명이 포함된 경우 텍스트 자체는 단순 DB 수정으로 바뀌지 않으므로 동기화 범위를 명확하게 결정한다.

## 4. 최신본 변경 및 버전 이력

### 4.1 원칙

- **기존 `document_id`를 유지**하면서 신규 `tb_document_versions` 버전 행을 추가한다.
- 새 업로드의 실제 파일명은 새 버전의 `original_filename`에 저장한다.
- `tb_documents.product_model`은 기존에 수정해 둔 값을 **절대로 자동 덮어쓰지 않는다.**
- `tb_documents`의 표시용 원본 파일명, 경로, 페이지, 청크 수, 활성 버전 번호 등은 **신규 버전 활성화 성공 시에만** 갱신한다.
- 교체 실패 시 기존 검색 가능 버전과 표시 정보를 유지한다.
- 같은 모델명이나 파일명이 있다는 이유만으로 자동 교체하지 않는다. 반드시 사용자가 기존 행에서 최신본 변경을 실행한다.

### 4.2 API 설계(신규)

```http
POST /ingest/documents/{document_id}/versions
Content-Type: multipart/form-data
file=<new-file>

GET /ingest/documents/{document_id}/versions
```

- 새 버전은 `building → ready → active` 등 명확한 상태 전이를 사용한다.
- 기존 `active` 버전은 **신규 버전 활성화가 성공한 후** `retired`로 전환한다.
- 활성 버전 동시 1개 제약, 중복 교체 요청 방지(락/낙관적 동시성 제어), 실패/롤백 처리를 구현한다.
- PostgreSQL RDB 트랜잭션과 Qdrant는 원자적 트랜잭션이 아니므로 청크/벡터 생성 → 검증 → 활성 버전 전환 → 이전 벡터 비활성화 또는 삭제 등의 안전한 처리 순서를 설계한다.
- 버전 이력에서는 버전 번호, 실제 파일명, 상태, 업로드 일시/업로더, 파싱/청크 수, 활성 여부를 보여준다.
- 기존 `tb_document_versions`의 복합 기본키 `(document_id, version_no)`를 사용한다. 별도의 `version_id`나 `current_version_id` 컬럼은 기존 구조를 검토하고 실제 필요할 때만 추가한다.
- 현재 적재 파이프라인이 `INITIAL_VERSION`으로 초기 버전만 생성하는 부분을 수정한다. 기존 `create_active_version()`을 재사용할 수 있으나 곧바로 active로 만드는 동작은 교체 시나리오에 맞게 분리/확장한다.

## 5. 기존 데이터·마이그레이션

- **기존 `product_model` 필드 재사용을 1순위로 검토한다.** `model_name` 컬럼 신규 추가는 하지 않는다.
- Alembic 신규 revision으로 기존 `product_model IS NULL` 또는 공백인 행만 파일명 stem 기반으로 백필한다. 사용자가 설정한 값은 변경하지 않는다.
- `tb_document_versions`에 기존 문서들의 v1 백필이 제대로 되었는지 점검한다. 기존 마이그레이션 `0003`에 관련 백필이 포함되어 있으므로 중복 실행하지 않는다.
- 로컬 개발 DB에서 `alembic current`, `alembic heads`, upgrade/downgrade를 검증한다. 개발자는 운영 DB에 접속하지 않고 운영 적용 여부 확인·반영 절차만 인계한다.
- 기존 `doc_key`, `title`, `product_model`, LLM용 `model_name` 필드의 역할을 혼동하지 않는다.

## 8. Claude Code 작업 지시

**우선 위 경로의 실제 코드를 열어 현행 코드와 이 문서의 분석이 일치하는지 확인하고, 변경 파일 및 구현 순서를 제시한 후 작업하라.** 특히 `product_model` 기존 저장 경로를 재사용하고 신규 `model_name` 컬럼은 추가하지 마라. `tb_document_versions`가 있다고 해서 버전 전환까지 완료되어 있다고 가정하지 마라. 실제 Vue 서비스 코드를 수정하되 기존 화면 분위기와 기능을 보존하고, 마이그레이션·API·UI·통합 테스트까지 완료하라. 확인할 수 없는 외부 서버 설정이나 실제 운영 DB 상태는 완료되었다고 주장하지 말고 확인 필요사항으로 남겨라.

### 9.1 모델명의 의미와 화면 흐름

- 모델명은 이미지의 `NEOCON C2 제조 관리 문서 대장`처럼 문서를 구분하는 표시명이다. 제품 코드만 입력하도록 제한하지 않는다. 대화 주제·접근 권한 그룹(D-15), LLM 모델명과 구분한다.
- 파일 선택/드래그 후 대기 목록 각 행에 `파일명 | 모델명 입력 | 기존 상태·작업`을 표시한다. 현재 공통 `제품 모델(선택)` 입력은 파일별 입력으로 전환한다.
- 파일 추가 시 마지막 확장자를 뺀 파일명을 기본값으로 넣고 업로드 전 사용자가 수정한다. 한 행 수정은 다른 파일에 영향을 주지 않는다. 안내 문구는 `파일명에서 자동 입력됩니다. 필요하면 수정하세요.`로 한다.
- 앞뒤 공백 제거 후 1~100자만 허용한다. 빈 값·공백·초과 값은 행별 오류를 표시하고 전송을 막는다. 서버도 같은 규칙으로 검증한다. 필드 누락 API 호출은 기존 클라이언트 호환용 파일명 기본값을 생성하되 명시적 빈 값·공백은 422로 처리한다. 자동 생성값도 길이를 검증하며 임의로 잘라내지 않는다.
- 전송 시작 시 파일별 값을 확정하고 처리 중 입력을 잠근다. 접수 거절 후 재전송은 해당 행의 수정값을 사용하고, 서버에 생성된 작업 재시도는 저장된 원래 요청값을 유지한다.
- 등록 완료 후 목록의 첫 컬럼에 모델명과 연필 아이콘을 표시한다. 파일명은 별도 `파일명(최신본)` 링크로 유지한다. 편집 저장 실패 시 입력값과 오류를 보여 주고 취소하면 기존 값으로 돌아간다.
- 이미지의 `현재 버전`은 시스템 `version_no`다. 파일명 속 `_v3`나 내부 개정 차수 `revision_label`에서 추측하지 않는다. `최근 변경일`은 등록·모델명 수정·최신본 활성화의 문서 변경 시각이며 기존 KST 표시 방식을 따른다.
- 실제 화면의 문서 유형·파서, 대화 주제 필터·새로고침·원본 열기·삭제, 최대 10개 업로드·진행 표시를 유지한다. 컬럼 추가에 따른 리사이즈 인덱스·너비 저장·가로 스크롤을 점검한다.

### 9.2 실제 코드 기준 구현 순서와 검증

| 단계 | 수정 대상 | 개발 내용 | 단계 완료 검증 |
|---|---|---|---|
| 1. 파일별 업로드 | `AdminView.vue`, `useDocumentUpload.js`, `useAdminDocuments.js` | 파일 항목에 `productModel`을 추가하고 파일명 기본값·개별 입력·행별 검증을 구현한다. FormData의 `product_model`은 공통 `options.productModel` 대신 해당 파일 항목에서 가져온다. 사용하지 않게 된 공통 상태만 제거한다. `adminApi.js`의 기존 FormData 전달은 재사용한다. | 두 파일에 서로 다른 모델명을 입력해 각 요청·작업 요청·DB 값이 일치하는지 확인 |
| 2. 서버 저장·조회 | `routes/ingest.py`, `ingest_service.py`, `document_repository.py`, `ingest_pipeline.py`, `ingest_record_repository.py` | 현재 100자 자동 잘림을 검증으로 변경하고 누락 기본값을 처리한다. 기존 저장 경로를 재사용한다. `DocumentItem`과 대화 주제 지정/전체 목록 조회에 모델명·버전·변경일을 연결한다. | 업로드 완료 후 목록·새로고침에서도 입력값 유지, 새 청크 생성 경로에 입력 모델명 전달 확인 |
| 3. 목록 편집 | `AdminView.vue`, `useAdminDocuments.js`, `adminApi.js`, 백엔드 라우트·저장소 | 선두 모델명 컬럼, 인라인 저장/취소, PATCH, 기존 권한 정책을 연결한다. 모델명만 바꾸면 버전 증가·재파싱·재임베딩을 하지 않는다. 검색 메타데이터 동기화 범위는 3.2절에 따라 명시한다. | 수정·취소·실패·권한·새로고침과 기존 파일 열기/삭제/필터 회귀 확인 |
| 4. 기존 데이터 | 신규 Alembic revision | 기존 비어 있는 값만 파일명으로 보정한다. 100자 초과 기본값은 사전 점검에서 보고하고 적용 전 정리한다. 기존 사용자 입력값을 보존하고 downgrade의 데이터 되돌림 범위를 명시한다. | 로컬 upgrade/downgrade, 기존 값 보존·누락값 보정 확인 |
| 5. 버전 관리 | 버전 API·서비스·저장소, 목록 버튼/모달 | 모델명 단계를 먼저 완료한 뒤 4절의 최신본 변경·이력을 별도 구현한다. D-01의 관리자 지정·문서별 직렬화·중복 파일 정책, D-18의 이전 버전 복원 범위를 준수한다. | 교체 중/실패 시 기존본 유지, 성공 시 새 버전만 검색, 동시 교체 방지·이전 이력 보존 확인 |

버전 전환 시 RDB와 Qdrant 사이 장애를 고려한다. 이전 벡터 정리가 실패해도 구 버전이 검색되지 않도록 활성 버전 검증을 포함하고, 원본·이미지 참조는 버전별로 보존한다. 버전 이력의 이전 버전 복원은 기존에 없으면 이번 1차 범위에 새로 추가하지 않는다. 교체 API의 권한 없는 대상 응답 등은 D-01의 정보 노출 방지 정책을 우선한다.

Phase 2 보고서에는 엑셀 적재·초기 버전 저장이 구현되어 있고 버전 전환과 docling 경로 리소스 ID 충돌은 후속 이슈로 남아 있다. 모델명 UI 추가만으로 버전 관리까지 완료됐다고 보고하지 않는다. 각 단계에 UI-12·SC-06·SC-07 등 실제 관련 ID, 변경 파일·검증 결과·남은 이슈를 기록한다. 기존 회귀 실패는 기준선과 비교해 신규 실패와 구분한다. `excel_ingest` 추출 규칙 및 docling-parser 서버 코드는 수정하지 않는다.

### 9.3 추가 완료 기준

- [ ] 파일 선택 시 파일별 모델명 기본값이 보이고 업로드 전에 개별 수정할 수 있음
- [ ] 서로 다른 모델명으로 2개 이상 업로드 시 요청·작업·DB·목록 값이 섞이지 않음
- [ ] 입력한 `NEOCON C2 제조 관리 문서 대장`이 파일명과 별개로 목록 선두에 표시됨
- [ ] 접수 거절 후 재전송과 서버 작업 재시도에서 해당 파일의 모델명이 유지됨
- [ ] 필드 누락 시 기본값 생성, 명시적 빈 값·공백·101자 입력은 오류, 100자 입력은 허용
- [ ] 모델명 저장/취소/실패 처리와 새로고침 후 유지 확인
- [ ] 최신본 변경 전후 문서 ID·모델명 유지, 실패 시 기존 검색본 보존
- [ ] 기존 업로드·폴링·원본 열기·삭제·대화 주제 필터·컬럼 리사이즈 회귀 확인
