# RAG 구현 현황·성능 평가·GPU 서빙·pgvector 비교 분석

- 작성일: 2026-11-09
- 분석 대상: `advanced-rag-voucher` 저장소의 코드·배포 스크립트·보관된 평가 결과
- 확인 범위: 정적 코드 및 문서 분석. 운영 서버 접속이나 성능 재측정은 수행하지 않았다.
- 해석 기준: 구현 여부와 실측 검증 여부를 구분한다. 코드 기본값은 실제 환경변수·요청별 설정에 따라 달라질 수 있다.

## 핵심 판단

현재 코드를 기준으로 **Dense·Sparse·RRF·Reranker·Fallback·문서 파싱은 모두 구현되어 있다.** 다만 “구현되어 있다”와 “현재 운영 데이터로 성능이 검증되었다”는 구분해야 한다.

- **검색:** Qdrant 서버 측 Dense + Kiwi BM25 sparse + 가중 RRF가 기본이다. BM42/SPLADE는 선택 가능한 별도 경로다.
- **평가:** 골든셋 생성·검수·평가·대시보드까지 구현되어 있지만, 평가와 운영의 차이 및 데이터셋 편향을 보완해야 한다.
- **GPU:** 저장소에는 H100 80GB 2장 운영 구성과 사용 현황이 있다. L40S 48GB 1장은 핵심 모델 3개에 한해 조정 후 가능성이 있으나, 현재 설정 그대로의 운영은 보장할 수 없다.
- **pgvector 비교:** 현 단계에서는 Qdrant 유지가 합리적이다. 다만 pgvector보다 검색 품질이나 속도가 우수하다는 비교 실험 근거는 없다.

## 1. RAG 검색 구성과 현재 구현 범위

### 1.1 전체 처리 흐름

```text
질문 입력
 → 입력 검증·가드레일
 → 질문 분석·정규화·재작성
 → 사용자 권한·문서 범위 필터 구성
 → Dense + Kiwi BM25 검색
 → Qdrant 서버 측 가중 RRF
 → 메타데이터 점수 보강
 → 본문 중복 제거·Reranker
 → 관련성 판단
 → 컨텍스트 구성
 → 답변 생성·인용·관련 이미지 연결
```

관련성이 부족하면 검색 범위를 확대해 재검색하고, 모델·검색 시스템 장애는 별도 오류 경로로 처리한다.

- [vector_repository.py](../../adrag_backend/app/repositories/vector_repository.py)

### 1.2 Dense 검색

Dense 검색은 질문을 임베딩해 Qdrant의 `dense` 벡터에서 유사 청크를 찾는 방식이다.

- 배포 모델: `Qwen3-Embedding-4B`
- 유사도: 코사인
- 재작성 질문이 여러 개면 각각 임베딩해 검색 후보에 반영
- 재작성 질문 수가 많아져도 Dense의 총가중치가 과도하게 커지지 않도록 가중치를 나누어 적용

예를 들어 Dense 가중치가 1.5이고 재작성 질문이 3개라면, 각 Dense 검색 목록에 0.5씩 배분한다.

즉, 단일 질문의 벡터 검색뿐 아니라 **다중 재작성 질문을 이용한 후보 확장**까지 구현되어 있다.

### 1.3 Sparse 검색: 기본은 Kiwi BM25

현재 기본 Sparse는 **한국어 형태소 분석기 Kiwi와 Qdrant BM25 sparse 인덱스의 조합**이다.

처리 방식:

1. 문서 적재 시 Kiwi로 본문을 토큰화한다.
2. `qdrant/bm25` 형식으로 인코딩한다.
3. Qdrant의 `kiwi_bm25` named sparse vector에 저장한다.
4. 질문도 같은 정책으로 처리해 검색한다.
5. 컬렉션의 IDF 보정은 Qdrant에서 적용한다.

| 항목 | 코드 기본값 |
|---|---:|
| BM25 `k1` | 1.2 |
| BM25 `b` | 0.5 |
| 평균 문서 길이 기준 | 128 |
| Sparse 벡터 이름 | `kiwi_bm25` |

질문에는 정규화된 원문뿐 아니라 확장 용어·법령 참조·추출 키워드를 반영한다. 법령 조문, 모델명, 메뉴명처럼 정확한 용어 일치가 중요한 질문을 보완하려는 구성이다.

**예전 Python BM25 코드도 남아 있다.** 이 경로는 제한된 후보를 가져와 BM25 점수를 재계산하는 방식이며, 현재 기본 Qdrant sparse 전체 인덱스 검색과 다르다. 일부 주석은 과거 방식을 설명하고 있으므로 실제 실행 분기를 기준으로 판단해야 한다.

근거: [kiwi_bm25_encoder.py](../../adrag_backend/app/clients/kiwi_bm25_encoder.py)

### 1.4 BM42·SPLADE

| 방식 | 구현 범위 | 현재 기본 경로 여부 |
|---|---|---|
| Kiwi BM25 | 적재·질의 인코딩, Qdrant sparse 검색 | 기본 |
| BM42 | FastEmbed 모델 로딩·인코딩·Qdrant sparse 검색 | 선택 경로 |
| SPLADE | 외부 서버 `/encode` 호출·sparse 검색 연결 | 선택 경로 |
| Python BM25 | 기존 후보 기반 재계산 | Legacy |

Legacy 검색 프로필로 `dense_kiwi`, `dense_bm42`, `dense_kiwi_bm42`가 존재한다.

다만 기본 `retrieval_engine="qdrant_hybrid"`에서는 **Dense + Kiwi BM25 전용 경로를 실행**한다. 프로필 이름만 바꾼다고 기본 검색에 BM42가 추가되는 구조는 아니다.

SPLADE는 클라이언트 연결이 있다는 의미이며, 실제 서버가 배포·가동되고 있다는 증거와는 구분해야 한다.

근거: [sparse_encoder.py](../../adrag_backend/app/clients/sparse_encoder.py), [retrieval_engine.py](../../adrag_backend/app/graphs/retrieval_engine.py)

### 1.5 RRF

기본 검색은 Dense와 Sparse를 따로 호출한 뒤 Python에서 합치는 방식에서 발전해, **Qdrant Query API 한 번으로 후보 검색과 가중 RRF 병합을 수행**한다.

| 단계 | 코드 기본값 |
|---|---:|
| Dense 사전 후보 | 질문별 최소 80개 |
| Sparse 사전 후보 | 최소 80개 |
| 병합 후 검색 후보 | 40개 |
| Reranker 반환 | 10개 |
| 최종 컨텍스트 | 최대 6개 |
| RRF 상수 | 60 |

RRF는 서로 척도가 다른 Dense 유사도와 BM25 점수를 직접 더하지 않고, 각 검색 목록의 순위를 이용해 합친다.

질의 유형별 가중치도 구현되어 있다.

| 질문 유형 | Dense | Kiwi BM25 |
|---|---:|---:|
| 법령·조문 참조 | 0.7 | 1.5 |
| 개념 설명 | 1.5 | 0.7 |
| 메뉴·매뉴얼 | 0.8 | 1.5 |
| 사고 사례·서술형 | 1.5 | 0.8 |

다만 이 값들은 코드에도 **평가셋으로 튜닝할 초기값**이라고 명시되어 있다. 현재 데이터에서 최적이라는 검증 결과로 보기는 어렵다.

### 1.6 Reranker

Reranker는 `bge-reranker-v2-m3`를 vLLM의 `/v1/score`로 호출한다.

실제 동작:

- 검색 후보의 동일 본문을 해시 기준으로 중복 제거
- 문서명·섹션 경로를 본문 앞에 붙여 입력
- 원 질문과 각 후보 청크의 관련성 재계산
- 점수순 정렬 후 상위 결과 반환
- 응답의 개수·인덱스 중복·누락·비정상 점수 검증

**`reranker_top_k=10`은 10개만 채점한다는 뜻이 아니라, 입력 후보들을 채점한 뒤 10개를 반환한다는 의미**다. 따라서 후보 수와 본문 길이가 Reranker 부하에 영향을 준다.

관련성 기본 임계값은 `0.25`다. 다만 활성화된 CE 점수이므로 “정답 확률 25%”로 해석하면 안 된다.

근거: [rerank.py](../../adrag_backend/app/graphs/nodes/rerank.py), [reranker_client.py](../../adrag_backend/app/clients/reranker_client.py)

### 1.7 Fallback

Fallback은 원인에 따라 구분되어 있다.

| 발생 상황 | 구현된 대응 |
|---|---|
| 검색 성공, 관련성 미달 | 검색·재정렬 반환 범위를 확대하고 재검색 |
| 재검색 | 재작성 질문 대신 원 질문 사용, 임계값 0.1로 완화 |
| Reranker 타임아웃·통신·응답 오류 | 기존 검색 순위의 상위 일부를 사용 |
| LLM 생성 오류 | 확보된 컨텍스트를 재사용해 생성 재시도 |
| Qdrant 장애·검색 타임아웃 | 검색 오류로 종료 |
| 재시도 후에도 근거 부족 | 관련 정보 없음 안내 |

재검색 시 후보 수와 재정렬 반환 수를 확대하지만, 컨텍스트 수는 유지한다. 기본 최대 재시도는 1회다.

Reranker 장애 시에는 RRF 점수에 CE 임계값을 적용하지 않도록 임계값을 우회한다. 서로 다른 점수 척도를 비교해 모든 청크가 탈락하는 문제를 피한 것이다.

다만 이때는 **관련성이 충분히 검증되지 않은 청크가 답변 생성에 들어갈 수 있으므로**, 운영 평가에서 정상 경로와 장애 시 경로의 품질을 따로 확인해야 한다.

**Qdrant 장애 시 다른 검색 DB로 자동 전환하는 Fallback은 확인되지 않았다.**

근거: [fallback_handler.py](../../adrag_backend/app/graphs/nodes/fallback_handler.py), [edges.py](../../adrag_backend/app/graphs/edges.py)

### 1.8 컨텍스트 구성

최종 컨텍스트에는 다음 제한이 적용된다.

- 관련성 임계값
- 동일 본문 중복 제거
- 기본 문서당 최대 2개 청크
- 컨텍스트 청크 수 제한
- 문자 수 제한
- 모델 입력 한도와 출력 토큰을 고려한 크기 제한

문서당 2개 제한은 특정 문서가 결과를 독점하는 것을 줄이지만, 하나의 SOP에서 여러 연속 단계를 설명해야 하는 질문에는 불리할 수 있다. SOP 평가셋에서 확인할 항목이다.

근거: [assemble_context.py](../../adrag_backend/app/graphs/nodes/assemble_context.py)

### 1.9 문서 파싱

문서 파싱은 단순 텍스트 추출을 넘어 구조 기반 청킹과 이미지 연결까지 구현되어 있다.

| 영역 | 확인된 구현 |
|---|---|
| PDF | Docling 기본 경로, pdfplumber 선택 경로 |
| 스캔 PDF | 텍스트 레이어 판별 후 한국어·영어 EasyOCR GPU 처리 |
| 표 | TableFormer 기반 구조 인식 |
| Word·PowerPoint | Markdown 변환과 청킹 경로 |
| 이미지 파일 | OCR 처리 경로 |
| Excel | OpenPyXL 구조 파싱 및 별도 backend 적재 경로 |
| 문서 유형 | 법령·매뉴얼·일반·스프레드시트별 청킹 |
| 출처 | 페이지·섹션·시트·셀 범위 등 메타데이터 |
| 사진 | 자원 저장, 청크 연결, 답변·출처 이미지 연결 |

Excel은 두 설정을 구분해야 한다.

- 백엔드 `EXCEL_PARSE_MODE`: Docling 서버 경로와 backend 전용 경로 선택
- 파서 서버 `EXCEL_PARSER`: OpenPyXL과 Docling 선택

backend 전용 경로에는 `.xlsx`, `.xlsm` 처리와 `.xls` 변환 경로가 있다.

파싱 한계:

- 스캔 PDF 판별은 일부 페이지를 표본 검사하므로 혼합형 PDF를 완벽하게 판별한다고 보기 어렵다.
- Word의 페이지 번호는 실제 인쇄 페이지와 동일하다고 보장할 수 없다.
- **사진을 추출·연결하는 기능과 도면의 의미를 VLM이 이해하는 기능은 별개**다.
- 확인한 기본 검색 경로는 텍스트 임베딩 기반이다. 이미지 자체의 유사도 검색이나 도면 의미 이해가 기본 RAG에 통합·검증되었다고 설명할 근거는 부족하다.

근거: [문서 파서](../../docling-parser/app/services/parser.py), [파싱·청킹 설정](../../adrag_backend/app/parsers/config.py), [파일 라우팅](../../adrag_backend/app/ingest/file_router.py)

## 2. 검색 성능 평가와 실증 운영

### 2.1 골든 데이터셋 관리 기능

관리자 평가 기능은 다음 흐름까지 구현되어 있다.

```text
컬렉션 청크 샘플링
 → LLM으로 질문·정답 후보 생성
 → 실제 검색으로 정답 청크 검출 여부 확인
 → 관리자 수정·승인·반려
 → 승인 항목으로 골드셋 확정
 → 검색 평가 또는 Full 평가
 → 결과 비교·추이·Excel 다운로드
```

주요 데이터는 질문, 정답, 정답 청크 ID, 정답 문서 ID, 질문 유형, 기대 동작, 태그다.

| 자동 생성 질문 유형 | 기본 비율 |
|---|---:|
| 사실 확인 | 50% |
| 절차 설명 | 30% |
| 비교 | 10% |
| 여러 청크를 조합하는 질문 | 10% |

문서·섹션 다양성을 고려한 샘플링과 같은 문서 내 인접 청크를 조합한 질문 생성도 있다. 다만 **인접 청크 조합이 곧 복잡한 다중 문서 추론 검증을 의미하지는 않는다.**

기대 동작에는 정상 답변 외에도 정보 부족, 가드레일, 권한 거절을 지정할 수 있다. 자동 생성기는 기본적으로 정상 답변 항목을 만들므로 부정 사례는 별도로 구성해야 한다.

근거: [데이터셋 생성기](../../adrag_backend/app/evaluation/dataset/generator.py), [평가 API](../../adrag_backend/app/routes/evaluation.py)

### 2.2 검증 도구와 지표

| 평가 대상 | 구현된 지표·관측값 |
|---|---|
| 검색 | Recall@K, MRR, NDCG, 문서 기준 검색 지표 |
| 재정렬 | Reranker 이후 순위 지표, 임계값 통과 여부 |
| 답변 | 임베딩 유사도, 문장 정렬 기반 지표, F2, LLM Judge |
| 인용 | 인용 완전성·정답 근거와의 대응·진단 |
| Fallback | 잘못된 거절·잘못된 답변·재시도 복구 여부 |
| 실행 | 소요 시간, 노드별 시간, 토큰 사용량, 오류·제외 건수 |
| 결과 분석 | 질문 유형·태그별 집계, 실행 비교·추이 |

답변 정확도는 여러 지표를 저장하고, 기본적으로 `F2`를 주 지표로 선택한다. 계산할 수 없으면 설정된 순서로 대체 지표를 선택한다. **여러 점수 중 가장 높은 값을 선택하는 방식은 아니다.**

CLI 검색 비교 모드:

- `dense_only`

### 2.4 현재 평가에서 보완해야 할 부분

#### 자동 생성 질문의 검색기 편향

현재 생성기는 질문으로 검색했을 때 정답 청크가 나오지 않으면, 핵심 용어를 더 포함하도록 질문을 한 번 다시 만든다. 검색 실패 질문을 모두 버리지는 않지만, 결과적으로 **현재 검색기가 잘 찾는 질문 쪽으로 데이터셋이 쉬워질 가능성**이 있다.

최종 시험셋에는 실제 사용자 질문과 최초 검색 실패 질문을 별도로 보존해야 한다.

#### 평가에서만 인용 추가 보정

Full 평가 어댑터는 그래프 실행 후 누락된 인라인 인용을 한 번 보정한다. 코드상 운영 스트리밍에는 이 보정이 적용되지 않는다.

따라서 평가의 인용 점수가 운영 사용자가 처음 받은 응답보다 좋게 나올 수 있다. **원본 응답 점수와 보정 후 점수를 분리하는 것이 필요하다.**

근거: [rag_pipeline_adapter.py](../../adrag_backend/app/evaluation/adapters/rag_pipeline_adapter.py)

#### 평가와 운영의 후보 수 차이

코드 기본 운영 배분은 `40 → 10 → 최대 6`이지만, 평가 API 기본값은 검색 10개·재정렬 5개이며 Full 평가에서 컨텍스트도 5개로 지정한다.

검색 단독 평가는 재작성 없이 원 질문으로 실행하는 반면, Full 평가는 그래프를 실행한다. **같은 검색 엔진을 사용하더라도 동일 조건의 평가는 아니다.**

#### 부정 사례 부족

과거 60건 분석에는 정보 부족 질문이 없어 거절 성능이 `N/A`라고 명시되어 있다. 이때 Fallback 정확도 100%만 보고 거절 정책이 완성되었다고 판단하면 안 된다.

#### 실제 사용자별 권한 평가

Full 평가는 고정된 평가 사용자로 그래프를 직접 호출한다. 따라서 실제 사용자별 로그인·권한·문서 버전·이미지 접근까지 포함한 API 검증을 대체하지는 않는다.

### 2.5 실증 운영에 적합한 검증 방법

| 단계 | 검증 내용 |
|---|---|
| 검색 품질 | 동일 질문으로 Dense / Hybrid / Hybrid+Reranker 비교 |
| 실제 답변 품질 | 운영과 같은 설정으로 답변·근거·사진·거절·권한 검증 |
| 운영 성능 | 동시 질의·문서 적재 중 지연 시간, 오류, GPU 메모리 측정 |

골든셋에 필요한 유형:

- 실제 SOP의 준비·작업·검사·안전 절차
- 모델명·부품명·사진 위치를 묻는 질문
- 유사한 문서 중 특정 모델·버전을 찾아야 하는 질문
- 띄어쓰기·약어·오탈자·STT 오류
- 여러 청크에 근거가 분산된 질문
- 문서에 없는 질문과 권한 밖 질문

튜닝셋과 최종 시험셋은 분리하고, 비교할 때 모델·청킹·문서 버전·후보 수·임계값을 고정해야 한다.

운영 코드에는 질의 결과 코드, 토큰 사용량, 사용자 피드백과 통계 기능이 있다. 이를 활용해 실패 질의를 검수 후 회귀 평가셋에 추가할 수 있다. 다만 현재 코드의 평균 지연 시간 집계만으로 P95·P99나 최대 동시 처리량이 검증되었다고 말할 수는 없다.

## 3. 로컬 LLM 서빙과 GPU 배분

### 3.1 현재 서빙 구조

모델 세 개를 하나의 엔진에 로딩하는 방식이 아니라, **각 모델을 별도 vLLM 프로세스와 포트로 실행**한다.

| 용도 | 모델 | 운영 GPU | 포트 | 주요 설정 |
|---|---|---:|---:|---|
| LLM | Qwen3.5-9B | 0 | 8101 | BF16, 24,576 토큰, 최대 시퀀스 16 |
| 임베딩 | Qwen3-Embedding-4B | 1 | 8102 | Pooling, 입력 8,192 토큰 |
| Reranker | bge-reranker-v2-m3 | 1 | 8103 | Pooling, FP16 |
| 문서 파서 | Docling·OCR | 0 | 별도 서비스 | LLM과 GPU 공유 |

메모리 이용 설정은 LLM `0.70`, 임베딩 `0.18`, Reranker `0.05`다.

개발 스크립트에는 GPU 0 한 장에서 세 모델을 함께 실행하는 설정도 있다. 이때 비율은 `0.49 / 0.12 / 0.05`이며 임베딩 최대 길이가 2,048로 더 작다.

따라서 **한 GPU에서의 공존을 고려한 구성은 존재**한다. 다만 스크립트만으로 L40S에서 안정적으로 운용했다는 경험까지 증명되지는 않는다.

### 3.2 저장소에 기록된 운영 경험

2026-11-05 GPU 사용 현황 문서에는 H100 80GB × 8장 중 2장을 사용한다고 기록되어 있다.

| GPU | 서비스별 기록 | 합계 |
|---|---|---:|
| 0 | LLM 약 55.8GB, 파서 대기 약 2.6GB | 약 58.4GB |
| 1 | 임베딩 약 14.9GB, Reranker 약 2.3GB, ASR 약 7.2GB | 약 24.4GB |

이 수치는 **문서에 기록된 사용량**이며 이번 분석에서 직접 측정한 값은 아니다.

LLM의 55.8GB를 모델 가중치의 필수 크기로 해석하면 안 된다. vLLM이 확보한 실행 메모리와 캐시 등이 포함된 수치다.

`gpu-memory-utilization`은 인스턴스별 메모리 예산 설정이며, GPU 연산 자원을 같은 비율로 격리하는 기능은 아니다. 모델들이 함께 요청을 처리하면 연산 자원과 메모리 대역폭을 공유한다.

근거: [GPU 사용 현황 기록](GPU_사용현황_메일_20261105.md), [vLLM 공식 문서](https://docs.vllm.ai/en/stable/configuration/engine_args/)

### 3.3 L40S 48GB 1장으로 가능한가?

**LLM 9B + 임베딩 4B + Reranker 세 개만 대상으로 하면, 설정을 조정해 구동할 가능성은 있다. 다만 현재 운영 설정을 그대로 옮겨 동일한 처리량을 내는 것은 별도 문제다.**

L40S는 48GB 메모리를 제공한다. 근거: [NVIDIA 공식 사양](https://www.nvidia.com/en-in/data-center/l40s/)

| 모델 | 16비트 가중치 기준 개략치 |
|---|---:|
| 9B LLM | 약 18GB |
| 4B 임베딩 | 약 8GB |
| Reranker | 약 1GB대 |
| 합계 | 약 27GB대 |

이는 파라미터 수로 계산한 근삿값이다. 실제 필요량에는 모델별 버퍼·활성값·CUDA 실행 메모리·그래프·LLM 캐시 등이 더해진다.

| 목표 | 판단 |
|---|---|
| 핵심 모델 3개, 짧은 입력·낮은 동시성 | 조정 후 가능성 있음 |
| 현재 LLM 24K 입력과 높은 동시 처리 유지 | 부하 시험 필요 |
| 대량 문서 임베딩과 채팅 동시 수행 | 자원 경합 검증 필요 |
| 세 모델에 OCR까지 동일 GPU 사용 | 파싱 피크 메모리 포함 검증 필요 |
| ASR·TTS·VLM까지 모두 상주 | 현재 자료로 가능하다고 보장하기 어려움 |

현재 비율을 단순 복사하면 안 된다. 임베딩 `0.12`는 48GB에서 약 5.8GB에 해당하므로, 4B 모델의 16비트 가중치 개략치보다 작다. 메모리 예산부터 다시 산정해야 한다.

검증 순서:

1. 핵심 모델 3개만 올리고 LLM 입력 길이와 동시 시퀀스를 보수적으로 제한한다.
2. 임베딩 배치와 Reranker 입력 길이를 제한한다.
3. 단일 질의와 동시 질의를 측정한다.
4. 문서 적재를 병행해 메모리 최대치와 P95 지연을 확인한다.
5. 부족할 경우 양자화 또는 더 작은 모델을 비교 평가한다.

LLM 입력 한도를 줄이면 backend의 컨텍스트 예산도 함께 맞춰야 한다. 양자화나 모델 변경 후에는 검색·답변 품질도 다시 측정해야 한다.

현재 근거로 외부에 설명할 수 있는 범위는 **“H100 2장 분리 운영 기록과 단일 GPU 공존 설정은 있으며, L40S 1장은 축소 설정에서 검증 가능한 후보 구성”**이다.

## 4. pgvector 하이브리드 검색과 현재 방식 비교

**현재 프로젝트에서는 Qdrant를 유지하는 편이 합리적이다. 다만 검색 품질·속도의 절대 우위는 아직 입증되지 않았다.**

### 4.1 검색 알고리즘은 pgvector에서도 구성 가능

pgvector도 PostgreSQL 전문 검색과 결합해 하이브리드 검색을 구성할 수 있으며, RRF나 Cross-encoder를 사용할 수 있다.

다음 기능은 Qdrant만의 독점적인 장점이 아니다.

- Dense 검색
- 키워드 검색과 결합
- RRF
- Reranker
- 질문 재작성과 Fallback

동일한 임베딩·토큰화·후보·가중치·Reranker를 사용하면 품질 차이가 작을 수도 있다. 검색 품질에는 DB 이름뿐 아니라 파싱·청킹·토큰화·후보 누락이 크게 작용한다.

근거: [pgvector 공식 하이브리드 검색 문서](https://github.com/pgvector/pgvector#hybrid-search)

### 4.2 현재 Qdrant 구성이 유리한 근거

| 관점 | 현재 Qdrant 구성의 이점 |
|---|---|
| 구현 완성도 | Dense·Kiwi sparse·가중 RRF가 이미 연결됨 |
| 한국어 검색 | 적재와 질의에 같은 Kiwi 정책 적용 |
| 검색 호출 | 서버 측 Query API에서 후보·RRF 처리 |
| 서비스 분리 | 검색 부하를 업무용 PostgreSQL과 분리 |
| 기존 기능 | 컬렉션·버전·권한·적재 흐름과 연동 |
| 전환 비용 | 기존 검증 범위를 유지할 수 있음 |

단순 PostgreSQL 전문 검색으로 교체하면서 Kiwi와 BM25 정책을 제거하면, 한국어 검색 결과가 달라질 수 있다. 이는 pgvector의 한계라기보다 **비교할 검색 구성 자체가 달라지는 문제**다.

### 4.3 pgvector가 유리할 수 있는 부분

현재 시스템은 PostgreSQL과 Qdrant를 함께 사용한다. 따라서 적재·버전 변경·삭제 시 두 저장소 사이의 일관성을 관리해야 한다.

pgvector 통합 시 이점:

- 메타데이터와 벡터를 같은 트랜잭션으로 처리
- 문서 버전·권한 테이블과 SQL 조인
- 백업·복구와 운영 대상 단순화

반대로 검색 부하가 업무 DB와 자원을 공유하고, 현재 sparse 인코딩·RRF·필터·버전 처리를 다시 구성해야 한다.

### 4.4 임베딩 차원 확인 필요

현재 배포 모델인 Qwen3-Embedding-4B는 최대 2,560차원 출력을 지원한다. 다만 저장소 예시 설정만으로 실제 컬렉션의 차원이 확정되지는 않았다.

pgvector의 일반 `vector` HNSW 인덱스는 최대 2,000차원, `halfvec`는 최대 4,000차원을 지원한다. 따라서 실제로 2,560차원을 사용한다면 `halfvec` 인덱싱이나 차원 축소 등을 검토해야 한다. 저장 가능 차원과 인덱싱 가능 차원은 구분해야 한다.

근거: [Qwen3-Embedding-4B 공식 설명](https://huggingface.co/Qwen/Qwen3-Embedding-4B), [pgvector HNSW 문서](https://github.com/pgvector/pgvector#hnsw)

### 4.5 권한 필터 검색은 별도 비교 필요

현재 Qdrant 구현은 Dense와 Sparse 후보 검색에 같은 권한·문서 버전 필터를 전달한다.

pgvector의 근사 검색은 필터 조건에 따라 반환 후보 수가 부족해질 수 있으며, 이를 보완하는 iterative scan 설정이 있다. 따라서 권한 필터가 강한 데이터로 후보 충족률과 지연 시간을 비교해야 한다.

이는 pgvector가 권한 검색을 못 한다는 의미가 아니라, 인덱스와 검색 설정까지 동일한 목표로 튜닝해야 한다는 의미다.

근거: [pgvector 필터 검색 설명](https://github.com/pgvector/pgvector#iterative-index-scans)

### 4.6 현재 방식의 우위를 검증하는 비교 조건

| 고정할 조건 | 비교할 결과 |
|---|---|
| 동일 문서·청크·임베딩 | Recall@K |
| 동일 Kiwi 토큰·키워드 검색 정책 | 한국어 정확 용어 검색 성공률 |
| 동일 후보 수·RRF·Reranker | NDCG·MRR·최종 답변 품질 |
| 동일 권한·활성 버전 | 필터 적용 후 후보 누락·권한 위반 |
| 동일 동시 부하 | P50·P95·P99, 처리량 |
| 동일 적재·변경 시나리오 | 갱신 시간·일관성·운영 비용 |

현재 저장소에서 확인한 자료만으로는 이 비교가 수행되었다고 볼 근거가 없다.

기술 검토나 대외 설명에는 다음 표현이 가장 정확하다.

> 현재 시스템은 한국어 Kiwi BM25와 Dense 검색을 Qdrant 서버 측 가중 RRF로 결합하고, vLLM Reranker 및 오류 유형별 Fallback까지 구현했다. 기존 기능과의 통합도 및 전환 비용을 고려하면 현재 Qdrant 유지가 합리적이다. 다만 pgvector 대비 검색 품질·응답 성능의 우위는 동일 데이터와 조건의 비교 실험으로 검증해야 한다.
