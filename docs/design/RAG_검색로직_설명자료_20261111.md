## 0. 한 장 요약

| 질문 | 답 |
|---|---|
| 1. 검색 구성·구현 범위 | Dense(Qwen3-Embedding-4B) + Sparse(**한국어 Kiwi 형태소 BM25**) → **Qdrant 서버 측 가중 RRF** → Cross-encoder Reranker(bge-reranker-v2-m3) → 관련성 판단 → 원인별 Fallback까지 **구현**. 문서 파싱은 PDF·스캔 OCR·표·Word·PPT·**Excel SOP(셀 위치·사진 연결)** 까지 구현. 11-10~11에 품번·규격 검색 개선(토큰 정책 v2)과 가중치 프로필을 추가했다. |
| 2. 성능 평가·실증 | 관리자 평가 화면(골든셋 생성·검수·검색/Full 평가·비교)과 CLI(`offline_evaluation`) 두 도구가 있다. 최신 수치는 **dev SOP 데이터 합성 질의 240건** 기준(리랭커 후 일반 질의 Hit@1 0.967, 품번 질의 0.883 → 개선안 0.983). **실제 작업자 질의 골든셋은 아직 없다.** |
| 3. 로컬 LLM 서빙 | 모델별로 **vLLM 프로세스를 따로** 띄운다. 운영은 H100 80GB 중 2장(0번 LLM, 1번 임베딩·리랭커·STT). dev는 **GPU 1장에 LLM·임베딩·리랭커 3개를 함께** 띄우는 스크립트 구성으로 개발·실험 중(설정 기준). **L40S 48GB 1장: 핵심 3개 모델은 메모리 예산을 다시 잡으면 가능성 있음, 현재 운영 설정·처리량 그대로는 부하 시험 필요.** |
| 4. pgvector 대비 | **지금은 Qdrant 유지가 합리적.** 근거: 한국어 BM25(IDF 서버 계산)·서버 측 RRF·권한/버전 필터·2,560차원 벡터가 이미 연결돼 있고, 이번 실측에서 성능을 좌우한 것은 DB가 아니라 **토큰화·가중치·질의 구성**이었다. 단 **pgvector와 같은 조건 비교 실험은 하지 않았다** → 품질·속도 우위는 주장하지 않는다. |

## 1. RAG 검색 구성과 현재 구현 범위

### 1.1 처리 흐름 (LangGraph 12개 노드)

```text
질문(텍스트·음성 STT)
 → validate_input        입력 검증
 → guardrail             업무 외·위험 질문 차단(SOP 도메인 분류)
 → analyze_and_rewrite   규칙 전처리(정규화·약어·법령 표기·형태소 키워드) + LLM 재작성 2~3개 + 임베딩(병렬)
 → build_metadata_filter 사용자 권한(보안등급·컬렉션·모델/문서 단위) 필터
 → retrieve              Dense(원문+재작성) + Kiwi BM25 → Qdrant 서버 측 가중 RRF → 메타데이터 soft boost
 → rerank                본문 중복 제거 → Cross-encoder 재채점(문서명·시트/섹션 prefix)
 → [관련성 판단]         임계값 이상 청크 없으면 fallback_handler → 범위 확대 재검색 1회
 → assemble_context      임계값·중복·문서당 개수·토큰 예산으로 컨텍스트 구성
 → collect_answer_images 근거 청크에 연결된 사진 수집(권한 확인)
 → generate_answer       로컬 LLM 답변(근거 번호 인용)
 → format_citations      출처(문서·시트·셀·개정 차수)·사진
 → build_response
```

근거: [rag_graph.py](../../adrag_backend/app/graphs/rag_graph.py), [edges.py](../../adrag_backend/app/graphs/edges.py)

### 1.2 구성 요소별 구현 범위

| 구성 | 구현 내용 | 기본값 | 상태 |
|---|---|---|---|
| **Dense** | Qwen3-Embedding-4B(2,560차원, 코사인). 원문 + LLM 재작성 질의를 각각 임베딩해 후보 확장 | 질의별 사전 후보 80 | 구현·운영 |
| **Sparse (기본)** | Kiwi 형태소 분석 → `qdrant/bm25` 형식 → Qdrant named sparse vector `kiwi_bm25`, **IDF는 Qdrant가 컬렉션 기준으로 계산**. 적재와 질의가 같은 토큰 정책 사용 | k1 1.2 · b 0.5 · 사전 후보 80 | 구현·운영 |
| Sparse (선택) | BM42(FastEmbed), SPLADE(외부 서버) 채널, 예전 Python BM25 | 꺼짐 | 구현(legacy 경로) |
| **RRF** | Dense 여러 목록 + BM25 목록을 **Qdrant Query API 1회**로 가중 RRF 병합. 질의 유형별 가중치 | k=60, 후보 40 | 구현·운영 |
| 메타데이터 보강 | LLM이 적재 시 뽑은 키워드·태그와 질의 키워드가 겹치면 점수 비율 가산(필터 아님 → 0건 없음) | +5% / +3% | 구현 |
| **Reranker** | bge-reranker-v2-m3, vLLM `/v1/score`. 후보 40개 전부 채점 후 상위 10개. 응답 인덱스·개수·점수 검증 | 임계값 0.25 | 구현·운영 |
| **Fallback** | 원인별 분기(아래 1.4) | 재시도 1회 | 구현 |
| 컨텍스트 | 임계값 → 중복 제거 → 문서당 최대 2청크 → 최대 6청크 → 문자·토큰 예산 | 40 → 10 → 6 | 구현 |
| 권한 | 권한 판단 함수 한 곳에서 검색·답변·출처·이미지 모두 적용, 활성 버전만 검색 | — | 구현 |
| **문서 파싱** | 아래 1.5 | — | 구현 |

질의 유형별 RRF 가중치(Dense / BM25)

| 질의 유형 | 기본(`legacy`) | SOP 프로필(`sop`, 11-11 추가·기본 꺼짐) |
|---|---|---|
| 법령 조문(제N조 등) | 0.7 / 1.5 | 0.7 / 1.5 (같음) |
| 개념 설명(그 외 대부분) | 1.5 / 0.7 | 1.0 / 1.5 |
| 메뉴·매뉴얼 | 0.8 / 1.5 | 1.0 / 1.5 |
| 사고 사례·서술형 | 1.5 / 0.8 | 1.0 / 1.5 |

### 1.3 11-10~11 검색 개선 (이번에 바뀐 것)

| 항목 | 문제 | 수정 | 적용 |
|---|---|---|---|
| 토큰 정책 v2 | 품번·규격이 BM25에서 사라짐("XG-500A"→`XG`, "M6"·"12N·m" 소실). Qdrant BM25도 하이픈·가운뎃점에서 다시 자름 | 코드·규격·N호기를 한 토큰 + 표준형(`xg500a`, `12nm`) + 조각. 적재·질의 동일. 설정 `KIWI_BM25_ENCODER_VERSION` | **dev 적용**(재계산 551포인트), 운영 v1 |

| 재계산 도구 | 토큰 정책을 바꾸면 기존 문서와 어긋남 | `scripts/rebuild_kiwi_bm25.py` — BM25만 재계산, 이전 버전 복원 유지 | 신규 |

### 1.4 Fallback

| 상황 | 대응 |
|---|---|
| 검색 성공, 관련성 미달 | 후보·재정렬 수 2배로 넓혀 1회 재검색, 임계값 0.1로 완화(컨텍스트 수는 유지) |
| Reranker 타임아웃·통신·응답 오류 | RRF 순위 상위 3개로 진행(척도가 다른 점수에 CE 임계값을 적용하지 않음) |
| LLM 생성 오류 | 확보된 컨텍스트로 생성 재시도 |
| Qdrant 장애·검색 타임아웃 | **재시도 없이 오류 종료** — 장애가 "문서 없음"으로 위장되지 않게 |
| 재시도 후에도 근거 부족 | "찾지 못했다" 안내(R4-2) |

없는 것: Qdrant 장애 시 다른 검색 DB로 자동 전환.
주의: Reranker 장애 경로에서는 관련성이 검증되지 않은 청크가 답변에 들어갈 수 있다.

근거: [fallback_handler.py](../../adrag_backend/app/graphs/nodes/fallback_handler.py)

### 2.3 최근 측정 결과 (dev, SOP 컬렉션 1개)

토큰 정책 v1 → v2 (BM25 + Dense 하이브리드, 리랭커 전, 각 80건)

| 질의 | 지표 | v1 | v2 |
|---|---|---:|---:|
| 품번·규격 포함 | 하이브리드 Hit@10 | 0.762 | **0.850** |
| 품번·규격 포함 | BM25 Hit@10 | 0.787 | **0.925** |
| 일반 | 하이브리드 Hit@10 | 0.975 | 0.975 |

가중치·원문 비중 (리랭커 후 Hit@1, 각 60건, v2 기준)

| 설정 | 품번+명사 | 품번만 | 절차형 | 일반 |
|---|---:|---:|---:|---:|
| 현재 운영 설정 | 0.883 | 0.833 | 0.967 | 0.967 |
| SOP 프로필 + 원문 비중 0.5 + RRF k=20 | **0.983** | **0.950** | 0.983 | 0.967 |

읽는 법
- 리랭커가 순위를 크게 끌어올리지만, **후보 40개 안에 못 들어온 정답은 살리지 못한다** → 후보 단계(토큰화·가중치)가 중요.
- 가장 큰 개선 요인은 **LLM 재작성 질의가 원문을 희석하던 것**을 막은 것(재작성은 유지, 원문 비중 50%).
- 일반 질의는 어떤 설정에서도 떨어지지 않았다.
- 절차형 질의는 리랭커 최고점이 임계값 0.25를 넘는 비율이 40~47% → 실제 질의로 확인 필요(답변 거부 증가 가능성).

과거 보관 결과(2026-06, 법령 문서): Recall@10 81.7~87.5%, 인용 정확도 36.7~37.5% — **검색 방식 변경 전 수치라 현재 성능으로 제시하지 않는다.**

### 2.4 실증 운영 검증 방법 (계획)

| 단계 | 내용 |
|---|---|
| 1. SOP 골든셋 | 실제 SOP의 준비·작업·검사 절차, 품번·부품·사진 위치, 유사 모델 구분, 띄어쓰기·약어·**STT 오류**, 여러 청크 분산, **문서에 없는 질문·권한 밖 질문** |
| 2. 검색 품질 | Dense / Hybrid / Hybrid+Reranker를 같은 골든셋으로 비교(튜닝셋·시험셋 분리, 모델·청킹·버전·후보 수 고정) |
| 3. 답변 품질 | 운영과 같은 설정으로 답변·근거·사진·거절·권한 |
| 4. 운영 성능 | 동시 질의·적재 병행 시 P95 지연·오류·GPU 메모리 |
| 5. 운영 루프 | 결과 코드·사용자 피드백으로 실패 질의 수집 → 검수 후 회귀셋 추가 |

평가 시 알려진 차이(공정한 비교를 위해 맞출 것)
- 자동 생성기는 검색 실패 질문을 한 번 다시 만들어 **현재 검색기에 유리한 쪽으로 쉬워질 수 있다** → 최초 실패 질문 별도 보존.
- Full 평가는 누락 인용을 한 번 보정 → 운영 첫 응답보다 점수가 좋게 나올 수 있다.
- 평가 API 기본 후보 수(10→5)와 운영(40→10→6)이 다르다.

## 3. 로컬 LLM 서빙 구성과 GPU 배분

### 3.1 서빙 방식

- 모델마다 **별도 vLLM 프로세스·포트**(OpenAI 호환 API). LLM은 `/v1/chat/completions`, 임베딩은 pooling `/v1/embeddings`, Reranker는 pooling `/v1/score`.
- 모든 모델은 사내 GPU에서 자체 서빙, 외부 AI API 호출 없음. 용도별 모델은 설정만으로 교체(R7-1).
- `--gpu-memory-utilization`은 **프로세스별 메모리 예산**이며 연산을 격리하지 않는다 → 같은 GPU의 모델은 연산·대역폭을 공유.

### 3.2 운영 배치 (H100 80GB × 8 중 2장 사용, 배포 스크립트 기준)

| GPU | 서비스 | 모델 | 메모리 예산 | 주요 설정 | 기록된 사용량(11-05) |
|---|---|---|---:|---|---:|
| 0 | LLM | Qwen3.5-9B (BF16) | 0.70 | 입력 24,576토큰, 동시 16 | 약 55.8GB |
| 0 | 문서 파서 | Docling·OCR | — | 별도 서비스 | 약 2.6GB(대기) |
| 1 | 임베딩 | Qwen3-Embedding-4B | 0.18 | 입력 8,192토큰 | 약 14.9GB |
| 1 | Reranker | bge-reranker-v2-m3 (FP16) | 0.05 | — | 약 2.3GB |
| 1 | STT | Qwen3-ASR-1.7B | 0.15 | 입력 4,096, 동시 8 | 약 7.2GB |
| 1·3 | VLM·TTS(시범) | VLM 후보 시험 중, TTS는 GPU 3 배치 결정 | — | — | — |

- LLM 55.8GB는 가중치 크기가 아니라 vLLM이 미리 잡은 KV 캐시 등을 포함한 예산이다.
- GPU 1 예산 합계는 0.9 이하로 관리(VLM을 GPU 1에 올리면 0.73, TTS까지 올리면 0.97로 초과 → TTS는 GPU 3).

근거: [run-llm.sh](../../deploy/gpu/opt/yest/chatbot/vllm/app/run-llm.sh), [run-embed.sh](../../deploy/gpu/opt/yest/chatbot/vllm/app/run-embed.sh), [run-rerank.sh](../../deploy/gpu/opt/yest/chatbot/vllm/app/run-rerank.sh), [GPU 사용 현황](GPU_사용현황_메일_20261105.md), [VLM 시범 배포](운영배포_VLM테스트_20261105.md)

### 3.3 GPU 1장 공존 경험 (dev)

dev 백엔드 설정의 LLM·임베딩·Reranker 포트(8001~8003)는 **GPU 1장에 세 모델을 함께** 띄우는 개발 스크립트([run_adrag_model_v2.sh](../../vllm/app/run_adrag_model_v2.sh), `CUDA_VISIBLE_DEVICES=0`)와 일치한다. 이 구성으로 개발·평가 중이다(서버의 실제 GPU 점유는 이번에 직접 확인하지 않음).

| 모델 | 메모리 예산 | 설정 |
|---|---:|---|
| Qwen3.5-9B | 0.49 | 입력 24,576, 동시 16 |
| Qwen3-Embedding-4B | 0.12 | 입력 **2,048**(운영 8,192보다 축소) |
| bge-reranker-v2-m3 | 0.05 | — |

11-10~11 실측(질의 240건 × LLM 재작성·임베딩·리랭커 수천 회 호출)도 이 구성에서 수행했다. 동시 사용자 부하 시험은 하지 않았다. dev GPU의 종류는 저장소 기록으로 확정하지 못했다.

### 3.4 L40S 48GB 1장으로 가능한가?

**결론: LLM·임베딩·Reranker 3개는 메모리 예산을 다시 잡으면 올릴 가능성이 높다. 현재 운영 설정(LLM 입력 24K·동시 16)과 처리량을 그대로 유지하는 것은 부하 시험 전에는 보장할 수 없다. STT·VLM·TTS·OCR까지 한 장에 상주하는 것은 어렵다.**

16비트 가중치 개략치

| 모델 | 가중치 | 비고 |
|---|---:|---|
| Qwen3.5-9B | 약 18GB | + KV 캐시(입력 길이·동시 수에 비례) |
| Qwen3-Embedding-4B | 약 8GB | + 배치 활성값 |
| bge-reranker-v2-m3 | 약 1.1GB | |
| 합계 | **약 27GB** | 48GB 중 남는 약 20GB를 KV 캐시·CUDA 컨텍스트(프로세스당 수백 MB~1GB)·파서가 나눠 씀 |

시작점 예산(안, 미검증)

| 모델 | 예산 | 근거 |
|---|---|---|
| LLM | 0.55~0.60 (26~29GB) | 가중치 18GB + KV 8~11GB → 입력 8K~16K·동시 4~8 수준으로 축소 |
| 임베딩 | 0.20 (약 9.6GB) | dev처럼 0.12(약 5.8GB)로는 가중치 8GB도 못 담음 → 비율 그대로 복사 금지 |
| Reranker | 0.05 (약 2.4GB) | 현재와 같음 |
| 합계 | 0.80~0.85 | 나머지는 파서·여유 |

고려 사항
- L40S는 H100보다 메모리 대역폭이 낮아(약 864GB/s) **LLM 토큰 생성 속도가 느려진다** → 응답 지연 실측 필요.
- LLM 입력 한도를 줄이면 backend 컨텍스트 예산(`VLLM_MAX_MODEL_LEN`, `MAX_PROMPT_TOKENS`)도 같이 줄여야 한다.
- 부족하면 LLM FP8(L40S 지원)·더 작은 임베딩 모델을 비교하되, 바꾼 뒤 검색·답변 품질을 다시 측정해야 한다.

검증 순서: ① 3개 모델만 축소 설정으로 기동 → ② 단일·동시 질의(P50/P95) → ③ 문서 적재 병행 시 최대 메모리 → ④ 부족 시 FP8·소형 모델 비교.

## 4. pgvector 하이브리드 검색과 비교

### 4.1 결론

**현 단계에서는 Qdrant 유지가 합리적이다.** 다만 pgvector와 같은 데이터·조건으로 비교 실험을 하지 않았으므로 "품질·속도가 더 좋다"고는 말하지 않는다.

### 4.2 근거

| 관점 | 현재 Qdrant 구성 | pgvector로 같은 것을 하려면 |
|---|---|---|
| 한국어 키워드 검색 | Kiwi 토큰 → BM25 sparse, **IDF를 Qdrant가 컬렉션 단위로 자동 계산** | PostgreSQL 전문 검색(`ts_rank`)은 BM25가 아니고 한국어 형태소 분석기가 없음. `sparsevec`에 BM25 가중치를 넣으면 **IDF를 직접 계산·갱신**해야 함(또는 별도 확장) |
| 하이브리드 병합 | Query API 1회로 Dense 여러 목록 + Sparse 후보·가중 RRF | SQL로 후보 쿼리·RRF 조합 직접 작성 |
| 벡터 차원 | Qwen3-Embedding-4B **2,560차원** 그대로 HNSW | `vector` HNSW는 최대 2,000차원 → `halfvec`(최대 4,000) 또는 차원 축소 필요 |
| 권한·활성 버전 필터 | Dense·Sparse 후보 검색에 같은 필터를 넣어 함께 거름 | 근사 검색 + 강한 필터 시 후보 부족 가능 → iterative scan 설정·튜닝 필요 |
| 기존 기능 연동 | 컬렉션·버전·복원·권한·적재 흐름, BM25 재계산 도구까지 연결됨 | 저장·검색 계층 전체 재작성 + 재검증 |
| 부하 분리 | 검색 부하가 업무 DB와 분리 | 업무 DB와 자원 공유 |

**이번 실측이 시사하는 것**: 품번 질의 1위 정확도를 0.88 → 0.98로 올린 요인은 **토큰화(v2)·가중치·원문 질의 비중**이었다. 모두 DB와 무관한 검색 설계다. 즉 DB를 바꿔 얻을 품질 이득보다, 같은 설계를 다른 DB에 다시 구현하는 비용·위험이 크다.

### 4.3 pgvector가 유리한 점 (공정하게)

- 메타데이터와 벡터를 **한 트랜잭션**으로 처리 → 현재 PostgreSQL·Qdrant 이중 저장의 일관성 관리(적재·버전 변경·삭제) 부담이 없다.
- 문서 버전·권한 테이블과 SQL 조인, 백업·복구 대상 단순화.
- 데이터 규모가 작은 1차 범위에서는 성능 차이가 크지 않을 수 있다.

### 4.4 비교가 필요할 때의 실험 조건

| 고정 | 비교 |
|---|---|
| 같은 문서·청크·임베딩(2,560차원) | Recall@K, Hit@K |
| 같은 Kiwi 토큰·BM25(IDF 포함) | 품번·규격 정확 검색 성공률 |
| 같은 후보 수·RRF·Reranker | MRR·NDCG·최종 답변 품질 |
| 같은 권한·활성 버전 필터 | 필터 후 후보 누락·권한 위반 0건 |
| 같은 동시 부하 | P50/P95/P99, 처리량 |
| 같은 적재·변경 시나리오 | 갱신 시간·일관성·운영 비용 |

설명용 한 문장
> 한국어 Kiwi BM25와 Dense 검색을 Qdrant 서버 측 가중 RRF로 결합하고, 로컬 Reranker와 원인별 Fallback까지 구현했다. 최근 품질 개선은 DB가 아니라 토큰화·가중치 설계에서 나왔고, 기존 기능 통합도와 전환 비용을 고려해 Qdrant를 유지한다. pgvector 대비 품질·성능 우위는 동일 조건 비교로 검증할 과제다.

## 5. 예상 질문과 답변

| 질문 | 답 |
|---|---|
| 검색 정확도는 몇 %인가? | 실제 작업자 질의 골든셋이 아직 없어 공식 수치는 없다. dev 합성 질의 기준 리랭커 후 일반 질의 Hit@1 0.967, 품번 질의 0.883(개선 설정 0.983). |
| Reranker를 Qwen3-Reranker로 바꾸지 않나? | 후보로 검토 중. 공개 벤치마크는 다국어에서 bge보다 높지만 한국어 SOP 검증은 없다. 교체 시 vLLM 서빙 옵션·입력 템플릿·임계값 재보정이 필요해 같은 골든셋 A/B 후 결정. |
| 검색이 실패하면? | 관련성 미달은 범위를 넓혀 1회 재검색, 그래도 없으면 "찾지 못했다"고 안내. 시스템 장애는 오류로 구분해 '문서 없음'으로 위장하지 않는다. |
| 권한 없는 문서가 섞일 수 있나? | 권한 판단 함수 한 곳에서 검색 필터·출처·이미지 API에 모두 적용. 실제 사용자별 API 검증은 실증 단계에서 다시 한다. |
| 사진·도면은 검색되나? | 사진은 근거 청크에 연결해 답변·출처에 표시. 이미지 자체 검색·도면 의미 이해(VLM)는 시범 단계. |
| GPU 몇 장 필요한가? | 운영은 H100 2장(LLM 1장, 나머지 모델 1장). 핵심 3모델은 1장 공존 구성으로 dev 운영 중. L40S 1장은 축소 설정으로 가능성, 부하 시험 필요. |
| 왜 pgvector가 아닌가? | 4.2 표. 한국어 BM25 IDF·서버 측 RRF·2,560차원·필터 연동이 이미 되어 있고, 품질은 DB보다 검색 설계가 좌우했다. 우위는 비교 실험 전이라 주장하지 않는다. |

## 6. 설명할 때 주의 (말하지 않을 것)

- 6월 평가 수치(Recall 81~88%)를 현재 성능으로 제시하지 않는다.
- 합성 질의 결과를 "실사용 정확도"로 표현하지 않는다(방향 확인용).
- L40S 1장을 "가능하다"고 단정하지 않는다(축소 설정 후보, 부하 시험 전).
- pgvector보다 "빠르다/정확하다"고 말하지 않는다(비교 실험 없음).
- 토큰 정책 v2·가중치 프로필은 **dev 기준**이며 운영 미적용이다.
