## 1. 항목별 판단

| 지시서 항목 | 판단 | 근거(코드 확인) |
|---|---|---|
| **P0-1** 부서명 중복·주제 정규화 | **보류** | ① 부서명 변경은 사용자·컬렉션 갱신을 **한 트랜잭션**으로 처리한다(`department_repository.update`) — 지시서가 우려한 부분 실패는 현 코드에선 생기지 않는다. ② 주제를 전역 마스터로 할지 부서별로 할지는 **권한 단위(Q-5, D-15) 결정**에 달려 있다: 현재 "같은 부서가 만든 컬렉션만" 볼 수 있어 모델(주제)을 부서 너머로 줄 수 없음. 지금 정규화하면 고객 결정 후 다시 바꿀 가능성이 높다. ③ `tb_collections.department_name`은 주석상 "생성 부서 스냅샷"이지만 실제로는 부서명 변경 때 함께 갱신된다 → **"현재 부서명 사본"으로 정의서 설명만 정정**. ④ `tb_user_collection_permissions`는 판단에 쓰이지 않음(검토 보고서 3(d)) → Phase 4 권한 통합 때 제거 또는 단일 원천 연결 결정 |
| **P0-2** 리소스·분석 참조 무결성 | **일부 적용 + Phase 2** | 분석 결과는 항상 존재하는 리소스에 대해 등록된다(`register_analysis`가 리소스 확인) → **`resource_id` FK ON DELETE CASCADE 지금 적용**(staging rollback 시 분석 행도 삭제). 리소스→문서 FK는 지금 못 건다: docling 경로는 리소스가 파싱 중(문서 행이 생기기 전)에 staging으로 들어온다. → **Phase 2에서 staging 테이블을 분리**하고 확정 리소스에 문서 FK(ON DELETE CASCADE)를 건다(지시서 권장안 1). `parse_job_id`는 외부 docling 작업 ID라 FK 없음(사유 문서화). `status` 이중 의미는 Phase 2의 `review_status` 분리와 함께 정리 |
| **P0-3** 대화 이력 JSONB → 메시지 행 | **채택, Phase 4 적용** | 문제는 실재: 이력과 로그를 **질문·답변 텍스트로 매칭**(`routes/query.py:230-262`), 동시 요청 시 마지막 쓰기 우선. 다만 TOAST 비대화는 작다(이력은 최근 20개만 유지, `rag_service.py:267·317`). 메시지 테이블은 답변 경로(`rag_service` 스트림/비스트림 2곳, 이력 API)를 바꾸는데, 같은 코드를 Phase 4에서 `log_id`=message_id·SSE `final{message_id}`·TTS를 위해 다시 고친다 → **Phase 4에서 한 번에**. 설계는 지시서안 + `query_log_id` UNIQUE. 기존 이력 이관: dev 데이터 0건, 운영은 순서대로 메시지 행으로 변환(로그 연결은 하지 않음). 재생성 응답: 현재 기능 없음 → `sequence_no`만 |
| **P0-4** 이벤트·인용 문서 FK | **불채택** | 지시서 전제("문서는 soft-delete만")가 **사실과 다르다**: 대화 주제 삭제 시 `DELETE FROM tb_documents`로 **물리 삭제**한다(`collection_service.py:144·243`). FK를 걸면 주제 삭제가 막히거나(NO ACTION), 감사 기록이 지워지거나(CASCADE), 어느 문서였는지 잃는다(SET NULL). 인용은 Qdrant payload의 문서 ID에서 오므로 RDB·Qdrant가 어긋나면 FK가 통계 행을 버리게 된다. → **FK 없이 유지**(0001 설계 의도), 정합성은 야간 대조(WRK-06 `reconcile_index`, Phase 5)로 점검. 청크 단위 출처는 `context_meta` 보강으로(검토 보고서 2절) |
| P1 데이터 제약 | **채택·적용** | 사전 점검(dev DB·원본 SQLite) 위반 0건. `status`-`current_step` 조합과 평가 "완료 시 시각" 조건은 코드 경로가 여럿이고 효과가 작아 제외 |
| P1 `tb_app_settings.updated_by` | **감사 스냅샷으로 결정(FK 없음)** | 관리자 ID 문자열 기록용. 사용자 삭제와 무관하게 남아야 함 |
| P1 `updated_at` 트리거 | **채택·적용** | 14개 테이블. 앱이 쓰는 값보다 DB 시각이 최종 |
| P1 인덱스 | **측정 후 일부 채택**(3장) | 쓰이는 쿼리와 1:1로 대응하는 것만, 단일 인덱스는 대체·삭제 |
| P1 `UNIQUE NULLS NOT DISTINCT (created_by, display_name)` | **불채택** | `created_by`는 사용자 삭제 시 `SET NULL`. NULLS NOT DISTINCT면 같은 이름 컬렉션을 가진 두 사용자를 지울 때 **사용자 삭제가 유일성 위반으로 실패**한다 |
| P2 질의 로그 payload 분리·파티셔닝·집계 | **불채택(관측 먼저)** | 지시서도 선구현 금지. 운영 이관 후 월별 행 수·테이블/TOAST 크기·통계 API p95를 기록해 판단 |
| P2 다중 워커 claim | **채택, Phase 3** | `FOR UPDATE SKIP LOCKED`, 임대·하트비트·재시도·`job_type`(검토 보고서 B1) — 큐 재설계와 같이 |

## 2. 적용 내역 — Alembic `0002_schema_hardening`

파일: `adrag_backend/migrations/versions/0002_schema_hardening.py` (upgrade·downgrade)

### 2.1 CHECK 제약 (12)

| 테이블 | 제약 | 조건 |
|---|---|---|
| tb_documents | `ck_tb_documents_counts_nonneg` | total_pages·chunk_count NULL 또는 ≥0 (file_size는 0001에 있음) |
| tb_documents | `ck_tb_documents_version_no` | version_no ≥ 1 |
| tb_query_logs | `ck_tb_query_logs_metrics_nonneg` | 응답 시간(s·ms)·검색 청크 수·토큰 수·비용 NULL 또는 ≥0 |
| tb_eval_datasets / tb_eval_runs | `*_progress_nonneg` | progress_done·progress_total ≥ 0 |
| tb_eval_goldsets | `ck_tb_eval_goldsets_counts` | item_count ≥ 0, version ≥ 1 |
| tb_eval_run_metrics | `ck_tb_eval_run_metrics_counts_nonneg` | 4개 건수 ≥ 0 |
| tb_eval_item_results | `ck_tb_eval_item_results_latency_nonneg` | latency_ms NULL 또는 ≥ 0 |
| tb_spreadsheet_resource_analyses | `ck_tb_resource_analyses_confidence` / `_version` | confidence 0~1, analysis_version ≥ 1 |
| tb_ingest_jobs | `ck_tb_ingest_jobs_current_step` | queued·validate·parse·chunk·embed·index·completed (현재 코드 값, Phase 3에서 확장) |
| tb_app_settings | `ck_tb_app_settings_json_valid` | value_type='json'이면 `pg_input_is_valid(setting_value,'jsonb')` |

### 2.2 FK (1)

`tb_spreadsheet_resource_analyses.resource_id → tb_spreadsheet_resources(resource_id) ON DELETE CASCADE`

### 2.3 인덱스 (추가 4, 삭제 4)

| 추가 | 대응 쿼리 | 대체·삭제 |
|---|---|---|
| `idx_docs_active_created (created_at DESC) WHERE deleted_at IS NULL` | 문서 목록(전체·컬렉션) | — |
| `idx_logs_user_created (user_id, created_at DESC)` | 사용자 질의 이력 | `idx_logs_user` |
| `idx_logs_session_created (session_id, created_at DESC) WHERE session_id IS NOT NULL` | 세션 이력, 세션 삭제 FK(SET NULL) | `idx_logs_session` |
| `idx_logs_collection_created (collection_id, created_at DESC) WHERE collection_id IS NOT NULL` | 컬렉션 필터 이력, 컬렉션 삭제 FK | `idx_logs_collection` |
| `idx_ingest_jobs_active_created (status, created_at) WHERE status IN ('queued','running')` | 기동 시 재큐, 주제 삭제 전 진행 작업 확인 | `idx_ingest_jobs_status` |

임시 DB `rag_chatbot_perf`(측정 후 삭제)에 합성 데이터: 문서 5만(10% 삭제), 사용자 500, 세션 5천, 질의 로그 40만, 적재 작업 10만(대기·실행 200). 0001 → 측정 → 0002 → ANALYZE → 측정.

## 5. 운영 이관 절차 변경 (Phase 1.5 설계 6.2 보완)

`alembic upgrade 0001_baseline` → `migrate_sqlite_to_postgres.py`(dry-run → 실제) → **`alembic upgrade head`(0002가 이관 데이터를 검증)** → 앱 기동. 0002의 제약 위반이 나오면 자동 수정하지 않고 위반 행을 보고 후 결정.

`alembic downgrade 0001_baseline`(트리거·함수·인덱스·FK·CHECK만 제거, 데이터 영향 없음).
