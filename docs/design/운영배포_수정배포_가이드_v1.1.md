## 4. WAS 배포 (평소 배포)

### 4.1 묶음 만들기 (개발 PC)

이 PC의 WSL에는 Docker만 있고 npm·node는 Windows에만 있다. 그래서 **프런트는 Windows에서 빌드하고, 묶음은 WSL에서 `--skip-frontend-build`로 만든다.** WSL에 `svnversion`도 없어 묶음 `VERSION`의 `svn=`이 `unknown`이 된다(동작 영향 없음).

```powershell
# 1. 프런트 빌드 (Windows PowerShell) — 화면 코드를 바꿨을 때만. package.json 을 바꿨으면 npm ci 먼저
#    백엔드만 바꿨으면 생략하고 서버에서 --backend-only 로 반영한다(dist 에 손대던 화면이 있어도 운영에 안 올라간다)
cd D:\Dev\SVNLocal\advanced-rag-voucher\adrag_frontend
npm run build                      # → adrag_frontend\dist\
```

```bash
# 2. 묶음 만들기 (WSL — PowerShell 에서 wsl 입력) — 1~2분
cd /mnt/d/Dev/SVNLocal/advanced-rag-voucher
bash deploy/webwas/chatbot/build_package.sh --skip-frontend-build
# 성공하면 마지막 줄: 묶음: …/offline/chatbot-<YYYYMMDD-HHMM>.tar.gz (2.5M), 이미지 포함=0
```

결과: `D:\Dev\SVNLocal\advanced-rag-voucher\deploy\webwas\mnt\a\chatbot\offline\`의 `chatbot-<버전>.tar.gz`, `chatbot-<버전>.tar.gz.sha256`, `deploy.sh` → 4.2로 올린다.

| 상황 | 명령 |
|---|---|
| 평소(소스·화면만 바뀜) | `build_package.sh --skip-frontend-build` |
| 처음 설치, `adrag_backend/requirements.txt` 또는 `deploy/webwas/chatbot/Dockerfile.runtime`을 바꿈 | `build_package.sh --skip-frontend-build --with-image` (수백 MB~수 GB) |
| 버전 이름을 직접 정함 | `build_package.sh --skip-frontend-build 20261030-pathfix` (없으면 날짜-시각) |

- 런타임 이미지 태그는 `requirements.txt`와 `Dockerfile.runtime`의 해시다. 둘 중 하나를 바꾸고 이미지 없이 묶으면 서버 `deploy.sh`가 1단계에서 "서버에 … 가 없고 묶음에도 이미지가 없습니다"라며 멈춘다 → `--with-image`로 다시 만든다.
- `offline/`의 옛 묶음은 되돌리기(4.6)에 쓰므로 최근 2~3개는 남긴다. `deploy/` 폴더는 SVN에 커밋하지 않는다.

스크립트가 하는 일: 런타임 이미지 확인(없으면 빌드) → 네트워크 없이 의존성 불러오기 시험 → backend 허용 목록 복사, **엑셀·PDF·도면·이미지·음성·DB 파일이 섞이면 멈춤** → 프런트 담기(개발용 `admin-mockup.html` 제외), CDN 주소 경고 → 설정 파일 LF 변환 → 체크섬.

묶음 안 (`chatbot-<버전>/`):

```
VERSION        버전·빌드 시각·런타임 이미지·svnversion
RUNTIME_IMAGE  이 소스가 쓰는 이미지 태그 (chatbot-backend-runtime:<해시12>)
SHA256SUMS     안의 모든 파일 해시
backend/       허용 목록만: main.py init_database.py alembic.ini requirements.txt app/ excel_ingest/ migrations/ scripts/
frontend/      adrag_frontend/dist
config/        docker-compose.prod.yml · compose.env.example · .env.example · chatbot.service · chatbot.conf · check_rocky.sh
image/         (--with-image 일 때만) chatbot-backend-runtime_<해시>.tar.gz
```

넣지 않는 것: `instance/`, `.env`, `tests/`, `offline_evaluation/`, `app/graphs/workflow-graphs/`, `__pycache__`.

**자주 걸리는 문제**

| 메시지 | 원인 · 해결 |
|---|---|
| `docker 가 없습니다 — WSL 에서 실행합니다.` | Windows 셸(Git Bash 등)에서 실행했다. WSL에서 실행한다 |
| `Cannot connect to the Docker daemon` | WSL Docker가 꺼져 있다. `sudo service docker start` |
| `npm 이 없습니다 — Windows 에서 npm run build 후 …` | `--skip-frontend-build`를 빠뜨렸다 |
| `…/adrag_frontend/dist/index.html 이 없습니다.` | 1번(`npm run build`)을 하지 않았다 |
| `!! 묶음에 넣으면 안 되는 파일 — 반출 중지:` | 허용 목록 폴더(`app`·`scripts` 등)에 `.env`·DB·엑셀·PDF·이미지가 들어 있다. 표시된 파일을 소스 폴더에서 치운다(절대 규칙 3) |
| `!! 경고: 프런트가 외부 CDN 을 부른다(P-8 미해결)` | 기존 경고라 묶음은 만들어진다 |
| `/nonexistent/.cache/pip … not writable` | 이미지 안 의존성 점검 경고라 무시한다. `No broken requirements found`·`imports ok`면 정상 |

### 4.3 반영 (WAS, sychoi)

```bash
cd /mnt/a/chatbot/offline && chmod +x deploy.sh
./deploy.sh                                   # 가장 최근에 올린 chatbot-*.tar.gz (특정 판: ./deploy.sh chatbot-<버전>.tar.gz)
sudo systemctl restart chatbot && sleep 5 && curl -s http://127.0.0.1:8081/health
```

`deploy.sh` 단계: 체크섬 → 풀기 → **백업**(교체할 쪽만, 아래) → (이미지 load) → backend 소스 교체 → 프런트 교체 → `compose.env` 이미지 태그 → **`alembic upgrade head`** → 설정 점검 → 설정 파일 차이 알림 → 적용 기록. 실패하면 그 단계에서 멈추고 실행 중인 서비스는 그대로다.

**교체 범위** — 묶음은 같고, 옵션으로 서버에 반영할 쪽만 고른다. 옵션은 묶음 이름 앞에 쓴다.

| 명령 | 이미지·backend 소스 | 프런트 | DB 마이그레이션 | restart |
|---|---|---|---|---|
| `./deploy.sh chatbot-<버전>.tar.gz` (기본) | 교체 | 교체 | 실행 | 필요 |
| `./deploy.sh --backend-only chatbot-<버전>.tar.gz` | 교체 | **그대로** | 실행 | 필요 |
| `./deploy.sh --frontend-only chatbot-<버전>.tar.gz` | **그대로** | 교체 | 건너뜀 | 필요 없음 (Ctrl+F5) |

- API와 화면이 함께 바뀐 기능은 옵션 없이 둘 다 교체한다. 한쪽만 올리면 화면과 API가 맞지 않을 수 있다.
- 적용할 때마다 `/opt/yest/chatbot/DEPLOYED`에 `날짜 묶음 범위 이미지태그`가 한 줄씩 쌓인다. 지금 운영 판 확인: `tail -5 /opt/yest/chatbot/DEPLOYED` — backend 판은 마지막 `all`/`backend` 줄, 프런트 판은 마지막 `all`/`frontend` 줄이다.

**백업**(2026-11-04) — 교체 직전에 지금 운영 파일을 `/mnt/a/chatbot/backup/<YYYYMMDD-HHMMSS>_<범위>/`에 담는다. 폴더는 없으면 만든다(`sychoi` 750).

| 파일 | 언제 | 내용 |
|---|---|---|
| `frontend.tar.gz` | 프런트 교체 시 | `/opt/yest/chatbot/frontend` 통째 |
| `backend.tar.gz`, `compose.env` | backend 교체 시 | `/opt/yest/chatbot/backend`(`instance/` 제외), 이미지 태그 |
| `DEPLOYED.tail` | 항상 | 적용 기록 마지막 5줄(백업 시점 운영 판) |
| `RESTORE.txt` | 항상 | 이 백업으로 되돌리는 명령 |

최근 10개만 남기고 오래된 것은 지운다(`BACKUP_KEEP=20 ./deploy.sh …`로 바꿀 수 있다). **DB는 백업하지 않는다**(Cloud DB 백업 정책을 따른다).

- **restart는 직접 한다.** `deploy.sh`는 서비스를 다시 시작하지 않는다. 실행 중인 프로세스는 옛 코드를 들고 있다.
- **엑셀 등록이 진행 중이면 끝난 뒤** restart 한다(적재 큐가 프로세스 안에 있다).
- 프런트만 바꾼 배포는 restart 없이도 새 화면이 나온다(브라우저 새로고침). 해도 무방하다.

### 4.5 경우별 추가 작업

| 바꾼 것 | 추가로 할 일 |
|---|---|
| 백엔드·프런트 코드만 | 없음 |
| `requirements.txt`, `Dockerfile.runtime` | 묶음을 `--with-image`로 만든다(이미지 태그가 바뀐다) |
| DB 스키마(Alembic) | 없음(`deploy.sh`가 upgrade). **되돌릴 revision**을 Phase 보고서에 적어 둔다 |
| 서버 `.env` 값만 | 묶음 필요 없음. 서버 `/opt/yest/chatbot/.env`를 `vi`로 고치고 `sudo systemctl restart chatbot`. 저장소 `deploy/webwas/opt/yest/chatbot/.env`도 같게 맞춘다 |
| `.env`에 **새 설정 이름** 추가 | 코드에 기본값이 있으면 그대로 둬도 된다. 운영 값을 넣을 때만 위처럼 |
| `docker-compose.prod.yml` | `deploy.sh`가 "다릅니다"라고 알린다 → `install -m 640 <풀린 폴더>/config/docker-compose.prod.yml /opt/yest/chatbot/` → restart |
| `chatbot.service` | `sudo install -m 644 <풀린 폴더>/config/chatbot.service /etc/systemd/system/` → `sudo systemctl daemon-reload` → restart |
| `chatbot.conf` (nginx) | MAIP 담당에게 알린 뒤 `sudo install -m 644 <풀린 폴더>/config/chatbot.conf /etc/nginx/conf.d/` → `sudo nginx -t && sudo systemctl reload nginx` |

`<풀린 폴더>` = `/mnt/a/chatbot/offline/chatbot-<버전>`

### 4.6 되돌리기

| 상황 | 방법 |
|---|---|
| 새 판에 문제(DB 변경 없음) | `./deploy.sh chatbot-<이전 버전>.tar.gz` → `sudo systemctl restart chatbot` |
| 한쪽만 되돌림 | 화면만: `./deploy.sh --frontend-only chatbot-<이전>.tar.gz` (restart 없음) / backend만: `./deploy.sh --backend-only chatbot-<이전>.tar.gz` → restart. 이전 판은 `DEPLOYED`에서 찾는다 |
| 새 판이 Alembic revision을 올렸음 | ① **새 판 소스로** `DC="sudo docker compose --env-file /opt/yest/chatbot/compose.env -f /opt/yest/chatbot/docker-compose.prod.yml"` 후 `$DC run --rm --no-deps backend alembic downgrade <이전 revision>` ② `SKIP_MIGRATE=1 ./deploy.sh chatbot-<이전>.tar.gz` ③ restart |
| 런타임 이미지 문제 | 이전 묶음으로 되돌리면 이미지 태그도 돌아간다 |
| 이전 묶음이 없거나 서버 파일을 직접 고친 적이 있음 | 백업으로: `ls /mnt/a/chatbot/backup/` → 되돌릴 폴더의 `RESTORE.txt`를 열어 해당 줄만 실행(4.7 ⑦) |

- 이전 묶음(`chatbot-<버전>.tar.gz`, 풀린 폴더)과 **직전 런타임 이미지 태그**는 지우지 않는다.
- 이미지 정리: `sudo docker image ls chatbot-backend-runtime` → 지금·직전 태그만 남기고 `sudo docker image rm <태그>`.

### 5.2 포트 바꾸기

한 서비스의 포트를 바꾸면 **네 곳**을 같이 바꾼다. 하나라도 빠지면 WAS가 그 모델에 연결하지 못한다.

| # | 어디 | 무엇을 |
|---|---|---|
| ① | GPU 실행 파일 `run-<이름>.sh` | `--port <새 포트>` (그리고 `echo "… (<포트>)..."` 문구) — docling은 `docker-compose.yml`의 `ports: "<새 포트>:8008"`(호스트 쪽만 바꾸면 된다. 컨테이너 안 `PORT=8008`은 그대로 둬도 된다) |
| ② | WAS `.env` | 해당 `*_API_URL` / `DOCLING_PARSER_HOST`의 포트 부분 |
| ③ | NCP ACG `yest-gpu` 인바운드 | `<WAS_IP>/32 → TCP <새 포트>` 추가, 옛 포트 규칙 제거 (인프라 담당에게 요청 — **가장 먼저**) |
| ④ | 문서 | 이 문서 5.1 표, 서버별 가이드 0.2·1.1·1.5·5.3 |

**순서** (예: 임베딩 8102 → 새 포트)

```bash
# 0. ACG 에 새 포트 규칙이 들어갔는지 먼저 확인 (③)

# 1. 개발 PC — 저장소의 run-embed.sh 수정 (①), 저장소 WAS .env 수정 (②)

# 2. GPU 서버 (sychoi) — 고친 파일만 올려 설치
#    WinSCP: deploy\gpu\opt\yest\chatbot\vllm\app\run-embed.sh → /mnt/a/chatbot/offline/
sudo install -o vllm-admin -g vllm-admin -m 750 /mnt/a/chatbot/offline/run-embed.sh /opt/yest/chatbot/vllm/app/run-embed.sh
sudo sed -i 's/\r$//' /opt/yest/chatbot/vllm/app/run-embed.sh
sudo systemctl restart vllm@embed
sudo tail -f /mnt/a/chatbot/vllm/logs/embed.log          # "Uvicorn running on http://0.0.0.0:<새 포트>" → Ctrl+C
ss -ltn | grep ':<새 포트>'

#    docling 이면: docker-compose.yml 을 /opt/yest/chatbot/docling/ 에 install(root:adrag 640) → sudo systemctl restart docling-parser

# 3. WAS 서버 (sychoi) — .env 의 해당 URL 포트 수정 → restart
vi /opt/yest/chatbot/.env
sudo systemctl restart chatbot
DC="sudo docker compose --env-file /opt/yest/chatbot/compose.env -f /opt/yest/chatbot/docker-compose.prod.yml"
$DC run --rm --no-deps backend sh -c 'curl -s -o /dev/null -w "embed %{http_code}\n" -H "Authorization: Bearer $EMBEDDING_API_KEY" $EMBEDDING_API_URL/models'   # 200
```

- 포트가 다른 서비스나 다른 팀과 겹치지 않는지 먼저 본다: GPU 서버에서 `ss -ltnp | grep ':<새 포트>'` → 출력이 없어야 한다.
- 키·모델 이름은 포트와 무관하다. 그대로 둔다.
- 여러 개를 한 번에 바꿔도 순서는 같다(ACG → GPU → WAS).

### 5.3 그 밖의 GPU 변경

| 바꾼 것 | 방법 |
|---|---|
| vLLM 인자(메모리 비율, max-model-len 등) | 5.2의 2단계처럼 `run-*.sh`만 올려 설치 → `sudo systemctl restart vllm@<이름>`. `--max-model-len`을 바꾸면 WAS `VLLM_MAX_MODEL_LEN` / `EMBEDDING_MAX_MODEL_LEN`도 같이 |

## 6. 하지 않는 것

- 운영 서버에서 소스를 직접 고치거나 빌드하지 않는다(서버 소스는 `deploy.sh`가 매번 덮어쓴다).
- `docker compose up/down`을 직접 쓰지 않는다 → `systemctl`.
- `.env`·`env.sh`의 값을 문서·메신저·로그에 남기지 않는다.
- `svn commit` / `git push`는 하지 않는다(로컬 개발 규칙). 묶음(`mnt/`)과 실제 값 파일은 SVN에 넣지 않는다.
